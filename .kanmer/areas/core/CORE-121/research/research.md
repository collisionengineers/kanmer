# Research — CORE-121: bootstrap ownership and backward-move contract

## Question

What is the smallest change to the stable v0.3.12 core/MCP contract that (a) lets a claim held by a dead controller be transferred without `force`, (b) makes Review → Implementing a sanctioned, audited move that keeps the same branch/worktree/PR, and (c) lets `get_execution_packet` resume that work — without introducing leases (CORE-115), a revision protocol (CORE-114), a new tool, or a board format bump?

## Findings

- **Claims are four plain frontmatter fields with no expiry.** `takeTicket` (`packages/core/src/store.ts:862-910`) sets `taken_at`, `branch`, optional `worktree`, `assignee`; the only override is `force`, which also deletes `worktree` ("a force-retake must not keep a stale worktree", `:899-900`). `releaseTicket` (`:913-926`) clears the three claim fields but not `assignee`. `TakeTicketInput` (`types.ts:538-548`) has no expiry/transfer notion. MCP `take_ticket` (`packages/mcp-server/src/index.ts:1206-1236`) exposes `action: take|release` only; the tool count is 37 (`smoke.mjs:62`, `AGENTS.md:404`, `docs/manual/connect.md:145`).
- **Unknown frontmatter keys survive round-trips.** `ItemFrontmatterSchema` is `.passthrough()` (`types.ts:378-428`) and `serialiseItem` appends unknown keys after `KEY_ORDER` (`frontmatter.ts:5-33, 49-58`). New optional fields are therefore readable and preserved by the installed v0.3.12 GUI/MCP; they need adding to the schema and `KEY_ORDER` only for typing and stable ordering. No `migrate_board` step is required.
- **Backward moves are unguarded and unaudited.** `boundariesCrossed` returns `[]` when `to <= from` (`gates.ts:166-172`), so `assertMoveAllowed` (`store.ts:775-791`) checks only existence, `expectedUpdated` and target-stage validity. There is no owner check on `move_item` and no `reason`. `stageEntered` is first-entry-only (`store.ts:706-714`), so a return to Implementing leaves no committed trace (CORE-113 shows `implementing` stamped after `review`).
- **The packet already has most of the resume lane.** `getExecutionPacket` (`execution-packet.ts:432-501`) refuses when `taken_at && status !== "implementing"` (`:471-479`) and when `assignee !== actor` unless the caller supplies the exact recorded `resume {branch, worktree}` (`:483-501`). MCP client names are explicitly "not durable agent identities" (`:483`). Nothing distinguishes a live owner from a dead one; the refusal text is identical.
- **A `needs-changes` attestation is already a structured artefact.** `check-pr.mjs:51-88` validates `scratch/review.md` frontmatter (`kind: review-attestation`, `pr`, full `head_sha`, `verdict: pass|needs-changes`, `reviewer`, `independent`, `plan_hash`, `ticket_updated`, `findings[]`). Core has `gray-matter` available (`frontmatter.ts:1`) and `store.getDoc(id, "scratch/review")` reads it. Core cannot query GitHub, so the store can bind the return move to the attestation's `pr` ∈ `item.prs` and `verdict`, not to the live PR head; the live-head binding remains the reviewer's/CI's job (`merge-gate.ts:179-191`).
- **Audit is best-effort only.** `appendActivity` never throws and the log is gitignored/derived (`activity.ts:9-14, 34-56`); `op` is a closed union `create|update|delete|take|release|doc`. Committed history for a transfer or return therefore needs a second, committed record — a ticket document append is the only committed per-ticket surface (`setDoc` with `append: true`, `store.ts:1032-1070`).
- **Governing contracts.** FRD-030 requires that reclaiming an expired lease "preserves dirty work, records the old/new controller and never treats expiry as deletion", that "a live competing controller cannot acquire or renew the same workspace", that expiry durations are "explicit testable configuration" (initial thirty minutes), and that legacy `taken_at/branch/worktree` data receives "one migration path rather than a permanent parallel ownership model". FRD-034 AC3 requires that "an in-scope correction stays in the original ticket/PR and receives one delta review", and AC5 that budgets "stop repeated unchanged audits". HZN-008 context (updated 2026-08-27) forbids mutating reconciliation before these contracts exist and records the interim 30-minute rule this ticket formalises.
- **Existing test conventions.** Store behaviour is covered in `packages/core/src/store.test.ts` (`"takes and releases a ticket"` at `:685`, refusal/`stageEntered` cases at `:969-1006`); packet behaviour and `take_ticket` are exercised end-to-end in `packages/mcp-server/src/smoke.mjs` (`:538-562`, `:794-797`, occupancy at `:1915`, `:2024`). There is no `execution-packet.test.mjs`; smoke is the rail.
- No project-declared research source applies (`get_sources` → `declaredCount: 0`).

## Implications

- **Extend, do not add.** `take_ticket` gains `action: transfer | renew` (enum extension, tool count stays 37); `move_item` gains optional `reason`. No new MCP tool, no new stage, no board format change.
- **Claim fields (all optional, absent = legacy):** `claim_expires_at` (ISO), `claim_controller` (string; the durable controller-run identity, distinct from the MCP client name in `assignee`), `review_round` (int, default 0), `remediation_budget` (int, default 1). `take` and `renew` set `claim_expires_at = now + claimExpiryMinutes` (board.yml optional `claimExpiryMinutes`, default 30). Heartbeat, lease ids, batch membership and revision tokens stay with CORE-115/CORE-114.
- **Expiry semantics — one rule for new and legacy claims:** a claim is *expired* when `claim_expires_at < now`, or, when `claim_expires_at` is absent, when `taken_at + claimExpiryMinutes < now`. This is the FRD-030 "one migration path": legacy permanent claims become transferable after the window rather than living forever as a parallel model. Expiry never releases anything by itself.
- **`transfer`**: refused with `CLAIM_LIVE` unless the claim is expired or `reason` is supplied and starts with `operator:`; on success it replaces `assignee`/`claim_controller`, resets `claim_expires_at`, **keeps** `branch`/`worktree`/`taken_at`, and records `from`/`to` in activity plus an appended `## Transitions` entry in `scratch/execution.md`. `force` remains for the existing semantics and is unchanged.
- **`renew`**: owner-only (`assignee === actor` or `claim_controller` matches); extends `claim_expires_at`; refuses on a foreign live claim.
- **Backward move rule (store, not gates):** for tickets, when the target stage index is lower than the current, require a non-empty `reason`. For Review → Implementing specifically, additionally require either a valid `scratch/review.md` with `verdict: needs-changes` whose `pr` is in `item.prs`, or a `reason` starting with `operator:`; on success increment `review_round`, and refuse with `REMEDIATION_BUDGET_EXHAUSTED` when `review_round >= remediation_budget` unless the reason is an operator override (which also increments `remediation_budget`). Every backward move appends a `## Transitions` entry to `scratch/execution.md` and an activity row (`op: "update", field: "status"` with `reason`).
- **Packet:** keep the existing lane; change only the occupancy refusal to distinguish `expired` (name `take_ticket action: "transfer"` as the remedy) from `live`, and include a `claim` block (`state`, `expiresAt`, `controller`, `reviewRound`) in the ready packet so a resumed remediation knows its budget. A same-actor expired claim is allowed (the skill renews on resume).
- **Errors must be stable strings** for smoke/skills: `CLAIM_LIVE`, `CLAIM_NOT_OWNED`, `BACKWARD_MOVE_NEEDS_REASON`, `REVIEW_RETURN_NEEDS_ATTESTATION`, `REMEDIATION_BUDGET_EXHAUSTED` as message prefixes (the MCP layer already converts thrown errors to `isError` results).
- **Compatibility proof:** a store test must load a fixture with none of the new fields and show identical `take/release/move` behaviour, and a serialise/parse round-trip must keep the new keys in `KEY_ORDER` position.
