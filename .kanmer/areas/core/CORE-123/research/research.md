# Research — CORE-123 Merge-gate hardening and board-sync confirmation

## Question

How do the CI merge gate (`kanmer-gate`), the review attestation, the GUI board auto-sync and `get_status` need to change so that a `needs-changes`/missing attestation cannot pass CI, a stale remote board is reported as a structured `SYNC_REQUIRED`, the gate re-runs when `kanmer-board` is pushed, and board-sync drift is visible — all in one PR on the stable v0.3.12 line?

## Findings

### F1. Gate levels today (`packages/core/src/merge-gate.ts`)
- `NO_REVIEW_RECORD`, `STALE_REVIEW` (covers invalid attestation, head mismatch and `needs-changes`) and `COMMITS_UNREACHABLE` are hard-coded `level: "warning"` in `reviewChecks()`; only `NO_TICKET`, `OPEN_QUESTIONS`, `WRONG_STAGE`, `DEPENDENCY_BLOCKED` are errors. `mergeGateOk` blocks only on `error`. So a PR with a `needs-changes` attestation exits 0.
- `MergeGatePhase2Evidence` is the only input channel from the CLI (`check-pr.mjs`); core never spawns git (ADR-0011 §"kanmer-gate", ADR-0016). A strict switch and board evidence must therefore arrive as evidence fields, and ancestry must be computed in `check-pr.mjs`/`git-reachability.mjs`.
- `phase2NoTicket` and `skipped()` enumerate the fixed check list in order; adding a code (`SYNC_REQUIRED`) means extending `MergeGateFindingCode`, `skipped()` level mapping, and the two skipped lists so `checks[]` stays complete and ordered (test "returns every check in stable order").
- ADR-0011 and ADR-0016 both state that missing/stale attestations and unreachable commits are "compatibility-period warnings". Promoting them unconditionally would contradict the ADRs; the ticket's `KANMER_GATE_STRICT` flag keeps the default (warn) and lets the repo opt into errors for one release. The ADR text should get a one-line amendment noting the strict switch (verify:docs only checks structure, not this wording — confirmed by reading `scripts/verify-docs.mjs` usage in the rail list).

### F2. Attestation parsing is duplicated
- CORE-121 (origin/main dc514375) added `packages/core/src/review-attestation.ts` exporting `parseReviewAttestation(raw)` → `{state:"absent"|"invalid"|"valid",...}` with the same field rules as `parseReviewEvidence` in `packages/mcp-server/src/check-pr.mjs`; its header comment asks that the two be kept in step. The core version returns `headSha` lowercased and named fields (`pr, verdict, reviewer, independent, ticketUpdated, findings`) but not `plan_hash` or unknown extras.
- `check-pr.mjs` already imports from `../../core/dist/index.js`, so it can import `parseReviewAttestation` and drop its own validator. `check-pr.test.mjs` imports `parseReviewEvidence` from `check-pr.mjs`; keep that export as a thin wrapper (adds `details`) so the existing test still runs.
- `board_sha`, `threads_snapshot`, `expected_reviewers` are not mentioned anywhere in the repo yet (grep over docs/, plugins/, packages/) — the kanmer-review skill template (plugins/kanmer/skills/kanmer-review/SKILL.md §"whole-file review attestation") lists exactly the current fields. They are new optional fields: `board_sha` full 40-hex SHA of the board branch tip the reviewer read; `threads_snapshot` array (objects or strings; only shape-validated); `expected_reviewers` array of non-empty strings. Absence must remain valid (older attestations on the board), malformed presence is `invalid`.

### F3. Board SHA and staleness
- The workflow (`.github/workflows/pr.yml` job `kanmer-gate`) fetches `refs/heads/$KANMER_BOARD_BRANCH` into `$RUNNER_TEMP/kanmer-board` via `git worktree add`, so inside `--board` the tip is `git -C <board> rev-parse HEAD` and ancestry is `git -C <board> merge-base --is-ancestor <board_sha> HEAD` (exit 0 = ancestor, 1 = not, 128 = unknown object). `git-reachability.mjs` already wraps argv-safe `git` calls for `base..head`; a sibling helper `collectBoardEvidence({boardRoot, attestedSha})` fits there.
- Evidence shape proposed: `board: { sha: string|null, attestedSha?: string, state: "current"|"stale"|"unknown"|"unrecorded" }`. Gate outcome: `SYNC_REQUIRED` fails when `state === "stale"` (attested board SHA not an ancestor of the fetched tip: reviewer read a board that was never pushed, i.e. the PR #286/#287 failure) or `"unknown"` (attested SHA not present at all — same root cause); passes when `current`; passes-with-note when `unrecorded` (attestation predates the field). Level follows the strict switch. `MergeGateResult.boardSha` records the evaluated tip for the JSON verdict.
- The test fixture board in `check-pr.test.mjs` is a plain temp dir (not a git repo) — `collectBoardEvidence` must degrade to `{sha:null,state:"unrecorded"|"unknown"}` without throwing when the board is not a git checkout, and the test needs a second fixture that `git init`s the board to exercise stale/current.

### F4. Strict switch plumbing
- Actions repo variables reach steps only via `${{ vars.X }}` → env. `check-pr.mjs` should read `process.env.KANMER_GATE_STRICT` (`"1"|"true"` case-insensitive → strict) and pass `strict: boolean` in evidence; the workflow step sets `KANMER_GATE_STRICT: ${{ vars.KANMER_GATE_STRICT || '' }}`. Core decides levels from `evidence.strict` (default false = today's behaviour), keeping `merge-gate.test.ts` existing expectations intact and adding strict cases.

### F5. Workflow triggers (`.github/workflows/pr.yml`)
- Currently `on: pull_request` (opened/synchronize/reopened/ready_for_review/edited) only. Both jobs use `github.event.pull_request.*`, so a bare `push`/`workflow_dispatch` trigger would break them; they need `if: github.event_name == 'pull_request'`.
- Re-running the gate for open PRs after a board push cannot be done by evaluating in the push run (a check on the board-branch commit is not visible on the PR). The cheap route is a third job `regate` (`on: push: branches: [kanmer-board]` + `workflow_dispatch`) that uses `gh` with `permissions: actions: write, pull-requests: read` to list open PRs to `main` and `gh run rerun <run-id> --job <kanmer-gate job id>` for the latest run of this workflow at each PR head SHA (`gh run list --workflow pr.yml --commit <sha>` / `gh api repos/{owner}/{repo}/actions/runs/{id}/jobs`). This re-runs only the gate job (seconds), not the 10–14 min `verify`. Runs whose gate already passed still get re-run (harmless; result replaces). Cannot be executed locally — verification is "push kanmer-board, observe the PR check re-run".
- `KANMER_BOARD_BRANCH` var already parameterises the branch; the trigger list must use the literal default `kanmer-board` (YAML `on:` cannot read `vars`). Note this in a comment.
- Push-to-main evidence: adding `push: branches: [main]` to run `verify` costs a full rail per merge (~14 min runner). It gives every merge SHA a bound `verify` result that `kanmer-verify` can cite. Decision recorded in open-questions as parked: include it (one line) since cost is runner minutes only; gate job stays PR-only.

### F6. GUI `syncBoard` race (`apps/gui/src/main/kanmerGit.ts` L597–625)
- Sequence: `add -- .kanmer .gitignore` → conditional commit → `ls-remote` → `fetch` → `rebase origin/<branch>` → `push`. Any MCP write between `add` and `rebase` makes `git rebase` refuse with "cannot rebase: You have unstaged changes"; the catch returns `paused: true`, and `shouldRunAutomaticSync` (L116) requires `!paused`, so the timer never fires again until a human presses Retry. Confirmed against scratch/research.md and the CORE-121 review observation (remote 9a2e0648 stale ~1 h).
- `git rebase --autostash origin/<branch>` stashes the unstaged tracked change, rebases, then reapplies; a stash reapply conflict leaves the change in the stash and rebase reports it, which is a genuine conflict path. After rebase, a second `add`+`commit` picks up whatever the autostash restored (and any newer writes) so the push carries them; otherwise the next tick does.
- Transient vs conflict: a rebase failure with `CONFLICT`/`could not apply` (rebase left in progress — `rebase --abort` already runs) must keep `paused: true`. Anything else (unstaged-changes refusal, network errors on fetch/push, non-fast-forward push because someone pushed between fetch and push) should return `paused: false` with `error` set so the timer retries on the next tick. A pure `classifySyncFailure(message): "conflict" | "transient"` helper keeps this testable without git.
- Reproducing the race in `kanmerGit.test.ts` (real-git suite, `realGitTest` with a bare `origin` and `repo`): install a `post-commit` hook in the board worktree's git dir (`git rev-parse --git-path hooks`) that appends to a tracked `.kanmer` file, make origin ahead by one commit via a second clone, then `syncBoard` — today's code fails and pauses; with autostash it succeeds and `paused === false`. Windows Git ships `sh` for hooks, so the hook is portable enough for the existing `realGitTest` guard.

### F7. Ahead/behind visibility
- Neither `KanmerGitStatus` (apps/gui/src/shared/ipc.ts L364) nor the MCP `get_status.boardWorktree` block (packages/mcp-server/src/index.ts ~L484) carries ahead/behind. `git rev-list --left-right --count HEAD...refs/remotes/origin/<branch>` gives `ahead\tbehind` after a fetch; without fetching it reports against the last-fetched remote ref, which is what a "did my sync push?" indicator needs (ahead > 0 means unpushed board commits). Add `sync?: { remote: boolean; ahead: number; behind: number; localSha: string; remoteSha: string | null }` to `KanmerGitStatus` (computed in `ensureBoardWorktree`'s final status and after `syncBoard`) and render `ahead N / behind M` next to "last sync" in `Settings.tsx` L738. MCP: `boardSync: { remoteBranch, ahead, behind, localSha, remoteSha } | null` on `get_status`, computed with the same paired-git-inspector pattern the file already uses for the branch probe (core stays git-free). `smoke.mjs` asserts `boardWorktree` fields, so a new sibling key does not break it; add one assertion that `boardSync` is `null` or has integer counts.

### F8. Default sync interval
- `settings.ts` DEFAULTS `gitSyncMinutes: 0` and the parser coerces missing/invalid to 0 (off). There is no "unset" state, so "default to 5 when a remote exists" = treat an absent key as 5 while an explicit `0` stays off, and only arm the timer when the board worktree has an `origin` remote (`status.sync?.remote`). `armSyncTimer` in `apps/gui/src/main/index.ts` (L698, L949, L966, L1311) reads `readSettings().gitSyncMinutes`; the remote guard belongs in `shouldScheduleAutomaticSync` (kanmerGit.ts L121) by widening its status pick to include `sync`. Existing tests for `shouldScheduleAutomaticSync` pass a minimal status object, so `sync` must be optional and absent = allowed (non-git flows never reach the timer anyway because `available` is false).

### F9. Verification rail facts
- `npm run verify` = build → test → typecheck → verify:docs → smoke.mjs → smoke:headless → mcpb:check → smoke:protocol → smoke:discovery → verify:skills → verify:agents-block → plugin:check. `check-pr.test.mjs` runs under `test:http -w @kanmer/mcp-server` and spawns the CLI against `core/dist`, so core must be built before it. `plugin:check` compares `plugins/kanmer/mcp/kanmer-mcp.cjs` with the built server — any mcp-server change requires rebuilding the bundle (`npm run build`) or plugin:check fails.
- Known host-only failures to record, not chase: `scripts/antigravity-plugin-config.test.mjs` (2 tests, EBUSY/cmd.exe) and `kanmerGit.test.ts` "serializes concurrent orphan cleanup".

## Implications for this ticket

1. One PR, five surfaces: core merge-gate (+ tests), core review-attestation extension (+ tests), check-pr.mjs + git-reachability.mjs (+ fixtures), pr.yml, GUI kanmerGit/settings/index/ipc/Settings.tsx (+ tests), mcp-server get_status (+ smoke assertion), skill template + ADR wording. It is still one coherent unit ("gate and board agree"); no split needed unless execute finds the regate job needs a separate workflow file.
2. Default behaviour must not change for existing repos without `KANMER_GATE_STRICT`: warnings stay warnings, `SYNC_REQUIRED` is a warning, older attestations without `board_sha` pass with a note.
3. The reviewer skill must start writing `board_sha` (and the MCP tool-reference should mention it) or `SYNC_REQUIRED` never fires; the review skill is under `plugins/kanmer/skills/kanmer-review/SKILL.md` and `verify:skills` checks prose — keep the template edit minimal.
4. The regate job and push-to-main run cannot be proven locally; they are verified by the ticket's own PR (the first board push after opening the PR should re-run `kanmer-gate` on it).
