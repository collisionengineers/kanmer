## What

Give the MCP server a board-discovery step, so it can find the board when it was
started without `--root`.

## Why

`resolveProjectRoot` (`packages/mcp-server/src/root.ts:16`) ends at
`process.cwd()`, and `resolvePaths` then looks for `<cwd>/.kanmer`. **A board
created by the desktop app is not there** — it is at `.worktrees/kanmer/.kanmer`,
and `deriveRepoRoot` (`packages/core/src/paths.ts:32`) only maps board → repo,
never repo → board. This repo has no `<repo>/.kanmer` at all.

So any registration that does not carry an absolute `--root` reports "no board"
on the layout the product itself creates. That is every path into Kanmer except
the desktop app's Connect button — including both plugin manifests
([[MCP-011]]), a `.mcpb` install ([[MCP-008]] already notes "a desktop install
has no project context to infer from"), and any hand-registration.

`root.ts:9` calls the cwd fallback "the common case". It is the broken case.

There is a second reason discovery beats absolute paths: they do not survive a
different machine or user account. `pegasus/.mcp.json` on this machine hardcodes
`C:\Users\Alex\...` under a `C:\Users\PC` profile and is inert.

## Approach

After the existing `--root` → `KANMER_ROOT` steps, search:

1. `<cwd>/.kanmer`
2. `<cwd>/.worktrees/*/.kanmer` — the layout `ensureBoardWorktree` creates
3. ancestors of cwd, applying 1 then 2 at each level

Found nothing → **throw, naming every path tried** and how to set `--root`. A
silent "no board" is what makes this invisible today.

Return the discovered root *and how it was found*, so [[MCP-012]] can surface it.

Stop the ancestor walk at a filesystem root or a `.git` boundary — a deep
subdirectory must not latch onto an unrelated parent board.

Keep the resolver pure over an injected `existsSync`, matching the
testable-by-injection style already used in `packages/core/src/io.ts`.

## Governing docs

Discovery order is a cross-cutting decision and needs its own **ADR** — hence
`docs_todo`. Refs FRD-022.

## Outcome

Shipped in **PR #40**, squash-merged as `741ef81` on 2026-08-16.
<https://github.com/collisionengineers/kanmer/pull/40>

Verified on merged `main`: the plugin-manifest invocation (no `--root`, cwd at
the repo root) went from `exists: false` / `boardSource: "default"` / **0
tickets** to `exists: true` / `boardSource: "file"` / **148 tickets**, with
`rootSource: "cwd-worktree"`. Before and after are both in
`scratch/falsification.md`; the full evidence is in `proof`.

**Shipped differently than the ticket described, in three places — each recorded
rather than quietly absorbed:**

1. **The `.git` boundary is a `.git` DIRECTORY only; a `.git` FILE is
   traversed.** The Approach above says "a `.git` boundary" without the
   distinction. That wording is *wrong*: a git linked worktree's `.git` is a
   66-byte `gitdir:` file, and `kanmer-execute` puts every implementing agent
   inside one, so the rule as written would have broken discovery for the
   dominant real case. ADR-0012 carries a **"Corrected premise"** section saying
   so explicitly.
2. **Not-found is fatal, plus an explicit `--init` opt-in** (operator's call).
   The ticket said only "throw". `--init` / `KANMER_INIT=1` is what keeps
   bootstrapping a board-less repo possible, and `kanmer-setup` was updated in
   this ticket to use it — a fatal resolver with a setup flow assuming lazy
   creation would have been a broken product.
3. **Two injected seams became three.** `existsSync` cannot enumerate
   `.worktrees/*` (so `readdirSync`) and cannot tell a file from a directory (so
   `isDirectory`) — and that second distinction is the entire boundary rule.

Also: `how` gained a seventh value, **`init`**, for "nothing found, `--init`
permitted a board at cwd". The six values MCP-012 was promised are unchanged.

**Governing docs:** **ADR-0012** (new, `docs/architecture/adr/`) fixes the
resolution order, the boundary rule and the provenance vocabulary.
**FRD-022** amended — it is `approved` and asserted the retired three-step order
as verified fact.

**Follow-ups:** [[MCP-011]] is unblocked and should land next (point the
manifests at the resolver that now works). [[MCP-012]] consumes `rootSource` and
must report `init` alongside the other six. [[MCP-008]]'s `.mcpb` case gains only
the better error message, as expected. [[MCP-007]] gained a second data point:
the committed bundle again had to be built with care over worktree module
resolution, and the guard is still procedural.
