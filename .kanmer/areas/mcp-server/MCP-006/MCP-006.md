## What

Expose `update_group(id, { title?, body?, archived? })` over MCP, so an agent can
rename, re-body and **archive** a group.

## Why

The group tool surface is read-mostly: `create_group`, `get_group`,
`list_groups`, `get_group_doc`, `set_group_doc`. There is no update. FRD-001 G5
specifies exactly that set, so this is a gap in the spec as much as the code.

It contradicts the rest of the design:

- **G4 says "Deleting = archiving"** — so archiving is the only way to retire a
  group, and an agent cannot do it. There is no delete either, which means an
  agent cannot retire a group at all.
- **`list_groups`' own tool description** tells the reader "archiving is how a
  group is retired", describing an operation the surface does not offer.
- **`set_group_doc`'s description** says the group's own `<ID>.md` must be
  edited "through create_group's body" — but `create_group` allocates a new id
  and cannot edit anything. The advice is impossible to follow.

The capability already exists everywhere else: `KanmerStore.updateGroup`
(`packages/core/src/store.ts:1285-1297`) writes the file, stamps `updated`, and
appends an activity entry; the GUI wires it through `CH.updateGroup`
(`apps/gui/src/main/index.ts:762`) and `GroupView.tsx:75` uses it to archive.
Only MCP is missing.

Found in use: renaming [[HZN-003]] from "0.3.4" to "0.3.3" had no tool path and
had to go through core directly, outside the tool layer that exists precisely to
keep ids, timestamps and frontmatter consistent.

## Approach

- Add the tool to `packages/mcp-server/src/index.ts` alongside the other group
  tools, delegating to the existing `store.updateGroup` — no new core logic.
- Match `update_item`'s conventions: only provided fields change, and a patch
  that changes nothing does not bump `updated` (core already does this).
- Consider `expected_updated` for optimistic concurrency, as `update_item` has.
- Fix the two misleading descriptions above once the tool exists.
- Update FRD-001 G5 (it enumerates the surface) and the tool reference
  (FRD-023 R5 makes that mandatory for any surface change).

## Verification

- [x] An agent can rename a group and the change is visible in `get_group` and
      on the board.
- [x] An agent can archive a group; it drops out of `list_groups` unless
      `include_archived`, and member tickets are untouched (FRD-001 G4).
- [x] A no-op patch does not bump `updated`.
- [x] `list_groups` and `set_group_doc` descriptions no longer describe
      operations that cannot be performed.
- [x] Tool reference and FRD-001 G5 updated; `plugin:build` + `plugin:check`
      pass with the regenerated bundle committed.

## Outcome

Shipped in PR [#58](https://github.com/collisionengineers/kanmer/pull/58),
squash-merged as `ac01b8b`. The MCP surface is now **30 tools** — recounted from
the code, not incremented: it was 29, not the 24 the docs claimed.

**Final shape:** `update_group(id, title?, body?, archived?, expected_updated?)`,
annotations `readOnlyHint:false / destructiveHint:false / idempotentHint:true`.
`kind` is deliberately not patchable — `createGroup` allocates the id from the
kind's prefix, so `EPIC-`/`HZN-` encodes it permanently.

**It was not zero-core after the Approach's estimate.** `store.updateGroup` did
need `expectedUpdated`, and adding it surfaced three ways the existing
`{...current, ...patch}` could corrupt a group file: the concurrency token being
persisted into frontmatter via the passthrough schema, a stale token silently
succeeding whenever the patch was a no-op, and an explicit `title: undefined`
erasing `title:` because `serialiseGroup` skips undefined values. All three are
now guarded in `updateItem`'s order, and `updateGroup` — which had **zero**
tests — has nine.

**MCP-only, as scoped.** The GUI typechecks untouched: the new core field is
optional, so `kanmer:updateGroup`'s existing end-to-end path stays assignable.

**Docs corrected beyond the one line.** AGENTS.md §5 said 24 tools and omitted
all five existing group tools; FRD-022's Phase-0.2 audit note was stale in three
separate ways (the count, "group tools absent", and "column tools still accept
`status|area|priority`" — `columnKindEnum` has been `z.literal("area")` for some
time). Both were recounted from the code rather than patched.

**Follow-ups, none filed as blocking:**
- Three items stay parked in `open-questions`: the GUI still renders a group's
  title and body read-only, so an *agent* can now rename a group but a *human*
  still cannot; `plugin:check` verifies tool *names* but not *descriptions*,
  which is how the two misleading descriptions survived; `updateGroup` logs one
  `field: "group"` activity entry rather than per-field ones.
- FRD-022's R2 Phase-0.2 bullet still carries stale line references
  (`index.ts:744`/`:800`, actually `:976`/`:1025`). The claim is still true;
  worth a sweep of that note as a whole.
