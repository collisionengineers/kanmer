## Ripple effects

- **Release rail** — `scripts/release.mjs` GATE runs `npm run plugin:check` from `root`. A root-derived guard is a no-op there. This must be re-proved by running the release dry-run, not assumed.
- **`kanmer-execute` skill** (`plugins/kanmer/skills/kanmer-execute/SKILL.md` lines 34-54) tells every implementing agent to `cd .worktrees/<id>` and work there. The moment the guard exists, any ticket touching the MCP server hits it from inside that skill's prescribed workflow. Whether the skill needs a paragraph about it depends entirely on Q1's answer — do not edit the skill until Q1 is settled, or the instruction will be wrong.
- **Committed build artifact** — `plugins/kanmer/mcp/kanmer-mcp.cjs` must **not** be rebuilt as part of this ticket. This ticket changes no server or core source, so the bundle's correct state is byte-identical to what is committed. A diff on that file in the PR means something went wrong.
- **AGENTS block** — `npm run verify:agents-block` is in the release GATE; any AGENTS.md edit must leave it passing.
- **No tests to update.** There is no test file covering `scripts/`, no `scripts/lib/`, and no `.github/workflows` in this repo — nothing runs these scripts automatically. Verification for this ticket is a hand-run command log in both roots (proof type `command-log`), and the plan should say so explicitly rather than leaving an implementer hunting for a suite to extend.
- **Human-facing docs** — `docs/manual/troubleshooting.md` mentions worktrees; check whether a contributor-facing note is warranted, or whether this is purely a repo-maintainer concern that belongs only in AGENTS.md. Leaning: AGENTS.md only, since `plugin:build` is not an end-user command.

## Out of scope

- **Guarding `npm run build` generally.** That is `tsup` across workspaces and is a legitimate thing to run in a worktree (GUI dev loop, typecheck). Its output is gitignored, so a wrong build there harms nothing until `build-plugin.mjs` copies it. Guard the artifact-producing step, not the compiler.
- **Making worktrees build correctly** (auto-`npm install`, per-worktree `node_modules`, hoisting changes, pnpm-style linking). That is a different and much larger ticket; this one only has to stop a false pass. If Q1 pushes that way, split it out.
- **Asserting bundle provenance from its contents** — e.g. checking the embedded `../../node_modules` comment depth, or stamping a build-root marker into the artifact. Corroborating at best, tsup-formatting-dependent, and a separate design question from "where am I running".
- **Reproducibility of tsup output.** The existing header flags this as an assumption; it stays an assumption. This ticket does not make the byte comparison more robust, only more honest about when it means anything.
- **Retro-checking already-merged bundles.** PR #32 fixed the SKILL-011 instance. This ticket is prevention only.
