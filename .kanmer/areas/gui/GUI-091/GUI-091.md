## What

Three independent capture routes were tried against the running Kanmer window
during [[GUI-065]] and all three failed:

- **CDP `Page.captureScreenshot`** — hangs.
- **CDP `Page.startScreencast`** — one stale frame, then zero. A red-background
  diagnostic deliberately injected into the page never appeared in any frame.
- **GDI `PrintWindow`** — returned the initial paint, then a blank client area
  after a forced `MoveWindow` + `RedrawWindow`.

The renderer was provably alive throughout: CDP `Runtime.evaluate` returned live
DOM and layout rects the whole time. So this is a *capture* failure, not a
rendering or automation failure.

## Why it matters

The board's `proof:visual` policy — agent-rendered evidence counts, provided the
image is actually reviewed with vision — has worked well this release. But it has
been carried by two different techniques, and only one of them is affected:

- **Headless Chromium over the real stylesheet** works, and is what [[GUI-072]]
  used. Fine for anything that is purely CSS.
- **Photographing the actual Electron app** does not work on this host. GUI-065
  was the first ticket to need it and had to fall back to DOM + layout rects from
  the live app, plus pixels from headless Chromium over the same built bundle with
  `window.kanmer` stubbed. It named that boundary honestly in `proof.md` rather
  than blurring the two.

That fallback is sound but it is not free: it cannot show chrome, native dialogs,
window-level layout, or anything drawn outside the renderer.

**[[GUI-068]] is the case that makes this urgent.** It requires a screenshot of the
updater's *refusal dialog* — and that is exactly the class of thing the working
fallback cannot produce. GUI-068 is already parked pending a real release cut and a
human, so this is not currently blocking it; but if this were solved, GUI-068's
visual half would stop needing a person.

## Approach

- Establish *why* capture fails. Candidates worth eliminating in order: GPU/ANGLE
  compositing path (try `--disable-gpu`, `--disable-gpu-compositing`, software
  rasterisation), the window being off-screen or minimised, Windows capture
  protection, and the CDP target being attached to the wrong page vs browser
  endpoint.
- Try `webContents.capturePage()` from the **main** process, which is Electron's
  own API and does not go through CDP or GDI at all. This is the most likely fix
  and was not among the three routes tried.
- If a route works, write it down somewhere an agent will find it — AGENTS.md §8 or
  the `kanmer-verify` skill — because the next agent will otherwise repeat all
  three failures.
- If **no** route works, say so plainly and record it as a standing limitation, so
  future tickets scope their proof accordingly instead of discovering it late.

## Verification

- [ ] A screenshot of the running Kanmer window, produced by an agent, showing
      content that is provably current (e.g. a value written into the DOM
      immediately before capture).
- [ ] The working method recorded where an agent will find it — or the failure
      recorded as a standing limitation with what was ruled out.
