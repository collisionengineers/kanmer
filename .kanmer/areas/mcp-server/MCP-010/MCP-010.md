## What

Give the MCP server a board-discovery step, so it can find the board when it was
started without `--root`.

## Why

`resolveProjectRoot` (`packages/mcp-server/src/root.ts:16`) ends at
`process.cwd()`, and `resolvePaths` then looks for `<cwd>/.kanmer`. **A board
created by the desktop app is not there** — it is at `.worktrees/kanmer/.kanmer`,
and `deriveRepoRoot` (`packages/core/src/paths.ts:32`) only maps board → repo,
never repo → board. This repo has no `<repo>/.kanmer` at all.

So any registration that does not carry an absolute `--root` reports "no board"
on the layout the product itself creates. That is every path into Kanmer except
the desktop app's Connect button — including both plugin manifests
([[MCP-011]]), a `.mcpb` install ([[MCP-008]] already notes "a desktop install
has no project context to infer from"), and any hand-registration.

`root.ts:9` calls the cwd fallback "the common case". It is the broken case.

There is a second reason discovery beats absolute paths: they do not survive a
different machine or user account. `pegasus/.mcp.json` on this machine hardcodes
`C:\Users\Alex\...` under a `C:\Users\PC` profile and is inert.

## Approach

After the existing `--root` → `KANMER_ROOT` steps, search:

1. `<cwd>/.kanmer`
2. `<cwd>/.worktrees/*/.kanmer` — the layout `ensureBoardWorktree` creates
3. ancestors of cwd, applying 1 then 2 at each level

Found nothing → **throw, naming every path tried** and how to set `--root`. A
silent "no board" is what makes this invisible today.

Return the discovered root *and how it was found*, so [[MCP-012]] can surface it.

Stop the ancestor walk at a filesystem root or a `.git` boundary — a deep
subdirectory must not latch onto an unrelated parent board.

Keep the resolver pure over an injected `existsSync`, matching the
testable-by-injection style already used in `packages/core/src/io.ts`.

## Governing docs

Discovery order is a cross-cutting decision and needs its own **ADR** — hence
`docs_todo`. Refs FRD-022.
