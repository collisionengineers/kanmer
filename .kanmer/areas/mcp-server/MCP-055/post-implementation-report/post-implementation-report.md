# Post-implementation report — MCP-055

## Summary

`ok()` in `packages/mcp-server/src/index.ts` now returns
`structuredContent: { result: data, ...(lastProject ? { project: lastProject } : {}) }` instead of
`structuredContent: { project: lastProject }`. Every successful tool result therefore carries the
whole payload in the field that structured-content-preferring clients render, while
`structuredContent.project` keeps its exact previous shape and location. Error results are
untouched.

- Branch: `MCP-055-structured-content-result`
- Worktree: `.worktrees/mcp-055`
- Base branch: `main`; `delivery.baseSha` = `7e114cd117ef720c20797e2bf9f5cf58643a94e6` (`baseShaState: resolved`, v0.4.0)
- Implementation commit: `e9ff3a5366a2a024df25223fc526c8058e242d14`

## Files changed and why

| File | Change |
|---|---|
| `packages/mcp-server/src/index.ts` | The `ok()` result builder only (plus its doc comment). The payload is **nested** under `result`, not spread, because `get_status` (`:759`) and `get_execution_packet` (`:1173`) already build their own richer `project` field inside the payload; a top-level spread would silently overwrite it and make `content[0].text` disagree with `structuredContent` at exactly the fields the smokes assert. Nesting also handles arrays and scalars through the same single branch. No other line in the file changed. |
| `packages/mcp-server/src/smoke.mjs` | Added a `mirrorsText(res)` helper beside `textOf`, one check that `structuredContent.result` deep-equals the parsed text block for a read (`get_item`), a write (`update_item`) and `get_status`, and one check that the existing `WRONG_PROJECT` error result's `structuredContent` carries `error` and no `result`. |
| `packages/mcp-server/src/smoke-protocol.mjs` | Added the same `get_status` mirror check immediately after the existing `statusPayload` compatibility check, inside the existing loop. |
| `packages/mcp-server/src/http.test.mjs` | Added `assert.deepEqual(status.structuredContent.result, statusPayload)` immediately after the existing `statusPayload` parse; the two assertions after it are unchanged. |
| `plugins/kanmer/skills/kanmer-tickets/references/tool-reference.md` | Extended the result-shape sentence in "Write tools" to state that a successful call's `structuredContent.result` mirrors `content[0].text`, and that an error result carries `error` there instead and no `result`. No other sentence changed. |
| `plugins/kanmer/mcp/kanmer-mcp.cjs` | Regenerated by `npm run plugin:build`. Not hand-edited. |

## Deviations

1. **Plan Step 4's live in-host Claude Code observation was not performed; it is deferred.** An MCP
   server is bound at session start, so a running session cannot observe a bundle rebuilt inside
   it, and this work ran in a subagent session. On explicit controller instruction the substitute
   evidence is the raw JSON-RPC transcript above, and **the in-host Claude Code rendering check is
   deferred to verification/promotion (CORE-137 acceptance)**. The corresponding checklist item is
   ticked with that note verbatim rather than claiming the in-host observation happened. This is
   the one place where the plan's stop condition ("the live Claude Code observation is recorded")
   was satisfied by an equivalent rather than literally.
2. **`smoke-protocol.mjs`'s loop iterates protocol versions, not transports.** The plan said "both
   transports (stdio/http — whichever the loop already iterates as `proto`)"; the actual
   `PROTOCOLS` constant is `["2025-11-25","2025-06-18","2025-03-26","2024-11-05"]`, so the new
   check runs four times over stdio. The HTTP transport is covered by the new `http.test.mjs`
   assertion against the official HTTP client, so both transports are covered — just in the file
   that actually exercises each one.
3. **`npm install` was required** in the fresh worktree before any command could run. No
   dependency was added, changed or upgraded; `package-lock.json` is unmodified.
4. The packet carried three **advisory** plan-validation findings (`PLAN_PATH_INVALID` on
   `index.ts:210-214`, `PLAN_STEP_FILE_FORBIDDEN` / `PLAN_STEP_FILE_UNDECLARED`). They are
   artefacts of the plan's prose using line-qualified paths and a "none (verification only)" step;
   `validation.ok` is `true` with 0 blockers. No plan document was rewritten.

## Risks and follow-ups

- **Response size**: the payload now travels twice (in `content[0].text` and in
  `structuredContent.result`), roughly doubling successful-response bytes. Accepted in the plan as
  residual risk and consistent with the MCP spec's guidance that structured results SHOULD be
  mirrored in a text block. `get_status` measured 3580 text bytes.
- **`structuredContent` is now always present on success**, even before a project identity is
  resolved (previously omitted when `lastProject` was null). Intended per plan; no assertion
  depended on its absence, but it is the one externally visible shape change beyond the new field.
- **The installed launcher is still v0.4.0.** The board tooling this session used a shim because
  the running control plane predates this fix; the fix only reaches the operator's Claude Code
  session after this lands and a 0.4.1 build is installed and promoted.
- No `outputSchema` was declared, so the SDK still skips `validateToolOutput` for all 41 tools. If
  `outputSchema` is ever added, `structuredContent`'s new shape becomes a validated contract —
  worth a deliberate decision then, out of scope here.
