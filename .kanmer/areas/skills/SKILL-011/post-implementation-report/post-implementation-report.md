# Post-implementation report — SKILL-011

## Summary

`list_items` now filters by `group`, and `kanmer-auto` scopes a roster from an
epic or horizon rather than only an area. The core change is three lines; the
value is in *where* it sits. Resolving group membership in the tool rather than
in skill prose is what makes the roster usable: `get_group`'s derived members
carry only `id/title/status/archived`, so a skill scoping through it could not
apply its own documented drop rules (`taken`, `blocked`) or partition by
`profile` without one `get_item` per ticket. Measured on the real board, the
filter returns fifteen summaries carrying `profile` and `taken`; `get_group`
supplies neither. Membership stays derived — the filter is a predicate over
`item.groups` and no group file is read.

## Governing docs

**FRD-001 (Groups) — meets.** G3 holds literally: the filter reads
`item.groups` and never opens a group file, so member lists stay derived on
every read. G8/AC4 required a group filter to narrow every view; the GUI half
existed and this is its MCP counterpart. **G5 is deliberately not amended** — it
enumerates the *group* tools, and this adds a parameter to an item tool; the
missing `update_group` it does concern is [[MCP-006]].

**FRD-023 (Agent skills) — meets.** R1 (derive, don't restate) is the whole
argument for the placement: §1 gained a parameter to call, not a rule to follow.
R2 is met by not regressing — profile-aware partitioning needs `profile` on the
roster, which is precisely what the filter supplies and `get_group` does not. R5
is met by the tool reference, `plugin:build` and `plugin:check`.

**No new ADR.** An optional filter parameter matching the shape of `label` is
not a design decision.

## Risks / follow-ups

- **[[GUI-067]] is understated and should be corrected before it is worked.**
  The plan called for `npm run typecheck` at the root. There is no such script —
  the root defines build/test/smoke/plugin/release and no typecheck at all. The
  ticket reads "make the root typecheck cover every workspace"; there is nothing
  to extend, only something to create. `typecheck -w @kanmer/gui` exists and was
  run clean.
- **The `blocked` drop rule is documented but not queryable.** `blocked` is
  derived on summaries, not a filter, so `kanmer-auto` drops those tickets after
  the call — as it already does for `taken`. No change made; flagged because §1
  could be misread as implying a filter.
- **Multi-group (OR) filtering is deliberately absent.** AND composition comes
  free and covers the real case; an OR filter would be the only one on the
  surface. Recorded in open-questions as a default taken, not a question dodged.
- **`kanmer-report` and `kanmer-groom` do not yet use the filter.** It is
  generic and they can adopt it when they need it.
- **Sequencing:** [[SKILL-012]] edits the same `kanmer-auto/SKILL.md` and must
  rebase on `origin/main` after this merges.

## Verification hand-off

On merged `main`:

- `npm test` — expect 201 passing (21 files), including the five new
  `filtering by group` tests.
- `npm run smoke:protocol` — 26/26; it exercises the tool surface over real
  stdio, so it is what proves the new parameter is actually reachable.
- `npm run plugin:check` — 29 tools match, bundle bytes match. This is the one
  that catches a stale committed bundle.
- `npm run verify:agents-block` — 26/26.
- `npm run typecheck -w @kanmer/gui` — clean. (No root equivalent exists; see
  follow-ups.)
- **The functional check that matters:** `list_items` with `group: "HZN-003"`
  returns the group's members with `profile` and `taken` populated, and
  `get_group("HZN-003")` returns members with neither. That contrast is the
  evidence for the design, not just for the code, and it should be re-run on
  merged main rather than trusted from here.
