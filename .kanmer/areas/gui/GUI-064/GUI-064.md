## What

Updating an installed Kanmer to 0.3.1 fails at the uninstall-old-files step. The
NSIS installer aborts with a modal:

> **Kanmer Setup** — Failed to uninstall old application files. Please try running the installer again.: 2

The update does not apply. Make the update survive this, or fail in a way the
user can act on.

## Why

This is the auto-update path's last mile: everything upstream of it works
(detect, download, `quitAndInstall`) and the user still does not get the new
version. `: 2` is the old uninstaller's exit code, surfaced by electron-builder's
`msg_uninstall_failed`. A nonzero code there almost always means the uninstaller
could not delete files that something still holds open.

Leading hypothesis, and the repo already documents the mechanism —
`apps/gui/src/main/mcp-sessions.ts:7-20`: `connect.ts` registers the agent's MCP
server `command` as `process.execPath`, so **an agent's MCP server IS the
installed `Kanmer.exe`, running from `$INSTDIR`**. The app can already *detect*
those sessions (`mcpSessions()`, used to warn before restart) but nothing kills
them, and a surviving one holds handles under
`%LOCALAPPDATA%\Programs\Kanmer\resources\` exactly where the uninstaller needs
to delete. Same family of Windows handle contention as [[CORE-022]].

Other candidates to rule out, not assume: a stale `Uninstall Kanmer.exe`
registry entry from a prior install, antivirus holding the bundle, and
`perMachine: false` + `allowToChangeInstallationDirectory: true`
(`electron-builder.yml:40-43`) leaving two install roots.

## Approach

- Reproduce with an install log — `Kanmer-Setup-x.y.z.exe /NCRC` and the NSIS
  log, plus `%LOCALAPPDATA%\kanmer-updater\` — before choosing a fix.
- Identify what actually held the handle at failure time (Process Explorer /
  `handle.exe` against `$INSTDIR`).
- Decide the fix on evidence: close/kill our own MCP sessions before
  `quitAndInstall`, or block the install with an actionable message naming the
  processes, rather than the current opaque `: 2`.
- Whatever lands, the failure message must name what to do, not "try again".

## Verification

- [x] Update from a released build with an agent MCP session live against the
      installed app — the update completes, or is refused with a message naming
      the blocking session.
- [x] Update with no sessions live — completes unchanged.
- [x] `dist:check` / boot smoke on the packaged build.

## Outcome

**Shipped in v0.3.2.** PR [#29](https://github.com/collisionengineers/kanmer/pull/29),
merged `e293df0` on 2026-08-16, plus `c8b94a4`. The user's stuck 0.3.0 install
was taken to 0.3.2 as part of verification: installer exit code 0 after three
prior failures.

**The hypothesis above was right about the culprit and wrong about the
mechanism**, which is worth preserving. `Kanmer.exe` and every DLL rename fine —
Windows permits renaming a mapped image — so "the MCP server holds Kanmer.exe"
explains nothing. Measured, the blockers are `icudtl.dat` and
`v8_context_snapshot.bin`, which V8 and ICU memory-map *without*
`FILE_SHARE_DELETE`. One `ELECTRON_RUN_AS_NODE` process is enough:
`0 blocked → 2 blocked → 0 blocked` across its lifetime. And `: 2` is not a
generic failure — it is the uninstaller's `un.atomicRMDir` aborting on the first
file it could not rename.

Two of the three "other candidates" were never reached: the registry-entry and
two-install-roots theories were unnecessary once the lock was measured.

**Shipped differently than planned:** the `restartWarning` wording change (plan
step 7) turned out to be unneeded — the sentence never named who closes the
sessions, so it stayed true. And two bugs in the first cut were caught before
commit: delivering the refusal via `phase: "error"` would have been invisible on
auto checks and would have wiped the `downloaded` phase, stranding the update.

**Not proven:** the automatic path end-to-end (the fix runs in the version doing
the updating, and this machine was on 0.3.0 — needs 0.3.2 → 0.3.3), and the
refusal dialog on screen. Both recorded in proof.md.

**Follow-ups worth filing, not yet raised as tickets:**

- **Move the MCP server out of `$INSTDIR`** (AGENTS.md §11 already names it).
  Ends this failure *and* the "every update kills your agents" behaviour instead
  of managing them. Needs its own ADR. Awaiting the user's call.
- **Releases keep uploading incompletely.** Three in a row: 0.3.0 lost its
  blockmap, 0.3.1 lost the exe and manifest, 0.3.2 lost `latest.yml` — each time
  electron-builder logged success. `release.mjs`'s final check is the only
  reason none of them shipped broken; it should also assert the installer asset,
  not just the manifest.
- **`npm run typecheck` at the root does not reach the GUI workspace**, which is
  how `c8b94a4`'s error survived a green rail.
