## Ripple effects

- **Callers:** none. `store.updateGroup` gains an *optional* parameter field, so the
  GUI main-process call site (`apps/gui/src/main/index.ts:764`) and the untracked
  `packages/ui/src/demo.tsx:713-721` mock stay structurally compatible.
- **Tests:** `store.test.ts` (new group tests), `smoke.mjs` (count + names +
  scenario), `smoke-protocol.mjs` (count). No GUI test touches groups beyond
  `readOnly.test.ts:14`, which already lists `updateGroup` and needs no change.
- **Build artifacts:** `plugins/kanmer/mcp/kanmer-mcp.cjs` must be rebuilt and
  committed. `apps/gui/src/renderer/src/manual/chapters.generated.ts` is **not**
  affected (verified). The `.claude/skills/…` and
  `apps/gui/release/win-unpacked/…` copies of the tool reference are an untracked
  local install and a packaging artifact respectively — do not hand-edit either.
- **Docs:** FRD-001 G5, FRD-022 R1 + Phase-0.2 count, AGENTS.md §5, tool reference.
- **Agent-visible behaviour:** two tool descriptions change meaning
  (`list_groups`, `set_group_doc`), which is a contract-layer change under ADR-0009
  — nothing mechanically verifies descriptions, so review has to.
- **Verification burden:** AGENTS.md §10 steps 1, 2, 3, 6 all apply (server changed).
  Step 5/9 (GUI/packaging) do not.

## Out of scope

- **`kind` as a patchable field** — the id prefix is allocated from it (research F7).
  Excluded deliberately; the description should say so, as `update_item` does for `type`.
- **A `delete_group` tool** — FRD-001 G4 makes archiving the retirement path; a real
  delete would orphan the `groups: []` entries recorded on member tickets.
- **Editing a group's title/body in the GUI** — `GroupView` renders them read-only.
  A genuine gap, but a GUI ticket, not this one (see open-questions Parked).
- **Membership add/remove tools** — membership lives on tickets via
  `update_item(groups: [...])` by design (`index.ts:401-404`, FRD-001 G3).
- **Per-field activity entries for groups** — `updateGroup` logs one `update` entry
  with `field: "group"` where `updateItem` logs one per changed field. Consistent
  with today's behaviour; changing it is not required here.
- **Making `plugin:check` verify tool *descriptions*** — the real reason the two
  misleading descriptions survived (FRD-022 Phase-0.2 note `:37-39`). Worth its own
  ticket; not this one.
