# Open questions — CORE-131

*These block the ticket at three real gates; scratch is a notepad and is never
gated. One question per checkbox, answer recorded on the same bullet.*

The five questions the preparation brief required to be resolved are answered
below and in full in `plan/plan.md`. Trivial defaults taken by the planner are
marked **(default taken)**.

- [x] **Where does the apply/collect seam sit, and how is the recommendation bound to the revision it came from?** — Resolved. The **MCP boundary** (`packages/mcp-server/src/reconciliation.ts`) re-collects by calling the *same* `reconcileTicket` the dry run used, so re-collection cannot drift from what was reported. The collector stamps the ticket's document-inclusive `revision` (`store.getRevision`) into the recommendation, so the recommendation carries its own binding; core's pure classifier is unchanged in this respect and still git-free. Apply compares the caller's `expected_revision` to the freshly-collected revision *and* to the freshly-classified action, then delegates to `store.applyReconciliation`, which passes `expectedRevision` down to `moveItem`/`releaseTicket`/`transferTicket` so the final CAS happens inside the board write lock. Collection stays outside the lock because AGENTS.md §8 item 17 forbids networked work inside it.
- [x] **What is the exhaustive action set?** — Resolved. Six actions, all composed from existing verbs: `MOVE_TO_VERIFYING`, `MOVE_TO_IMPLEMENTING`, `MOVE_TO_DONE`, `ROUTE_VERIFICATION_FAILURE` (typed, target from `failure_class`), `RELEASE_CLEAN_TERMINAL_CLAIM`, `RECOVER_EXPIRED_CLAIM` (CORE-115 `transferTicket`). No new stage, no force-push, no required-check bypass, no worktree/branch deletion, no workspace cleaning, no `force` on any lease verb, and `.worktrees/kanmer` is refused in every path (twice — at collection and in the classifier's first refusal). Enumerated with their preconditions in `plan/plan.md` §2.
- [x] **How does typed verification routing work, and what happens for `inconclusive`?** — Resolved. `proofEvidence` learns `failure_class`; the classifier routes a FAIL/INCONCLUSIVE proof in Verifying by `kanmer-verify/SKILL.md:144` verbatim: `implementation` → Implementing, `plan` → Preparing, `transient` → **no recommendation**, ticket stays in Verifying with a `VERIFICATION_TRANSIENT_RETRY` finding, `inconclusive` → **no recommendation**, ticket stays in Verifying with `VERIFICATION_INCONCLUSIVE`. A non-PASS proof that names no class is treated as `inconclusive` — the skill's explicit default, and the safe one. `apply_reconciliation` on a ticket whose recommendation is `null` is a normal refusal, not an error condition.
- [x] **Where does the durable audit record live?** — Resolved: the `## Transitions` record in `scratch/execution.md` that CORE-121 established, written by `store.appendTransition`. It is committed to the board branch, included in the document-inclusive revision, and already the home for backward moves and claim transfers. `appendActivity` is kept as a secondary index only — it is explicitly best-effort (`catch { /* best-effort by design */ }`) and self-truncating, which is exactly CORE-113's unresolved objection. Every applied action writes exactly one transition line naming the action, the from/to stage or claim, and the old → new responsible controller.
- [x] **What moves with the tool roster 39 → 40?** — Resolved: nine places, tabulated in `research/research.md` and re-stated as checklist steps — `smoke.mjs:69` and its roster list at `:72`, `smoke-protocol.mjs:160-161` (message string *and* predicate), `AGENTS.md:413` (§4) **and** `AGENTS.md:638` (§8 item 19's "roster stays 39" parenthetical), `docs/manual/connect.md:145`, the regenerated `chapters.generated.ts` (`npm run build:manual`), the `tool-reference.md` write-tools table (plus its now-false "There is no apply surface" sentence on the `reconcile_ticket` row), and the re-committed `plugins/kanmer/mcp/kanmer-mcp.cjs` bundle verified byte-for-byte by `plugin:check`.
- [x] **Does the apply surface need its own proposal-id hash, as PR #286 had?** — No. **(default taken)** The document-inclusive `revision` already fingerprints the ticket *and* every pipeline document, which is strictly stronger than `updated` and is what closes F-015; a second 64-char token would be one more thing to keep in sync and is unreadable to a caller. `expected_revision` is the only freshness token.
- [x] **Which identity is recorded as the new responsible controller?** — **(default taken)** The calling MCP client, as `write(...)` already resolves it via `actorName(server, extra)` for the activity log. `apply_reconciliation` also accepts an optional explicit `controller` for a host that runs on someone's behalf. No new identity model.

## Parked (explicitly deferred)

Everything below this heading is not counted by the gate.

- [ ] **May `apply_reconciliation` return a Review ticket to Implementing on its own authority, or must an operator authorise it?** — This is an authority/policy decision, not an implementation choice, and only the operator can make it. The facts: `store.backwardMoveEffects` (`packages/core/src/store.ts:940-1001`) refuses `review → implementing` with `REVIEW_RETURN_NEEDS_ATTESTATION` unless a valid `needs-changes` attestation in `scratch/review.md` is bound to one of the ticket's `prs`, **or** the reason begins `operator:`. Both of the classifier's `MOVE_TO_IMPLEMENTING` routes — `CLOSED_UNMERGED_REVIEW` and `REVIEW_WITHOUT_PR_OR_WORKER` — are precisely the cases in which no attestation can exist, because the PR is closed or absent. So the route is unreachable for an autonomous agent unless a third authority (say a `reconcile:` reason prefix) is added to CORE-121's contract. **Recommendation: do not add one.** `apply_reconciliation` should take a `reason` from the caller and let the existing contract judge it, so the route succeeds when an operator supplies an `operator:` reason and refuses with the existing `REVIEW_RETURN_NEEDS_ATTESTATION` code otherwise. That keeps CORE-121's audited backward-move contract the single authority, matches HZN-008's interim rule that "agents never use `force`" and that the operator performs transfers, and still satisfies FRD-028 acceptance 3 (whose enumeration names merged-Review, PASS-Verifying, verification failures and abandoned claims — not closed-unmerged). **Safe to defer** because the plan implements the recommendation as the default, so nothing is blocked: the behaviour is a one-line policy change if the operator later decides otherwise. **What would reopen it:** an operator decision to let a controller self-authorise the return, or a later FRD amendment adding a reconciliation authority to the backward-move contract.
- [ ] **F-016 (`GH-3867261023`): failing or pending required checks pre-empt the closed-unmerged Review rollback in the classifier.** — Inherited from CORE-122, dispositioned minor there, unfixed. Deferring is honest under HZN-008's Scope discipline section: it is neither a blocker/major nor a finding that blocks a named FRD acceptance criterion, so it is recorded as explicit residual risk rather than filed as a follow-up ticket. **What would reopen it:** evidence that a real recovery is blocked by it, which would make it block FRD-028 acceptance 3.
