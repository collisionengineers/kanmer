## Problem

`get_ticket_doc` accepts one document id per call. Workflows that must read a ticket’s research, files, open questions, plan, and checklist therefore spend several sequential or parallel MCP calls retrieving one ticket folder.

## Desired outcome

Allow callers to request multiple ticket documents in one `get_ticket_doc` invocation while preserving the existing single-document form for compatibility. Return a clear per-document result containing the document id, existence/content, and version token so callers can still use optimistic concurrency with `set_ticket_doc`.

Define deterministic behavior for unknown document ids and partial availability: one missing document must not hide the successfully retrieved documents, while invalid inputs must remain explicit.

## Verification

A single protocol request retrieves several selected documents with their independent content and version metadata. Existing one-document clients continue working unchanged, and MCP tool-reference/plugin sync checks cover the updated schema and response.
