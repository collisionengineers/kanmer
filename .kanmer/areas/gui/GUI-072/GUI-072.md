## What

Checkboxes in Settings render detached from their labels — pushed to the far
right and onto a line above the text. Affects at least Appearance
("Toast when an agent changes the board…", "Ask for confirmation before deleting
a ticket") and Git ("Automatic sync").

## Why

`label.check` has **no styling inside Settings**. The only rule for it in
`styles.css` is scoped to the filter bar:

```css
.filterbar .check { display: flex; align-items: center; gap: 5px; … }
.filterbar .check input { width: auto; }
```

There is no bare `.check` rule — grep returns zero. So in the Settings modal the
same markup (`Settings.tsx:282`, `:309`, `:513`) is an unstyled `<label>`,
picking up the modal's generic label/input layout instead: the input takes the
full width rule that fields use, and the text falls below it.

The class name makes it look styled. It is styled — somewhere else.

**Research refined this.** The cause needs *two* conditions, not one: the global
`input, select, textarea { … width: 100% }` (`styles.css:82-92`) has no type
exclusion, so the checkbox stretches into a full-width bar; and no bare `.check`
rule exists to counteract it. Measured before the fix: 786px wide in Settings
(866px at the real modal width), 94px in the Backlog actions row.

## Approach

- Promote `.check` to a bare rule (flex, centred, small gap, `input { width:
  auto }`), and let `.filterbar .check` keep only what is genuinely filter-bar
  specific — colour and font size.
- Check every `.check` in the codebase, not just the three in Settings; anything
  outside `.filterbar` is currently broken the same way and may not have been
  noticed.
- Look for the same shape elsewhere: a component-scoped rule whose class is used
  by an unrelated component is a pattern, and this is unlikely to be the only
  instance.

## Outcome

**Shipped** in PR [#39](https://github.com/collisionengineers/kanmer/pull/39),
squash-merged as `ed52e39` (branch commit `bdc2a1d`). CSS-only: `styles.css`
+16/−11 plus one new test file. No `.tsx` touched, which kept the ticket
file-disjoint from GUI-069/070/071 and GUI-074/080 in the same lane.

- Added a bare `.check` rule (`display:flex; align-items:center; gap:8px;
  cursor:pointer`) with `.check input { width:auto }`, modelled on `.check-row`
  (`styles.css:1322`) but **layout declarations only** — copying that rule's
  `font-size:12px` / `margin-top` would have resized the Settings rows as well
  as repositioned them.
- Deleted the dead `.filterbar .check` and `.filterbar .check input`.
- Added `stylesCheckRule.test.ts`: four zero-dependency assertions over
  `styles.css`, labelled throughout as a **rule-presence assertion, not a layout
  assertion** (no browser test dependency was added — operator decision, O2).
  Not vacuous: 3 of its 4 assertions fail against the pre-fix stylesheet.

**Shipped differently than the ticket described, in two ways.** There were
**four** broken sites, not three — `BacklogTable.tsx:147` was the fourth, which
the ticket did not list — and the filter-bar verification line was
unsatisfiable, corrected above rather than silently dropped.

**Proof:** before/after renders of all four call sites plus the `.check-row`
control, in dark, light and compact, captured on merged main and reviewed by
eye; six PNGs under `proof/`. Checkbox 786px → 13×13px, label `display:inline` →
`flex`, box/text centre offset 20.5px → 0.3px, row height 36.5px → 19.5px, and
the label text still toggles at every site. Limit stated in proof.md: this is
Chromium layout from `styles.css`, not the packaged app at the user's DPI or
under OS accessibility scaling.

**Follow-up filed:** [[GUI-082]] — audit `styles.css` for other dead and
mis-scoped selectors, the wider sweep deliberately kept out of this ticket
(Q7). It also inherits the `.check` / `.check-row` duplicate-idiom cleanup,
which was left alone here on purpose: `.check-row` was the only correctly
rendering row, and unifying it in this ticket would have turned the reference
implementation into a regression risk.

**Left as-is on purpose:** the global `input` rule at `styles.css:82` still
stretches any checkbox or radio not wrapped in `.check`. Narrowing it re-cascades
every text input in the app; the class-level fix is the deliberately narrower
blast radius (Q3).
