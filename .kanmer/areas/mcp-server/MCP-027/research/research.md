# Research — MCP-027: connector doctor — tunnel and transport health

## Question

What must MCP-027 add to diagnose configuration, tunnel, local HTTP, bearer, project, and public-route failures without exposing secrets or changing board state? Which existing MCP-021/025/026 contracts and test seams can the doctor reuse, and where are the current gaps?

## Findings

- **The governing contract is already explicit.** [Source: `docs/functional/frd/FRD-025-remote-access.md`, RA-DOCTOR-1, RA-OBS-1/2; `docs/architecture/adr/ADR-0017-streamable-http-remote-access.md`, §§1, 6, 8.] The doctor must distinguish executable/configuration, loopback bind, negative/positive bearer, MCP initialize/handshake, expected project fingerprint, remote tool policy, and requested tunnel reachability. Results must name a component and safe remediation, redact secrets, and preserve separate board/listener/auth/session/tunnel/remote-handshake dimensions. It is a local operator/GUI surface, not a remotely exposed MCP tool, alternate transport, auto-repairer, account/DNS mutator, or arbitrary network scanner.
  - **Risk:** Collapsing these checks into one boolean would hide whether a public failure is DNS/TLS, tunnel readiness, local origin, bearer, or board identity.
  - **Implication:** The report needs stable ordered check ids, explicit severity/status, prerequisites, safe observed/expected details, and a renderer over one structured result.

- **MCP-021 provides the provider-neutral tunnel boundary and the first Cloudflared implementation.** [Source: `packages/mcp-server/src/tunnels/types.ts`.] `TunnelAdapter` already exposes `doctor()`, `start()`, `getStatus()`, `stop()`, redacted `getDiagnostics()`, and optional status subscription; generic input is a loopback `TunnelTarget` plus provider-discriminated config and an opaque credential path. Generic states are `stopped`, `validating`, `starting`, `connected`, `degraded`, `stopping`, and `failed`; status carries non-secret attempt, endpoint, pid/version, project fingerprint, auth generation, and coded reason fields.
  - [Source: `packages/mcp-server/src/tunnels/cloudflared.ts`.] The current adapter doctor only checks the executable/credential file pair. Start performs stricter validation, creates a protected temporary config, reserves a loopback metrics port, invokes direct `shell:false` with a minimal environment, polls the provider readiness endpoint, monitors readiness flap, and removes owned resources on stop/failure. Its diagnostics are bounded/redacted.
  - [Source: `packages/mcp-server/src/tunnels/cloudflared-config.ts` and `packages/mcp-server/src/tunnels/cloudflared-validate.ts`.] The pure config validator requires a UUID tunnel id, one exact HTTPS hostname, one exact loopback `/mcp` origin, and a terminal `http_status:404` ingress rule. The executable validator runs only bounded direct `--version` and `tunnel --help`; ingress validation runs `tunnel --config … ingress validate` and an exact-host rule check. These are the reuse points for config mode; config mode must not call adapter start or create runtime resources.
  - **Risk:** Treating a child PID or provider log line as readiness would produce false health; the accepted signal is the bounded provider readiness/status contract in `packages/mcp-server/src/tunnels/readiness.ts`.
  - **Risk:** Calling `start()` from config mode would write temp files, reserve/bind a metrics port, spawn a provider, and violate the no-mutation/no-account-operation boundary.
  - [Source: `packages/mcp-server/src/tunnels/supervisor.ts` and `packages/mcp-server/src/remote-host.ts`.] Restart/backoff is bounded and terminal exits can be classified; RemoteHost starts the authenticated local host first, runs a required local verifier, then passes only loopback endpoint/project/auth-generation metadata to the adapter. The current RemoteHost status has `local`, `provider`, and `publicVerification` dimensions, but no doctor report or public verification implementation.

- **MCP-025 owns the canonical local Streamable HTTP host and MCP-026 owns bearer/secret handling.** [Source: `packages/mcp-server/src/http.ts`.] `KanmerHttpHost.start()` resolves the immutable project before binding and returns a safe ready record containing the loopback `/mcp` endpoint, process id, project fingerprint, `authRequired`, transport mode, and supported protocol versions. Authentication is applied before body parsing/session lookup; POST, GET, and DELETE are independently authorized; session close/rotation failures are surfaced and shutdown is bounded.
  - [Source: `packages/mcp-server/src/http-auth.ts` and `packages/mcp-server/src/http-secret.ts`.] Bearer material is 32 random bytes encoded as 43-character base64url, verified through SHA-256 fixed-length constant-time comparison, and exposed only as opaque token id/fingerprint metadata. Protected token-file load validates regular/no-follow/size/permission/file-identity constraints. `loadTokenMaterial()` is an internal remote bootstrap seam and its raw token must never enter report/diagnostic/output paths.
  - [Source: `packages/mcp-server/src/index.ts` and `packages/mcp-server/src/project-identity.ts`.] `createKanmerMcpServer("remote-http-v1")` composes the same registry as stdio through a central exposure policy; remote exclusion is a set, not per-handler duplication. `get_status` and the ready record expose the canonical `kanmer-proj-v1:<sha256>` project fingerprint. The doctor must import/reuse these contracts rather than copy tool lists, project hashing, or expected-project semantics.
  - **Risk:** A doctor that infers board identity from hostname/URL or accepts a caller-selected root can diagnose the wrong project. Every local/public positive check must compare the full expected fingerprint, and the doctor must not accept arbitrary URLs or route requests to a different board.

- **The existing remote composition proves the intended local-first ordering but is not itself a doctor API.** [Source: `packages/mcp-server/src/remote-cli.ts`, `packages/mcp-server/src/remote-host.ts`, `packages/mcp-server/src/smoke-remote.mjs`.] The headless command reads provider/token references from protected environment/file inputs, performs an authenticated local MCP initialize followed by DELETE before starting the tunnel, and emits only safe status metadata. The smoke uses a fake provider and deliberately has no public route. The doctor should reuse the same official protocol/cleanup behavior through injected callbacks or library seams; it must not turn the remote CLI into an arbitrary diagnostic target.

- **Current coverage is strong for predecessors but there is no doctor surface yet.** [Source: `packages/mcp-server/src/http.test.mjs`, `http-auth.test.mjs`, `http-secret.test.mjs`, `remote-host.test.mjs`, `remote-cli.test.mjs`, `tunnels/cloudflared*.test.mjs`, `tunnels/readiness.test.mjs`, `tunnels/supervisor.test.mjs`, `smoke-http.mjs`, `smoke-remote.mjs`.] Existing tests cover local auth rejection/acceptance, official SDK initialize/discovery, project fingerprint, remote policy parity, session close, Cloudflared exact ingress and executable checks, readiness/flap, process cleanup, restart classification, redaction, and fake-provider lifecycle. They do not provide schema-v1 doctor report aggregation, stable check ids, prerequisite skips, public DNS/TLS/redirect probes, negative/positive public MCP probes, or a doctor CLI/smoke.
  - [Source: `packages/mcp-server/package.json` and root `package.json`.] The server exposes stdio, HTTP, token, and remote CLIs only; there is no doctor bin/script. `test:http` builds the server and runs the current HTTP/tunnel test set. Root `npm test` includes that package suite; the canonical plugin/tool surface must remain unchanged. There is no `scripts/verify.mjs` in the current checkout, so the doctor rail must integrate with the existing package/root commands or the separately owned verify ticket rather than claim a nonexistent command.
  - **Risk:** Implementing an unregistered library or a second CLI-only evaluator would leave GUI-095/MCP-028 without a stable production caller or create divergent JSON/human results.

- **The ticket’s existing decisions already resolve product-level ambiguity.** [Source: MCP-027 `open-questions.md`.] Modes are `config`, `local`, and `public`; config makes no network/provider changes; local/public do not mutate the board; valid bearer material comes through the protected secret-provider/GUI callback; public mode uses only the validated configured hostname; standard certificate verification and no automatic redirects are required; official SDK Streamable HTTP is for positive initialize/discovery/session lifecycle while raw HTTP is limited to negative auth/status/redirect edges; the exact remote exposure set comes from MCP-025; later checks are explicit `skipped`; exit codes are 0 healthy/warnings, 1 required failure, 2 invalid invocation/internal inability; no doctor MCP tool is added. The file is complete with no unresolved non-parked questions.

- **The ticket is correctly positioned for this research handoff.** [Source: MCP-027 item/gates and HZN-007 `context.md`.] MCP-027 is a feature in Preparing, references FRD-025 and ADR-0017, blocks MCP-028, and is blocked by the completed MCP-021 adapter. Its governing-doc gate is satisfied even though the item still carries `docs_todo: true`; no stage move is part of this research handoff. HZN-007 requires the provider-neutral sequence MCP-021 → MCP-027 → GUI-095/DOC-013 → MCP-028 and requires remote proof only in MCP-028.

## Implications

- Build one doctor library around a schema-v1 structured report and one ordered check registry. Render human text from that report; JSON is canonical and deterministic. The CLI should validate invocation and protected configuration, keep stdout machine-readable, keep diagnostics on stderr, and return only the agreed 0/1/2 exits.
- Keep three mode pipelines explicit: config reuses pure Cloudflared executable/config/ingress validators without starting anything; local checks a configured loopback host using the protected bearer callback, official SDK initialize/discovery/read-only orientation, fingerprint comparison, exact remote exposure policy, and session DELETE; public adds configured-host-only DNS/TLS/no-redirect and the same negative/positive auth/MCP/project/tool/session checks, then compares local/public identities. All later checks become explicit prerequisite-based skips.
- Add injected interfaces for secret metadata/token generation, HTTP/SDK client, DNS/TLS connector, clock/abort/timeout, and tunnel status/doctor so normal tests remain disposable and offline. Use built-in Node networking/SDK APIs; no general scanner or dependency is justified by the current repository.
- Preserve the existing validators and registry. A minimal production wiring should expose the doctor library to the new CLI and leave GUI-095 to consume the JSON/library contract; MCP-028 should consume the same report for controlled remote proof. Do not add a remote MCP doctor tool, alternate transport, board mutation, tunnel auto-repair, credential rotation, Cloudflare account/DNS calls, or extra provider mode.
- The planned doctor files are a new `packages/mcp-server/src/doctor/` surface (types, checks, config checks, MCP checks, network checks, orchestration, rendering, tests, generated fixtures) plus `packages/mcp-server/src/doctor-cli.mjs` and `packages/mcp-server/src/smoke-doctor.mjs`. Existing integration touchpoints are `packages/mcp-server/src/index.ts`, `http.ts`, `http-auth.ts`, `http-secret.ts`, `tunnels/types.ts`, `tunnels/cloudflared.ts`, `remote-host.ts`, package/root scripts, and the shared FRD/manual consumers. The current ticket files document lists a stale `packages/mcp-server/src/server.ts`; the actual canonical registry module is `index.ts` and the plan must correct that path.
- Evidence must include canary scans over report/status/error/stdout/stderr and ensure no token, verifier, authorization header, full session id, document/prompt body, credential content, or unsafe path leaks. Local/config tests can be committed and run in normal CI; public provider/DNS proof remains MCP-028/manual and must not be fabricated here.
