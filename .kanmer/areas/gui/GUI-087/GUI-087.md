## What

`friendlyGateError` in `apps/gui/src/renderer/src/App.tsx` never rewrites
anything. It early-returns unless the message contains the string
`"document gate(s) unmet"` — **a phrase that exists nowhere else in the
repository**. Grep finds exactly one occurrence: the guard clause itself.

So every gate refusal reaches the human error banner in its raw, agent-facing
form.

## What the user actually sees

Verbatim from `packages/core/src/store.ts`, unmodified on the way to the banner:

> `API-003 cannot move from "verifying" to "done": entering Done requires proof
> (profile "fix"). Write the missing document(s) **with set_ticket_doc**, then
> move. **Call get_doc_gates** for the full picture.`

`set_ticket_doc` and `get_doc_gates` are MCP tool names. A human dragging a card
has no way to act on either, and the sentence reads as an internal error that
leaked.

The "questions-resolved" variant is worse — it tells the user their
`open-questions/` folder has unticked `- [ ]` lines, which is right, but frames
it as something to fix with a tool call.

## Why it was missed

The function exists, is called, and looks correct at the call site. Only reading
its first line shows it can never do anything. It was presumably written against
an earlier message format and never updated when the messages changed.

## Found by

[[DOC-007]], while writing the manual's "Why can't I move this?" chapter. That
chapter is deliberately **honest about this** — it quotes what users really see
and translates it, rather than describing friendlier copy that does not exist.
When this ticket lands, that section of the chapter should be revisited.

## Approach

Two candidate fixes, and the choice matters:

1. **Fix the sentinel** — match on what the messages actually contain (`cannot
   move from`) and rewrite the tool names into GUI language: "write it in the
   ticket's tab", "the readiness panel at the top of the Ticket tab shows the
   whole picture". Cheap, but leaves two copies of the wording to drift apart.
2. **Have core emit an audience-neutral message** and let each surface add its
   own affordance. More correct, more work, and it touches the MCP surface that
   agents rely on — those messages are genuinely useful *to agents* and should
   not be dumbed down for them.

Recommend 1 with a test that fails if the sentinel stops matching — the class of
bug here is precisely a guard that silently stops applying.

Whichever is chosen: **add a test that asserts a rewritten message, not that the
function was called.** A test that mocks the input to contain the old sentinel
would have passed throughout this bug's life.
