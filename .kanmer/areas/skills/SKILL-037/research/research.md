# Research — SKILL-037: review consolidation and remediation-loop contract

*The research. Not the files document — this is what you **learned**, not what you will **touch**.*

## Question

What does the shipped CORE-121 contract on `origin/main` (a8318ea6) and the in-flight CORE-123 branch already provide, and what must the review / execute / verify / auto / closeout skill prose say so that (a) an attestation cannot precede later reviewer findings on the same head, (b) an in-scope finding legally returns the same ticket/branch/worktree/PR to Implementing, and (c) verification failures carry a typed class with a routing table — without contradicting `scripts/verify-skill-prose.mjs` or the code the prose describes?

## Findings

- **CORE-121 shipped the mechanics the skills must describe** (`packages/core/src/types.ts` 356–621, `store.ts` 802–1130, `packages/mcp-server/src/index.ts` 1211–1250, `packages/mcp-server/src/execution-packet.ts` 65–80, 482–549):
  - Claim fields on a ticket: `taken_at`, `branch`, `worktree`, `claim_expires_at`, `claim_controller`, `review_round` (default 0), `remediation_budget` (default 1). Board `claimExpiryMinutes` defaults to 30. `claimState()` returns `unclaimed | live | expired`.
  - `take_ticket action: "transfer"` hands an **expired** claim to the caller while preserving branch/worktree/`taken_at`; a live claim refuses with `CLAIM_LIVE` unless `reason` begins `operator:`. `action: "renew"` extends the caller's own claim; a foreign claim refuses `CLAIM_NOT_OWNED`. Tool description already says "Never use force to recover a dead controller's ticket; transfer it."
  - `move_item` backward moves require `reason` (`BACKWARD_MOVE_NEEDS_REASON`). Review → Implementing additionally needs a **valid `needs-changes` attestation in `scratch/review.md` whose `pr` matches an entry in the ticket's `prs[]`** (`REVIEW_RETURN_NEEDS_ATTESTATION`), or a reason beginning `operator:`. It increments `review_round`; once `review_round >= remediation_budget` the move refuses `REMEDIATION_BUDGET_EXHAUSTED` unless the reason is `operator:` (which also raises the budget). GUI actor gets an implicit `operator: moved on the board` reason. Every backward move and transfer is appended under `## Transitions` in `scratch/execution.md`.
  - `get_execution_packet` carries a `claim` block (`state`, `expiresAt`, `controller`, `reviewRound`); an expired foreign claim is refused with text naming `take_ticket action "transfer"` or resume with the exact recorded branch/worktree. Resumed packets are issued **only while the ticket is in `implementing`** — so the re-entry lane is: reviewer/controller moves Review → Implementing first, then execute resumes the packet.
  - The `prs[]` binding means execute **must record the PR ref on the ticket** (`update_item prs`) for the sanctioned return to work; the current execute skill already says to record the PR with `update_item` (step 2 of Finish) — the re-entry text must make the same-PR rule explicit.
- **Attestation schema** (`packages/core/src/review-attestation.ts` on main; CORE-123 branch `origin/core-123-merge-gate-board-sync` adds optional fields): required `kind: review-attestation`, `pr`, `head_sha` (full 40-hex), `verdict: pass | needs-changes`, `reviewer`, `independent`, `plan_hash`, `ticket_updated`, `findings[]` (each `id` matching `^F-\d{3,}$`, `severity blocker|major|minor|note`, `summary`, `disposition open|fixed|rejected-with-reason|accepted-risk|deferred-to-ticket`, `reason` required for rejected/accepted-risk, `ticket` required for deferred). CORE-123 adds **optional** `board_sha` (full SHA when present), `expected_reviewers` (array of non-empty strings), `threads_snapshot` (array, carried not interpreted). Absence keeps older attestations valid; a malformed present value is invalid. Finding ids must be `F-###` — so any external (GitHub) thread id must be **mapped** to an F-id, never used as the id itself.
- **CORE-123's diff of `kanmer-review/SKILL.md`** (12 lines) inserts the three fields into the frontmatter block and a paragraph: `board_sha` is `get_status.boardSync.localSha` with `ahead` at 0 after pushing the board; the CI gate reports `SYNC_REQUIRED` when it names an unseen board; `expected_reviewers`/`threads_snapshot` are "optional arrays … omit them rather than guessing". My rewrite must keep the same three field names and the `board_sha`/`SYNC_REQUIRED` sentence so the merge is compatible, but SKILL-037 makes `expected_reviewers` and `threads_snapshot` **required by this skill's procedure** (the schema stays optional for older attestations). CORE-123 also touches `kanmer-tickets/references/tool-reference.md` (`get_status` row only — `boardSync`), `AGENTS.md` (regate/`SYNC_REQUIRED` prose outside the managed block), merge-gate, check-pr, pr.yml, kanmerGit.ts — all off-limits to this ticket.
- **Operator ruling on expected reviewers** (controller brief): Codex/GitHub bot reviews are **not** a gate and not part of the workflow. HZN-008 context.md's interim rule says "every expected automated reviewer"; this ticket formalises it as the **independent subagent reviewer(s) named for the ticket** (the `expected_reviewers` set), with the settle rule "every expected reviewer has posted on the exact head, or is recorded explicitly as timeout-absent". Bot threads that do exist on the head are still evidence and still get dispositioned (mapped to F-ids) — they just never block by absence.
- **HZN-008 context.md "Interim ownership and remediation rule"** is the source of the prose to formalise: expired-claim = older than window with no pause/resume note; transfer records old/new controller + branch + worktree; agents never `force`; needs-changes attestation bound to the current head is the only agent-side authority to return Review → Implementing, same branch/worktree/PR; budget one batch + one delta review unless operator extends; attestation authoritative only after every expected reviewer posted on the exact head, later post on the same head → attestation **replaced**, not appended; confirm board pushed (`boardSync.ahead == 0`) before trusting a `kanmer-gate` result.
- **FRD-034** (draft, governing): one consolidated review, one in-scope remediation batch, one delta review "limited to original findings, changed lines, direct callers/contracts and relevant tests"; only blocker/major, failed required checks, stale review, unmet acceptance, or security/data-loss risk block merge; verification "routes transient failures, flake retries, implementation defects, plan defects, stale review and unavailable services to defined bounded outcomes"; AC3 same ticket/PR + one delta review; AC4 routes implementation/plan failures back to the correct earlier phase; AC5 budgets stop repeated unchanged audits.
- **Current skill text defects** (origin/main): `kanmer-review` says on needs-changes "leave the ticket in Review, and do not merge" and "Review feedback that needs implementation becomes a linked PR Review ticket" — both contradict the sanctioned same-PR return. `kanmer-execute` step 6 always "open a PR"; its resumed-packet section forbids re-take but says nothing about an existing PR or renewing the claim. `kanmer-verify` has no failure class and routes every non-PASS to "stay in Verifying (retryable)" or operator retirement; `WAIVED_BY_OPERATOR` is already listed as a top-level result. `kanmer-closeout` accepts only `PASS` for the Done shape (Done + WAIVED_BY_OPERATOR would be rejected) even though verify and the tool reference say WAIVED_BY_OPERATOR is the human disposition. `kanmer-auto` §1.2 says "tickets taken by another actor; coordinate rather than using `force`" and §9 "Never use force takeover as fallback" but never names `transfer`; stop predicate 8 treats any occupied ticket as a stop even when the claim is expired. Nothing tells subagent workers to read their own background logs.

- **Tool reference** (`kanmer-tickets/references/tool-reference.md` rows 41–42, 120–121, 212–255) already documents `transfer`/`renew`, the Review → Implementing rule, `review_round`/`remediation_budget`, the attestation finding schema and the proof `WAIVED_BY_OPERATOR` top-level rule. It does not list `board_sha`/`expected_reviewers`/`threads_snapshot` (CORE-123 did not add them to the attestation section) nor `failure_class`. Proof `result` enum is enforced by the tool-reference prose and the check-pr/proof validation only for the listed top-level values; `failure_class` is a **new optional key** that no parser rejects (frontmatter is free YAML), so introducing it in prose is safe without a core change.

## Implications

- The skill rewrite is pure prose plus consistency edits; no TypeScript changes. Every new rule has a runtime home already (CORE-121 store/MCP) or is a reviewer-procedure rule whose truth is board-independent (check 7 safe).
- Field names must be exactly `board_sha`, `expected_reviewers`, `threads_snapshot` (attestation) and `failure_class` (proof), and finding ids `F-###`.
- The review skill's needs-changes path becomes: write the `needs-changes` attestation bound to the current head **with the PR recorded in `prs[]`**, then `move_item review → implementing` with `reason` (one gated boundary backwards, audited), leaving branch/worktree/PR untouched, then hand off to `kanmer-execute`'s re-entry lane. Round 2 (after `review_round` = 1) is a **delta review**; a third return needs an `operator:` reason.
- The verify skill's routing table must sit alongside (not replace) the existing retryable-default and terminal-retirement text that check 16 pins: `transient` → retry in Verifying (default), `implementation` → Implementing via `move_item` with reason after operator/controller authority (a proof is not an attestation, so the store requires an `operator:` reason for Verifying → Implementing; document that the controller supplies it and that backward moves from Verifying are audited), `plan` → Preparing (same, `operator:` reason), `inconclusive` → stay in Verifying and report. Verifying → Implementing/Preparing is a backward move outside the Review → Implementing special case, so it needs only a `reason` — but by convention the reason should quote the failure class and proof.
- Closeout: accepted Done shape becomes "final proof result `PASS`, or `WAIVED_BY_OPERATOR` with operator identity and reason in the proof body".
- Auto: replace the stop-on-occupied wording with "live foreign claim → stop predicate 8; expired foreign claim → `take_ticket action: "transfer"` with a scratch note naming old/new controller, branch, worktree; never `force`"; add "workers renew their claim on resume and before long commands; a subagent that backgrounds a command reads its own log rather than waiting for a notification".
- Compatibility with CORE-123: keep its sentence about `board_sha`/`SYNC_REQUIRED` verbatim-ish so the later merge is a clean textual overlap; expect a merge conflict in the same paragraph either way — whichever lands second re-applies the other's sentence.
