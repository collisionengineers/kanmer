# Open questions — CORE-119

Every question below was resolved during research and planning; the answer is recorded here as well as in `plan/plan.md` so it can be found later. Trivial defaults were taken rather than asked, and each is named as such.

- [x] **Where does the golden runner live, and is it a `VERIFY_STEPS` entry or a separate rail?**
  Resolved: `packages/mcp-server/src/golden-board.mjs`, invoked as `npm run golden`, appended to `VERIFY_STEPS` after `npm run smoke:discovery`. `AGENTS.md:502` states the repository rule outright — *"Extend `VERIFY_STEPS`, never a third verification pyramid"* — and one array edit then reaches `.github/workflows/pr.yml` `verify` (every PR and every push to `main`), `.github/workflows/release.yml` `release-verify` (every `v*` tag) and `scripts/release.mjs:308` (the prepare phase). A separate workflow would need three new wirings and would leave `npm run release` uncovered. The runner is safe to put on the shared rail because it enforces its own fail-closed `KANMER_GOLDEN_BUDGET_MS`.

- [x] **Does the promotion rehearsal also belong in CI?**
  Resolved: no. A GitHub runner has no prior stable install, no retained prior-stable installer and no live-board backup, so `install-candidate`, `rollback` and `cut-over` cannot execute there and would have to be faked — which FRD-035 edge case 1 forbids. `npm run golden:promotion` is an operator/release script owned by CORE-137. FRD-035 AC5 is still met: the promotion record is an ordinary PR whose required `verify` check now includes `golden`.

- [x] **What is the wall-clock budget, and what happens if the runner exceeds it?**
  Resolved: `KANMER_GOLDEN_BUDGET_MS`, default 300 000, checked between scenarios, exhaustion is exit 1 naming the elapsed time and the remaining scenario ids. Five minutes is sized from the measured Windows costs in `packages/core/vitest.config.ts:1-30` (a ~1 s first-locked-write PowerShell identity resolution **per process**, a 2145 ms lock-retry ladder, and a 3–5× slowdown when a second rail shares the host), which is also why scenarios are grouped by fixture so one server process serves many of them. An overrun gets exactly one mechanism fix — fewer server spawns by regrouping onto fewer fixtures — never a raised budget and never a deleted scenario.

- [x] **Should the existing smokes be refactored so the golden runner can import shared helpers?**
  Resolved: no. `packages/mcp-server/src/smoke.mjs` is 4132 lines with **zero exports** and runs its whole suite as top-level side effects ending in `process.exit` at `:4132`; importing it executes the suite. A mechanical extraction from an authoritative rail file during a release window is a large diff with no acceptance value. The four idioms — `startServer` (`smoke-protocol.mjs:50`), `textOf`/`check`/`treeSnapshot` (`smoke.mjs:22`/`:60`/`:27`) and `directoryDigest` (`reconciliation.test.mjs:122`) — are copied into one new harness module. Recorded in `files/files.md` → Out of scope; not filed as a follow-up because it fails the HZN-008 scope test (no named FRD acceptance criterion requires it).

- [x] **How does the runner guarantee it never touches the live board?**
  Resolved mechanically, not by convention, because ADR-0021's Consequences require it: every board root is a fresh `mkdtempSync(join(tmpdir(), "kanmer-golden-"))`; `assertDisposable(root)` throws unless the root is under the realpath of `os.tmpdir()` and contains `kanmer-golden-`; the child env **deletes `KANMER_ROOT`** (the `smoke-discovery.mjs:26` precaution — on this machine an inherited `KANMER_ROOT` points at the live board); the CLI rejects a `--root` flag outright; and GB-00 asserts all of it, including that `get_status.projectRoot` equals the fixture with `rootSource: "flag"`. A full rail run ends with `git -C .worktrees/kanmer status --porcelain` empty.

- [x] **Which fixture boards are needed, and are any copied from the real board?**
  Resolved: three shapes, none copied. `fresh` is the two-file `.kanmer/version.json` `{"format":3}` skeleton already used at `scripts/verify.mjs:45-47`; `seeded` is `KanmerStore.init()` plus a small census (two areas, one group, six tickets covering all six stages, one capture, one `feature` ticket with `research`/`files`/`plan`/`checklist` and a structured `### Step 1 — …` plan), with a `legacy` variant that deletes `project.json` afterwards (the `smoke.mjs:725-775` idiom); `repo` is `seeded` plus an offline `git init`. Total on-disk size stays in the low hundreds of kilobytes and contains no secrets. Copying the 6 MB live backup was rejected: it carries the whole real board, is not reproducible in CI, and is not needed for any assertion.

- [x] **Can reconciliation scenarios run without GitHub, and if not, what is recorded?**
  Resolved: two tiers. The **product tier** drives `reconcile_ticket`/`apply_reconciliation` over MCP against the offline `repo` fixture and covers everything with a local source — `BOARD_WORKTREE_PROTECTED`, `WORKSPACE_MISSING`, `CLAIM_WITHOUT_RECORDED_WORKSPACE`, `CLAIM_EXPIRED`, `DIRTY_WORKSPACE_PRESERVED`, dry-run inertness by whole-board digest, and `EVIDENCE_INCONCLUSIVE` when no provider exists (the exact behaviour CORE-136's proof already recorded on the copied board). The **simulated tier** drives the provider-derived routes (`MERGED_REVIEW`, `PASS_PROOF_STILL_VERIFYING`, `PROOF_MERGE_SHA_MISMATCH`, `VERIFICATION_FAILED_IMPLEMENTATION|PLAN`) through the injected `ReconciliationRun`/`CommonDirResolver` seam (`packages/mcp-server/src/reconciliation.ts:71,77,321,409,600`; the `reconciliation.test.mjs:47,88-111` shape), recording `mode: "simulated"` with the injected evidence printed. FRD-035 Behaviour ("simulated provider-adapter evaluations") and edge case 1 authorize exactly this and forbid calling it a provider pass. No `gh`, no network.

- [x] **Does the missing-worktree scenario depend on CORE-133?**
  Resolved: yes, hard. CORE-133's plan Step 2 introduces the recoverable-workspace predicate that makes `missing + unavailable` and `not-recorded + not-applicable` reach `RECOVER_EXPIRED_CLAIM`. GB-15 is written as a hard assertion against merged CORE-133 — no capability gate, no version sniffing, no skip — and Step 8 begins by rebasing onto CORE-133's exact merge and re-reading both reconciliation modules. HZN-008's 2026-09-02 order already sequences CORE-133 before CORE-119, and CORE-137's cut point requires both Done. **Controller action:** link CORE-133 `blocks` CORE-119 before dispatching implementation, so the order is recorded on the board and not only in this plan. (Recording a link is a board mutation this research/planning pass deliberately does not perform.)

- [x] **How is this coordinated with SKILL-039 on the anti-churn tests A–G, without duplicating FRD text?**
  Resolved: SKILL-039 owns the normative prose (an "Amendment — review budget and root-cause classes" section in FRD-034) and the `obsolete-after-change` value in `DISPOSITIONS`. CORE-119 copies none of it: GB-18 names each test by its amendment **letter** and cites `FRD-034 § Amendment`, falling back to HZN-008 `context.md` § "Review budget and root-cause rule" if that section is absent. Mechanically testable and covered: **A** (`review_round` advances only through `backwardMoveEffects`, so repeated reads cannot move it), **B** and **C** (merge-gate evaluation on injected PR/attestation evidence), **D** (requires SKILL-039's enum value), and the mechanical half of **F** (`REMEDIATION_BUDGET_EXHAUSTED:` plus the `operator:` authorisation path). Step 7 runs after SKILL-039's merge; if the enum value is absent, GB-18 D records `unavailable` and the rail exits 1 rather than asserting the pre-amendment behaviour as correct.

- [x] **Which server binary does the runner drive?**
  Resolved: `packages/mcp-server/dist/index.js` by default, overridable with `KANMER_SERVER` — the same convention as `smoke.mjs:15-16` and `smoke-headless.mjs:11` — so the AGENTS.md §10 discipline (`KANMER_SERVER=plugins/kanmer/mcp/kanmer-mcp.cjs`) applies to `npm run golden` exactly as it does to the smokes. `KANMER_NODE` + `ELECTRON_RUN_AS_NODE=1` is honoured so the runner can also drive the packaged Electron-as-node path. Default taken without asking.

- [x] **Does MCP-055's `structuredContent` change break the harness?**
  Resolved: no, provided the harness reads `content[0].text` for successful payloads and `structuredContent.error.code` for refusals. Error results already carry `{error:{code,message}, project}` (`packages/mcp-server/src/errors.ts:74-87`) and MCP-055 does not change them; MCP-055's own approach requires `JSON.parse(content[0].text)` to deep-equal `structuredContent` minus `project`, so the text block stays authoritative either way. The harness is therefore insulated whether MCP-055 lands before or after this ticket, and no ordering dependency exists.

- [x] **Is `git` a hard requirement, and what if it is unavailable?**
  Resolved: required for the `repo` fixture, used offline only (`init`, `add`, `commit`, `branch`, `worktree add`), always with `-c user.email=golden@example.invalid -c user.name=golden` inline so no global config is needed and `windowsHide: true` so the rail does not flash console windows. If `git --version` fails, `repoFixture()` reports `git: "unavailable"` rather than throwing, the dependent scenarios are recorded `unavailable`, and the runner exits 1 — never 0, and never a fabricated pass. Windows CI runners provide git, so this is a diagnostic path, not an expected one.

- [x] **Where is the v0.4.0 transcript recorded as the first passing instance?**
  Resolved: inline in the repository as `RECORDED_TRANSCRIPTS["0.4.0"]` inside `scripts/golden-promotion.mjs`, transcribed from CORE-136 `proof/proof.md`@`2b12c27d1cd31641` with that version cited in a comment, and asserted by `scripts/golden-promotion.test.mjs`. This copies the established repository idiom — `scripts/verify-release-assets.test.mjs:151-154` holds real GitHub API responses as `const GOLDEN = {…}` against a pure comparator. Deliberately **not** a new file under `/docs/`: that would consume a doc-numbering slot, put narrative prose under `check-doc-structure.mjs`, and duplicate the authoritative ticket record. The narrative stays on CORE-136; only the machine-shaped attempts are transcribed.

- [x] **Does the exit-code convention match the repository?**
  Resolved: 0 = pass, 1 = a scenario failed or a required capability was `unavailable`, 2 = the run could not start (usage error, coverage gap). That is `scripts/verify-release-assets.mjs`'s documented convention (`:633`, `:683`, `verificationFailureExitCode` `:508`; `AGENTS.md:502-503`). `process.exitCode` is set and the loop is allowed to drain rather than calling `process.exit()`, per the Windows libuv hazard recorded at `verify-release-assets.mjs:649-654`. Default taken without asking.

- [x] **Does FRD-035, ADR-0021 or FRD-034 need editing?**
  Resolved: no. The plan **Meets** all three; no modification is proposed and no new ADR is written. The FRD-034 Amendment text belongs to SKILL-039. Governing-doc mapping is recorded in `plan/plan.md` → Governing docs.

- [x] **Do the FRD-035 measurement fields require a metrics platform?**
  Resolved: no. FRD-035 says the evaluation "records" verified outcomes, human correction, unnecessary documents, plan deviations, review cycles, stuck stages, recovered leases, incorrect-project attempts, duplicate work and observable tool/token cost. They are recorded as counters in the transcript JSON of a single run. No dashboard, no time series, no cross-run aggregation, no scoring model — MASTERPLAN's "workflow metrics" non-goal and HZN-008's "no metrics platform" both stand. Recorded in `files/files.md` → Out of scope.

## Parked (explicitly deferred)

- **Anti-churn amendment tests E and G are not mechanically testable here.** E ("several findings from one parser or lifecycle root cause produce one replan/follow-up, not several patches or tickets") and G ("budget exhaustion with a genuine unresolved product or security decision does request the operator") are properties of an agent's judgement, not of any server-observable contract: the store records a round counter and a refusal, and nothing in `packages/core` can distinguish one root-cause class from two coincidental findings or a genuine product decision from a stubborn one. Deferred to SKILL-039, which pins them as skill prose enforced by `scripts/verify-skill-prose.mjs`. Attempting them here would mean either an LLM-scored prose gate (explicitly a non-goal) or a test that asserts nothing. Reason for deferral: no server contract exists to assert against, and the owning ticket already exists.

- **`MASTERPLAN.md:43` and `:346` still list "golden-board eval harness (quarry)" and "workflow metrics" as non-goals.** That text is contradicted by PRD-002 requirement 8 and FRD-035, which govern HZN-008. Not edited in this ticket: MASTERPLAN is the superseded v0.3 planning document rather than a governing doc in `refs`, and rewriting a historical plan's non-goal list is documentation churn outside FRD-035's acceptance criteria. Recorded as an explicit dispositioned residual risk — a future reader may find the contradiction — with the resolution written here and in `plan/plan.md` → Governing docs. Reason for deferral: HZN-008 scope discipline (a ticket joins the horizon only if a named FRD acceptance criterion or the Definition of done requires it, and no criterion requires this edit).

- **Extracting the shared smoke helpers into a module the existing smokes also use.** Deferred as ordinary quality work outside this horizon; see the resolved question above for why imitation is the chosen approach. Reason for deferral: a 4132-line rail-file refactor during a release window has real regression risk and satisfies no named acceptance criterion.

- **Automating the live cut-over and the "mark stable" decision.** `golden:promotion` rehearses against a copied board and reports; installing the candidate, stopping the stable server and marking a candidate stable stay explicit operator actions in CORE-137. Reason for deferral: ADR-0021 makes the promotion boundary an auditable operator handoff, and automating the decision would remove the boundary it exists to create.
