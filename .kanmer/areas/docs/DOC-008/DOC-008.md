## What

`README.md` states three things that are false of the shipped product. [[DOC-007]]
found them while writing the in-app manual, deliberately did **not** fix them
there, and got the manual right independently — so README and the manual now
disagree in front of users.

## Why it matters

README is what a user reads **before** they can open the manual. It is the
GitHub landing page and the first thing anyone evaluating Kanmer sees. A correct
manual behind a stale README means the first impression is the wrong one.

## The three

1. **`:78` — the stage list is wrong.**
   Says `Todo → Planning → Implementing → Review → Verifying → Done`.
   The product's stages are **Backlog → Preparing → Implementing → Review →
   Verifying → Done**. Two of six names are wrong, and "Preparing" merging
   research and planning is a deliberate design point the README erases.

2. **`:82-83` and `:155` — claims stages and priorities are editable in
   Settings.** Neither is true. Stages are fixed at six and cannot be changed
   (FRD-007); priority was removed entirely (FRD-008) and no control renders it.
   Settings → Board is areas only — the tab's own copy says "Stages and
   priorities are no longer board data, so areas are all there is."

3. **`:39-43` — the document names are wrong.**
   Lists `research.md / impact.md / plan.md / checklist.md / proof.md`. The real
   model is **seven types** — `research`, `files`, `plan`, `checklist`,
   `open-questions`, `post-implementation-report`, `proof` — and they are
   **folders**, not single files, so a ticket can hold several of a type.
   `impact` was renamed to `files`.

## Approach

Correct the three. While in there, cross-check the rest of the user-facing half
against shipped code the way DOC-007 did for the manual, because these three
were found incidentally rather than by an audit — there may be more.

Two useful constraints from DOC-007:

- **The manual is now the authority** on all three of these. Copy from
  `docs/manual/stages.md`, `profiles.md` and `documents.md` rather than
  re-deriving; they were fact-checked against `packages/core/src` and a live
  `get_doc_gates`.
- **Do not import FRD vocabulary.** README is user-facing.

The contributor half of README (Layout, Develop from source, manual MCP
registration, Verify end-to-end, Release) is out of scope — it is correct and
it is for a different reader.

- [ ] No claim that stages or priorities are editable.

- [ ] No remaining disagreement between README and the in-app manual on any
