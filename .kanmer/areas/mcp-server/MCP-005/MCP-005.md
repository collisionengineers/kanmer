## What

Stop registering the agent's MCP server as the installed `Kanmer.exe`. Ship it
as something that lives outside `%LOCALAPPDATA%\Programs\Kanmer` — a separate
binary, or a launcher shim that survives an update.

## Why

This is the root cause [[GUI-064]] managed the symptom of, and AGENTS.md §11
already names it as the real fix.

`connect.ts:37,51` registers `command = process.execPath` with
`ELECTRON_RUN_AS_NODE=1`, so an agent's MCP server **is** a process inside the
install folder. Two consequences, both bad:

1. **Updates used to fail outright.** The server memory-maps `icudtl.dat` and
   `v8_context_snapshot.bin` without `FILE_SHARE_DELETE`, so the uninstaller's
   `un.atomicRMDir` could not rename them and aborted — `uninstallFailed: 2`.
   GUI-064 fixed this by killing the server first, which works but is a race we
   chose to win rather than a race we removed.
2. **Every update still kills every live agent session.** FRD-021 accepts this
   as unavoidable and the app warns about it. It is only unavoidable *because*
   the server lives in the folder being replaced.

Move it out and both go away. The GUI-064 stop-and-verify code becomes belt to
that braces rather than the only thing standing between a user and a failed
update.

The original reason for `process.execPath` is good and must survive: **the
target machine needs no separate Node install**. Any design that quietly
requires one is a regression, not a fix.

## Approach

- Weigh the options against "no Node required" and "survives an update":
  a sidecar binary in a stable per-user location, a shim that resolves the
  current install at launch, or shipping a small standalone runtime.
- Whatever wins, existing registrations in every provider config
  (`connect.ts`'s provider table) have to migrate — a user who already ran
  Connect must not be left pointing at a path that changes.
- **Needs an ADR.** This changes how the product is delivered and how every
  agent host is told to launch it.

## Verification

- [ ] With the new registration, an agent MCP session is running and an update
      installs **without stopping it** — the session survives, or at minimum the
      install does not depend on killing it.
- [ ] A machine with no Node installed can still run the MCP server.
- [ ] An existing registration made by the old scheme is migrated, not broken.
- [ ] The `blocked:` lock probe over the install dir reads 0 with a live agent
      session — the measurement GUI-064 used, now expected to pass unaided.
