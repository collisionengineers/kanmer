## What

grok has a full plugin system that Kanmer does not use. Split out of [[MCP-009]].

Measured against the real CLI (`grok` 0.2.111):

- `grok plugin --help` → `list install uninstall … marketplace`
- `grok plugin install <dir> --trust` → `Installed 1 plugin(s)`
- `grok inspect` → `kanmer (user, enabled) 12 skills, 1 MCPs`

Kanmer currently treats grok as `configFile` + `copySkills`. That works, but it is
the fallback path for a host that has the real one.

## Why

Kanmer's `copySkills` route writes a skill tree into the project and relies on the
host discovering it. A plugin install is the host's own supported mechanism: it
handles the skills and the MCP server in one step, it is visible to
`grok plugin list`, and it is uninstallable by the same mechanism rather than by
Kanmer deleting directories it has to prove it owns — which is the exact problem
[[GUI-080]] exists to solve for the copy route.

One measured caveat that must be carried into the work: **`grok mcp list` is a
false oracle.** It reports "none configured" for servers that `grok inspect` shows
as active. Any verification here must use `grok inspect`, and any code that reads
grok's state must not trust `mcp list`.

## Approach

- Move grok from `register: configFile` + `copySkills` to the plugin install path,
  keeping disconnect symmetric.
- Note this interacts with [[GUI-079]]: grok currently shares `.mcp.json` and the
  `mcpServers.kanmer` key with Claude, and GUI-079 is moving grok off that shared
  file. Sequence after it, or fold the move into this ticket if GUI-079 has not
  landed — but do not do it twice.
- Every capability claim carries the command and its output ([[MCP-009]]'s rule).
