# Plan — MCP-018: make `plugin:check` prove isolated module resolution

## Objective

Change the existing plugin verification rail so it validates the exact installable Kanmer plugin outside the monorepo, proving the MCP server and lazy tool discovery resolve entirely from shipped payload bytes while retaining byte-for-byte bundle drift detection.

## Starting state

- `plugin:check` can execute an entry under the worktree and therefore borrow workspace paths/dependencies.
- The repository has canonical plugin build/check scripts and a committed generated MCP bundle.
- CORE-031 requires `plugin:check` as one step in the shared verification rail.

## Required changes

### 1. Map the canonical artifact contract

1. Read `package.json` scripts for `plugin:build`, `plugin:check`, and root verify.
2. Read the build/check scripts and plugin manifest(s).
3. Identify the exact installable payload list/root and the manifest-selected MCP command/entry.
4. Identify the existing fresh-build versus committed-byte comparison and preserve it.
5. Identify every environment/worktree assumption in the current check.
6. Confirm the generated bundle is never hand-authored.

### 2. Share payload metadata without duplicating policy

7. If build and check already share a payload/manifest helper, reuse it.
8. Otherwise extract one pure helper that returns installable files, plugin root, manifest data, and MCP relative entry path.
9. Keep provider-specific registration logic out of the helper.
10. Validate every selected path is relative and remains under plugin root after resolution.
11. Reject missing/duplicate/escaping payload entries before launching anything.

### 3. Preserve artifact drift comparison

12. Produce the fresh canonical bundle/payload in a temporary staging location or in the existing non-destructive check path.
13. Compare committed generated bytes/file list against the fresh result.
14. Report added, missing, and changed files deterministically.
15. Do not run `plugin:build` in a way that overwrites committed bytes before comparison.
16. Preserve the main-checkout-only build rule and actionable repair command.

### 4. Create isolated installation

17. Create an OS-temp parent whose name contains a space.
18. Create separate copied plugin root and unrelated empty child cwd.
19. Copy only the canonical installable payload, preserving required modes/relative layout.
20. Do not copy root `node_modules`, package workspaces, source packages, `.git`, `.kanmer`, or build caches.
21. Resolve copied manifest and MCP entry from the copied payload.
22. Assert copied realpaths remain outside repository root and entry remains inside copied plugin root.

### 5. Sanitize process environment

23. Start from a controlled allowlist/clean copy of required platform environment variables.
24. Remove `NODE_PATH`.
25. Remove `NODE_OPTIONS` development loaders unless a packaged runtime option is explicitly part of product behavior.
26. Remove repository/workspace variables that redirect module resolution.
27. Set noninteractive values and a deterministic locale/encoding where used by existing smokes.
28. Set child cwd to the unrelated empty directory.
29. Spawn executable and arguments directly without a shell.

### 6. Exercise the packaged MCP server

30. Reuse the canonical protocol smoke client/handshake code where possible.
31. Launch the copied manifest-selected entry.
32. Complete MCP `initialize`/initialized sequence.
33. Call `tools/list` and validate the expected non-empty/stable tool surface or canonical discovery assertion.
34. Optionally call one read-only orientation tool against a disposable root if the canonical smoke requires runtime/lazy imports.
35. Enforce a bounded startup/handshake timeout.
36. On timeout/error, terminate the child/process tree and report entry, cwd, environment differences, stdout, and stderr.
37. Close streams/client and await clean process exit.
38. Do not point the isolated server at the real board.

### 7. Prove the regression

39. Add a miniature fixture plugin/module that resolves an intentionally external dependency when run from its source checkout.
40. Run the fixture through the isolated checker and assert failure.
41. Assert the failure identifies unresolved/external dependency rather than silently borrowing root modules.
42. Add success coverage for the real built plugin.
43. Add path-with-spaces coverage.
44. Add missing-manifest/entry coverage.
45. Add timeout and child-termination coverage using a test fixture, not the real bundle.
46. Add cleanup assertions for success and failure.
47. If resolver-path instrumentation is needed, confine it to the test child and assert all non-built-in module paths remain under copied plugin root.

### 8. Wire the shared rail

48. Keep one canonical `plugin:check` package script.
49. Ensure CORE-031's `verify` calls it exactly once and does not call `plugin:build` first in a way that masks drift.
50. Ensure scripts tests cover checker helpers through the existing runner.
51. Do not add a separate GitHub Actions job.

### 9. Verification

52. Run scripts/checker unit tests.
53. Run `npm run plugin:check` from the normal main checkout.
54. Run it with repository cwd different from plugin/source paths where supported.
55. Run root typecheck/build/tests/verify.
56. Run the Windows PR workflow.
57. Confirm working tree remains unchanged after a passing check.
58. Deliberately alter a temporary copy/fresh fixture and prove drift or external dependency is detected without editing committed artifacts.
59. Run `git diff --check`.
60. Record isolated paths, manifest entry, handshake result, and negative fixture proof in the post-implementation report.

## Expected files

Modify the existing canonical plugin check/build metadata files named in `files.md`; add only a scripts test and miniature fixture/helper when absent. Generated bundle changes only through the canonical build command if a legitimate runtime dependency/build correction is required.

## Acceptance checks

- Check resolves entry from packaging metadata.
- Installable payload is copied outside the repo to a path with spaces.
- Child cwd is unrelated and resolution aids are sanitized.
- MCP initialize and tool discovery pass from copied bytes.
- No repository/workspace module is required.
- Negative external-dependency fixture fails.
- Committed-vs-fresh byte/file comparison remains active.
- Timeout, termination, diagnostics, and cleanup are deterministic.
- Root `verify` calls one `plugin:check` and no masking pre-build.
- Real installed plugin/board are untouched.

## Verification commands

Use exact repository scripts, including:

```bash
npm run plugin:check
npm test
npm run typecheck
npm run build
npm run verify
git diff --check
git status --short
```

Run `plugin:build` only through the documented main-checkout regeneration path when an intentional generated artifact update is required, then rerun `plugin:check`.

## Failure and deviation rules

- Stop if build/check payload definitions disagree; consolidate the metadata before adding isolation.
- Stop if isolated success depends on root/global packages; make runtime dependency ownership/bundling explicit.
- Do not weaken byte drift checks, hard-code a source entry, copy node_modules, use a shell, alter MCP semantics, or touch installed provider state.
- Do not hand-edit generated bundle bytes.
- Do not merge; hand off for review.

## Stop condition

Stop when `plugin:check` proves both artifact synchronization and a complete MCP initialization/tool-discovery run from a copied installable payload outside the repository with sanitized resolution state, the negative external-dependency fixture fails, root verification is green, and the PR is ready for independent review.
