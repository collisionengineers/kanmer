## What

Kanmer's Claude plugin install command **fails outright**, and the failure is
swallowed. Split out of [[MCP-009]], which measured it against the real CLI.

Three linked defects:

1. `pluginRoot()` returns `plugins/kanmer`, but the marketplace manifest lives at
   the **repo root** (`.claude-plugin/marketplace.json`). So:
   `claude plugin marketplace add …\plugins\kanmer` →
   `✘ Marketplace file not found at …\plugins\kanmer\.claude-plugin\marketplace.json`,
   exit 1. Pointed at the repo root instead it succeeds, and
   `claude plugin install kanmer@kanmer` then reports `✔`.
2. `connect.ts:152` swallows that non-zero exit into "plugin cmd skipped", so the
   user is never told.
3. `apps/gui/electron-builder.yml` ships only `plugins/kanmer` — **neither**
   marketplace JSON. The packaged app therefore has no local marketplace source
   at all, despite a comment claiming one. The v2 plan explicitly required both,
   so this is a regression against a written decision, not an oversight.

Two further disagreements found in the same audit, in scope here because they are
the same class:

- **Two marketplace names.** `.claude-plugin/marketplace.json` says `kanmer`;
  `.agents/plugins/marketplace.json` says `kanmer-plugins`. Both confirmed live.
- **Two bundled MCP paths** with different variables: `./mcp/claude.mcp.json`
  uses `${CLAUDE_PLUGIN_ROOT}`, `./.mcp.json` uses `${PLUGIN_ROOT}`. Whether
  `${PLUGIN_ROOT}` expands at all per host is unverified — check it, do not assume.

## Why

This is the blocker under "the plugin isn't helping as much as I hoped". The
marketplace path has never worked from the packaged app, and nothing said so
because the error was caught and relabelled.

Note the swallowing is the more important half. A command that fails loudly gets
fixed in a day; a command that reports "skipped" survives a release cycle.

## Approach

- Point the marketplace command at the directory that actually holds the
  manifest, verified by running it — not by reading paths.
- Stop swallowing a non-zero exit from an install command. Surface it.
- Ship the marketplace JSON(s) in the packaged app, or state with evidence why a
  packaged app cannot use a local marketplace and remove the claim instead.
- Reconcile the two marketplace names and the two `${…}_ROOT` variables, or
  document why both must exist.
- Follow [[MCP-009]]'s method: every capability claim carries the command and its
  output, and a probe needs a positive control.

Related but separately owned: [[MCP-011]] fixes the manifests' frozen `0.1.0`
version (which also freezes codex's cache path at
`…\kanmer-plugins\kanmer\0.1.0`).

## Verification

- [x] `claude plugin marketplace add` + `claude plugin install kanmer@kanmer`
      succeed from a clean profile, with the commands and output recorded.
- [x] The same works from the **packaged** app, not only the repo checkout.
- [x] A failing install command produces a visible error, asserted by a test with
      a deliberately broken path.
- [x] Marketplace names and plugin-root variables agree across every manifest and
      `providers.ts`, or the disagreement is documented with its reason.

## Outcome

Shipped in **PR #60**, squash-merged as `f5c370e` on 2026-08-17.
<https://github.com/collisionengineers/kanmer/pull/60>

**The fix is one line of arithmetic and a great deal of not hiding it.**
`marketplaceRoot()` is `pluginRoot()` minus `plugins/kanmer` — *derived* from it
rather than resolved by a second `app.isPackaged` branch, because two path
functions each independently correct about a layout are exactly what drifted
apart here. The invariant `marketplaceRoot()/plugins/kanmer === pluginRoot()`
is now stated in the code and pinned by a test that fails when the old argument
is restored.

**The swallow — the half the ticket called more important — was worse than
described, and is fixed in both places.** `installSkills` returns a
`{ note, failure }` outcome instead of a note string, so a failed install
command reaches the UI as `ok: false` carrying the exact failing command, which
`Settings.tsx` already renders as "Run this yourself:" with a copy button. That
is **FRD-012 AC-4**, specified since v2 and never honoured for the marketplace
hosts. The `copySkills` branch was swallowing the same way one branch over
(`connectAgent`'s `.catch()` → `skills failed: …` on an `ok: true` result); both
now report through the same channel.

**Three things found by running the commands rather than reading them:**

1. **codex's install command was missing entirely.** `codex plugin marketplace
   add` alone leaves the plugin `not installed` — codex's own listing says so —
   because its verb is `add`, and there is no `codex plugin install`. So a codex
   Connect delivered **no skills at all**, even with the root corrected. Fixed
   here; `codex exec` now reports all 12 `kanmer-*` skills. This is the skills
   half, so it does **not** pre-empt [[MCP-016]], which owns whether the plugin
   should keep advertising an MCP server codex cannot launch.
2. **The packaged app can carry a local marketplace — it is a packaging fix, not
   a product decision**, and that was established *before* the packaging was
   changed: a mirror of the proposed `resources/` layout was installed from by
   both hosts and a tool answered out of it. `extraResources` now packs both
   manifests beside the plugin, which the v2 plan
   (`docs/plans/kanmer-v2/phase-6-agents-connect/plan.md:30`) had required and
   `0f3bb03` shipped without, keeping only the comment that claimed it.
3. **The two marketplace names must stay different**, and the ticket's fifth
   defect was already closed. Different schemas, different hosts, no caller sees
   both, and a rename would relocate every existing codex user's plugin cache.
   What was missing was not agreement but a rail: `providers.test.ts` now pins
   each hard-coded `<plugin>@<marketplace>` string to the manifest that declares
   it, and `plugin:check` fails if the two names ever collapse into one. The
   `${PLUGIN_ROOT}` disagreement was fixed by [[MCP-011]] and was deliberately
   not reopened.

**Method.** ADR-0009's amended rule was the binding constraint throughout: every
install ran in an isolated profile with a control proving it empty, kept a
**negative control** (the old argument still exiting 1) so the pass is
attributable to the change, and was confirmed **by calling a tool** — never by an
install success line or a `plugin list`, which is the proxy that let this survive
three releases. Machine state was restored and the restore verified.

**Rails, each demonstrated failing on the defect it exists for:** the invariant
and the `ok:false` mapping (tests driven through the real `exec` against
subprocesses that really exit non-zero — a stub would let a genuine swallow
pass), the marketplace-name pins, `plugin:check` on both manifests and the
`extraResources` block, and `check-updater-package` on the packed artifact.

**Governing docs:** FRD-012 R2's two marketplace bullets rewritten with the
commands that established them, a third added for the packaged case, and MCP-013
removed from the open-work list. R6/R7 untouched (MCP-011's). No new ADR.

**Follow-ups:** [[MCP-016]] (untouched, still open), and two unrelated results
recorded in `proof`: a `jsdom` dependency added by GUI-065 after this merge, and
the pre-existing `kanmerGit.test.ts` Windows flake (GUI-085/GUI-089), shown to be
a flake and not chased.
