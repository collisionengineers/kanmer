## What

Connect shows **"Antigravity · register-only"**, which reads as "this host gets
less than the others". It does not — Antigravity has full project-level support.
The label means something narrower than it says.

## Why

The user is right, and the code says so. `providers.ts:374-388`:

```ts
id: "antigravity",
register: { kind: "configFile", configPath: ".agents/mcp_config.json", … },
install: { kind: "copySkills", skillsScope: "project", skillsDir: ".agents/skills" },
dispatch: false,
```

**Project-scoped MCP config and project-scoped skills** — written into the
project, exactly like the hosts that carry no warning. The in-repo comment even
notes `.agents/skills` is Antigravity's *primary* project location and is the
same tree opencode reads.

The only thing it lacks is **headless dispatch**, and the reason is recorded:
`agy -p` is known-broken piped (GH #318/#76).

But the badge is rendered from `dispatch` alone — `Settings.tsx:416`:

```tsx
{!p.dispatch && <span className="hint"> · register-only</span>}
```

So "cannot dispatch in the background" is being displayed as "register-only",
which in a panel headed *"Registers this project's board … and installs the
skills"* implies it does the first and not the second. It does both.

## Approach

- Say what is actually missing: something like "no background dispatch", not a
  term that reads as a capability tier.
- The flag is fine; the wording maps it to the wrong concept. Check whether
  `listProviders` should expose what a host *does* support (register / skills /
  dispatch) rather than a single boolean the UI has to interpret.
- While here: is `dispatch: false` still true? The comment is dated "v1" and
  cites upstream issues — worth a look before writing copy that outlives it.

## Verification

- [x] Antigravity's row no longer implies reduced project support.
- [x] Whatever replaces the label names the actual limitation, and matches
      whether the host appears in the "Dispatch to agent →" menu.
- [x] Connecting Antigravity still writes `.agents/mcp_config.json` **and**
      `.agents/skills` — the capability the old label denied.

## Outcome

Shipped in **PR #55** (`d1ef063`, squash-merged 2026-08-16), verified on merged
main — 257/257 GUI tests, typecheck clean, `check:manual` up to date.

**The ticket's premise was right, and the adjudication of the GUI-073/MCP-009
conflict proved it by measurement** (ten runs, positive controls, corroborated by
the probe MCP server's own process log). `.agents/skills/` and
`.agents/mcp_config.json` **are** read by `agy` 1.1.13 — functionally, not just
listed — so verification item 3 was never in doubt. What the adjudication added is
the condition nobody had: **the gate is a bound workspace folder**. A bare `agy`
binds to `default-cli-project`, whose record is `"projectResources": {}`, so there
is no folder to read `.agents/` from and cwd is irrelevant; only a flag on the
command line binds (`--new-project`, `--project <id>`, or `--add-dir`, which
persists nothing). Trust is not the gate, a git root does not auto-bind, project
existence does not bind, and a workspace MCP server never appears as a named
top-level tool — which is why a tool-list grep reads as a false negative.

So Kanmer writes **correct files into a session shape that never reads them**.
This ticket corrected everything Kanmer *says* about that:

- the "register-only" badge → "· no background dispatch", from the same
  `!p.dispatch` source as the dispatch menu, so the two cannot disagree;
- the Connect panel blurb, which claimed opencode and Antigravity "only read
  skills globally";
- `providers.ts`: the `dispatch` doc comment, the binding condition on the
  `.agents/skills` install, and the **refuted** `agy -p` justification
  (re-measured here: `PONG`, exit 0, piped — GH #318/#76 recorded as never
  fetched);
- `providers.test.ts`, which had locked the wrong claim into the suite;
- `docs/manual/connect.md`, which gained an "Antigravity: bind the folder"
  section with the flags and the tool-list warning.

`dispatch` stays `false` **deliberately** — flipping it without the binding would
put a host in the dispatch menu that cannot see the board it was just registered
with. **[[MCP-015]]** owns the binding, the plugin install path and the flip.
FRD-012 and ADR-0009 already carried the caveat ([[MCP-009]], `c81063e`) and were
cited, not re-amended.

**Follow-up filed:** [[GUI-088]] — `installSkills` returns at the marketplace
branch before `ensureAgentsBlock`, so Claude Code and codex never get the
