# Research — MCP-008 rescope: headless serve and Claude Desktop MCPB

## Why this addendum exists

The earlier MCP-008 research correctly proved that the standalone CJS server runs under plain Node with no Electron GUI or external `node_modules`, and that an MCPB manifest can request a directory and pass it through `--root`. Its remaining questions were written before the MASTERPLAN reconciliation and are now stale in several material ways.

## Resolved roadmap changes

- **MCP-005 is archived and no longer blocks this ticket.** Its premise—that the installed server payload had to be relocated to make a host registration portable—was refuted. MCPB is independently packaged and consumes the existing standalone CJS build.
- **MCP-010 is Done.** No-root discovery now finds a canonical board worktree from repository/worktree cwd. Claude Desktop itself has no useful project cwd, so the MCPB still uses an explicit user-selected board root; the picker description must say to choose the folder that directly contains `.kanmer` (normally `<repo>/.worktrees/kanmer`), not merely the repository root.
- **MCP-025 is a separate Streamable HTTP transport.** MCPB uses the local stdio Node server. These are complementary install/transport paths; MCP-008 must not add another network transport or make the MCPB depend on HTTP.
- **CORE-031/036 define the verification/release rails.** `npm run verify` is the PR rail; the tag workflow validates published assets. MCPB build/check/release integration must plug into those rails rather than create a separate release process.
- **GUI-092/093 own publisher correctness.** MCP-008 may add the MCPB asset to the expected release set after their single-pack/resilient-publish work, but it must not absorb or duplicate their fixes.
- **A square root `icon.png` already exists** and is 1254×1254 RGBA. Reuse/copy it into the MCPB staging area rather than create a competing icon asset.

## Settled package decisions

### Format and location

- Source manifest lives at `mcpb/manifest.json` (or a clearly named template in that directory if the MCPB tool requires a generated version).
- Generated staging lives under `dist/mcpb/staging/` and the distributable is `dist/mcpb/kanmer-<version>.mcpb`.
- Generated staging/archive are ignored; source manifest/build scripts are committed.
- The bundle contains:
  - `manifest.json` with the current repository version;
  - `server/kanmer-mcp.cjs`, copied from the fresh standalone build;
  - `icon.png`, copied from the root canonical asset.

### Runtime and platform

- `server.type` is Node and `entry_point` is the bundled CJS server.
- `compatibility.platforms` is **`win32` only for v1**. The payload may be portable, but macOS has not been executed and optional watcher behavior is unverified. Support claims follow evidence.
- Runtime minimum is Node 20, matching the standalone build target and the current repository contract. The real Claude Desktop acceptance must prove that its MCPB runtime satisfies this requirement.
- `@anthropic-ai/mcpb` is a pinned development dependency so `npm ci` can reproduce the build in CI/release. Do not require a global binary.

### Board selection and scope

- One installed MCPB instance configures **one board root**. `user_config.board_root` is required, type `directory`, and interpolated into `--root`.
- The picker/help text says: select the directory that directly contains `.kanmer`; for a GUI-created project this is normally `<repo>/.worktrees/kanmer`.
- A repository root that does not itself contain `.kanmer` is intentionally rejected by explicit `--root`; MCP-010 discovery does not override an asserted flag.
- Multi-board support in one process/installation is out of scope and becomes a separate ticket only after observed demand.

### Tools, prompts and skills

- The MCPB exposes the existing MCP tools and registered MCP prompts. It does **not** install the Kanmer agent skill tree into Claude Desktop.
- Manifest tool metadata must be generated/verified from a live `tools/list` call against the freshly built standalone server, not maintained as another hand-written roster.
- Refactor/reuse the existing discovery smoke client if needed; do not copy a tool-name array into the build script.
- Documentation states the workflow-guidance gap: MCPB users receive tools/prompts; Claude Code plugin users receive the full skills.

### Headless behavior

- The board worktree must already exist. MCPB/headless mode does not create the GUI’s canonical board worktree.
- All file-backed reads/writes/gates work with the GUI closed.
- GUI-owned periodic Git auto-sync does not run while the GUI is closed. The user is responsible for opening the GUI or committing/pushing board changes through their normal Git workflow.
- This ticket documents that limit; it does not add a headless committer, daemon or Git status block.

### Build, verification and release

- Add `mcpb:build` and `mcpb:check`; `mcpb:build` first ensures a fresh standalone build exists, generates the current manifest/tool metadata, stages payload/icon and invokes the pinned local MCPB packer.
- `mcpb:check` rebuilds into a temporary directory, unpacks/inspects both produced bundles and compares normalized manifest plus payload/icon bytes. Do not require archive byte identity if the packer writes nondeterministic timestamps.
- Extend the shared distributed-bundle sync rail so the plugin copy and MCPB server payload both match the same fresh standalone output.
- Add a durable isolated-Node/headless smoke: copy the server into a temp directory with no reachable workspace `node_modules`, create/use a disposable format-3 board, perform `initialize`, `tools/list`, `get_status` and one safe read/write round trip, and close cleanly.
- The MCPB becomes a GitHub release asset. `release.mjs` remains the publisher and builds it once; `verify-release-assets.mjs`/CORE-036 tag workflow require and hash-check it alongside installer assets. No manual out-of-band publishing path is the authoritative release process.
- Release integration must be sequenced with GUI-092/093 so the publisher still packages once and handles verification/repair consistently.

## Real acceptance

A named human/operator or verifier with real Claude Desktop performs the final install test after deterministic rails pass:

1. build the exact release candidate MCPB;
2. install it through Claude Desktop’s supported local-extension flow;
3. select a real canonical board worktree;
4. keep the Kanmer GUI closed;
5. invoke `get_status`, read a ticket, perform one controlled write, and verify the file changed on the selected board;
6. restart Claude Desktop and prove the configured board still works;
7. verify no GUI process is required and no unintended board/project is selected;
8. uninstall the MCPB and record cleanup.

The proof records Claude Desktop version, OS, MCPB SHA-256, selected board root, server identity, raw tool results and post-write board diff. A manifest validation or extension listing alone is not acceptance.

## Non-goals confirmed

No server relocation, Electron dependency, HTTP transport, multi-board server, headless Git sync, worktree creation, MCPB signing/directory submission, macOS claim, skill installation into Claude Desktop or new MCP tools.
