# FRD-012 — Connect: agent registration & skill install

## Overview

Connect registers the project's board with an agent host's MCP client and installs the skill roster — per provider, idempotently, with a copy-paste fallback when a command fails. Five providers: Claude Code, codex, opencode, Grok CLI, Antigravity.

## Requirements

- R1. **Registration matrix (end-state):** Claude Code — `claude mcp add kanmer -s project` (project `.mcp.json`, **Claude's alone**; stale user-scope cleanup retained). **codex — project config file** `<root>/.codex/config.toml` (`[mcp_servers.kanmer]`, TOML merge preserving unknown keys, idempotent unmerge), with the *project must be trusted* caveat surfaced in the UI, plus legacy cleanup `codex mcp remove kanmer-<project>` on reconnect. opencode — `opencode.json` merge (as shipped). **Grok — `<root>/.grok/config.toml`** (`[mcp_servers.kanmer]`, the same TOML merge as codex; grok's native project scope and its highest-priority MCP source — it no longer writes `.mcp.json`, see ADR-0013). Antigravity — `.agents/mcp_config.json` (as shipped).
- R1a. **One host, one file.** Kanmer registers a host only in a file that host alone owns, and unregisters only from files it owns (ADR-0013). No two providers may write the same path. Whether a config still registers Kanmer is answered by the provider that owns the file, tri-state, so "cannot read this file" stays distinct from "not registered".
- R1b. **Machine-wide legacy sweep.** The Connect panel lists every `mcp_servers.kanmer-*` left in the global `~/.codex/config.toml` by pre-ADR-0007 versions, classified against the project each one names, and drains the ones whose project has a registration codex will actually load — one confirmation, a no-op on the second run (ADR-0010). Entries whose project has **no** project-scoped replacement, or whose folder codex does not trust, are reported and **never removable**: that entry is the project's only working registration, and the user is told to open that project and Connect it first. Kanmer never writes another project's config files, and never rewrites the global TOML — removal is delegated to `codex mcp remove`. This, not per-project reconnection, is what drains the pile (ADR-0007, amended).
- R1c. **Registration files stay gitignored, not committed (GUI-083).** `.codex/config.toml` is per-project config a team could legitimately share — ADR-0007 is precisely about project scope being the right place for it — but that is a question of *where* the registration lives, not of whether *today's* file content is fit to commit. Every registration file this matrix writes (`.mcp.json`, `.codex/config.toml`, `.grok/config.toml`, `opencode.json`, `.agents/mcp_config.json`) is built from the same `Invocation` — `command` and `args` are this machine's absolute paths to the local Kanmer install, never a portable form. Committing one would be exactly as inert to a teammate as a checked-in `.mcp.json` hardcoding a different machine's `C:\Users\<other>\...` path: it silently fails to register anything and reads as if it should work. So all five are gitignored, symmetrically, for this one reason — not project-vs-personal-scope, which ADR-0007 already settled in project scope's favor. If a future change makes `Invocation` portable (e.g. a relative or env-resolved command), this call is worth revisiting; it is not settled for all time, only for what these files contain today.
- R2. **Skill install matrix (end-state).** Corrected 2026-08-16 against the installed binaries per ADR-0009's method clause; each divergence between this matrix and shipped code names the ticket that owns closing it.
  - **Claude Code** — plugin marketplace, **two commands**: `claude plugin marketplace add <marketplace root>` then `claude plugin install kanmer@kanmer`. The marketplace *root* is the directory holding `.claude-plugin/marketplace.json` — the repo root, **not** `plugins/kanmer`, which is only what that manifest points at. Connect passed the plugin directory until MCP-013, so every install exited 1 with `✘ Failed to add marketplace: Marketplace file not found`, and the non-zero exit was relabelled "plugin cmd skipped" on a result still flagged `ok`, so the panel showed `✓ Connected`. Both halves fixed: `connect.ts` derives `marketplaceRoot()` from `pluginRoot()` (the invariant `marketplaceRoot()/plugins/kanmer === pluginRoot()` holds in dev and packaged alike), and a failed install command now yields `ok: false` with the failing command as AC-4's copy-paste fallback.
  - **codex** — plugin marketplace, same root, also **two commands**: `codex plugin marketplace add <marketplace root>` then `codex plugin add kanmer@kanmer-plugins`. codex's verb is `add`; there is no `codex plugin install`. The second command was missing entirely until MCP-013, so `codex plugin list` reported `kanmer@kanmer-plugins  not installed` after a "successful" Connect and no skills arrived. Its marketplace name is **`kanmer-plugins`**, taken from `.agents/plugins/marketplace.json` — *not* Claude's `kanmer`. The two names legitimately differ (different schemas, different hosts, and renaming codex's would relocate every existing user's plugin cache at `~/.codex/plugins/cache/kanmer-plugins/kanmer/<version>`); any shared "install the plugin" copy that assumes one is wrong for the other, so `providers.test.ts` pins each hard-coded `<plugin>@<marketplace>` string to the manifest that declares it. Note the install delivers **skills only** — established by calling for them, not by a listing: `codex exec` in a fresh `CODEX_HOME` reported all 12 `kanmer-*` skills. codex cannot run a plugin-supplied MCP server that lives inside the plugin — see R6 — so a codex user's board comes from Connect's `<root>/.codex/config.toml` entry (R1), never from the plugin. Since **MCP-016** the plugin no longer *advertises* one either: `.codex-plugin/plugin.json` declares no `mcpServers` key and the plugin ships no root `.mcp.json`, so "skills only" is now what the manifest says rather than only what the host manages.
  - **Both marketplace hosts, packaged.** `extraResources` ships `plugins/kanmer` **and both marketplace manifests**, at paths that reproduce the repo-root layout under `resources/` — so each manifest's `./plugins/kanmer` resolves and `marketplaceRoot()` lands on `resources/`. Until MCP-013 only the plugin directory was packed, beside a comment claiming a local marketplace source, so the packaged app had none; the v2 plan had required both (`docs/plans/kanmer-v2/phase-6-agents-connect/plan.md:30`). Established against the binaries before the packaging was changed, by installing from a mirror of the proposed `resources/` layout and **calling a tool** that answered out of it (`server.build: "plugin"`, `server.path` inside the mirror, the project's real ticket count). `check-plugin-sync.mjs` asserts the three entries in the electron-builder config; `check-updater-package.mjs` asserts them in the packed artifact.
  - **opencode** — project-scoped copy to its native `.opencode/skills/` directory. opencode has no plugin installer at all, so the copy is a genuine necessity rather than a fallback. Although it also discovers `.claude/skills/` and `.agents/skills/`, Kanmer uses the provider-specific directory so OpenCode's own project copy does not also become a duplicate roster discovered by Codex. Antigravity's remaining `.agents/skills/` copy is explicitly outside this isolation.
  - **Antigravity** — project-scoped copy to `.agents/skills/`, plus `.agents/mcp_config.json`. Both **are** read by `agy`, but **only in a session bound to a workspace folder**, and Kanmer establishes no binding today, so the write is correct and currently inert. Antigravity can also take the plugin directly (`agy plugin install`), but that delivers to `~/.gemini/config/plugins/` — global, which cuts against ADR-0007. Since **MCP-016** that route delivers **skills only** as well (`✔ skills : 12 processed`, `- mcpServers : skipped (not found)`); it never delivered a working server, and its entry — also named `kanmer` — collided by name with the `.agents/mcp_config.json` one, which is the trap R6 records. Owner of both the binding and that choice: **MCP-015**.
  - **Grok** — `.agents/skills/` serves grok too, so its separate `.grok/skills` write is redundant, and grok can take the plugin outright (`grok plugin install <dir> --trust`). Note `grok inspect` is grok's oracle; `grok mcp list` reports "none configured" for servers that are active. Owner: **MCP-014**.
  - OpenCode's `.opencode/skills/` copy is intentionally isolated. `.agents/skills/` remains Antigravity's destination and is also readable by grok, subject to Antigravity's binding caveat; grok's separate `.grok/skills/` write remains MCP-014's concern. All copies are stamped (`.kanmer-skills-version`) with the existing update-offer flow; note that a marketplace host reports no installed version, so the update offer does not apply to Claude Code or codex.
- R2a. **A skill install is a reconciliation, not an overlay.** The stamp records the bundled version on line 1 and, below it, the **roster** — the skill folders Kanmer wrote to that destination. Install replaces each owned folder **wholesale** (so a file the bundle has dropped or renamed cannot outlive it) and removes any roster-recorded folder the bundle no longer ships. Wholesale replacement discards local edits inside a Kanmer-owned skill folder; that is accepted under ADR-0009's "install-time copies", and Connect therefore **names the folders it replaced** in its output rather than deleting silently. Skills Kanmer did not write are never touched: the roster is the only deletion authority, never a name prefix. A stamp that predates the roster means "ownership unknown" and must make Kanmer delete less, not more. One **closed** tombstone list of two paths retired by `130f837` (`kanmer-import`, `kanmer-research/assets/impact-template.md`) repairs installs made before the roster existed; **nothing is ever added to it** — every later retirement is the roster's job, and a growing list would be a second source of truth about what Kanmer owns.
- R3. The **AGENTS.md managed block** is written for every provider — the universal orientation layer (ADR-0009), no longer anyone's sole delivery. Idempotent, marker-delimited, verified by `verify-agents-block`.
- R4. Disconnect reverses exactly what connect **wrote** (config entries, skill copies, never the AGENTS block without asking) — which means the recorded roster, not the currently-bundled names: a skill retired since that install was written by connect and must be removed by disconnect. OpenCode owns `.opencode/skills/`; Antigravity owns `.agents/skills/`; disconnecting either removes only that provider's destination and leaves the other byte-for-byte intact. If a future provider shares a destination, the copies are retained while **any** host writing that directory is still registered; ADR-0009 makes the roster's atomicity a stated constraint, so a half-removed roster breaks a connected host. **And nothing else:** "what connect wrote" is scoped by ownership (R1a), so disconnect can never remove another host's registration, and it does not reach into a file this host no longer owns to undo what an older Kanmer wrote there.
- R5. **Provider capability claims follow ADR-0009's method clause** — established against the installed binary, never inferred from the absence of evidence, with the command and its output recorded; a probe needs a positive control, and a positive control is not sufficient, because the mechanism must be verified rather than a proxy for it. The rule is stated once, in ADR-0009, and is **not** paraphrased here: an earlier version of this requirement carried the wrong lesson ("re-verified against current host docs at implementation time" — a staleness reading of a failure that was never about staleness), and it carried it because the rule had been copied instead of referenced.

- R6. **Plugin-install runtime matrix (MCP-011).** The desktop Connect path launches the server with `process.execPath` and `ELECTRON_RUN_AS_NODE=1` precisely so a machine needs no separate Node. A *plugin* install cannot statically name that binary — the plugin is copied into the host's own cache with no knowledge of where, or whether, Kanmer is installed — so what each host can express differs, and the answer is recorded here with the command that established it rather than left implicit. Established 2026-08-17 against `claude` 2.1.233, `codex` 0.147.0, `grok` 0.2.111, `agy` 1.1.13, each by **calling a tool through a real install** (per R5, a tool listing is a proxy; the call is the mechanism).

  | Install path | Reaches the Electron binary? | Established by |
  |---|---|---|
  | Desktop **Connect** | Yes, always | `serverInvocation` — `process.execPath` + `ELECTRON_RUN_AS_NODE=1` |
  | **Claude Code** plugin | **Yes, on opt-in.** `"command": "${KANMER_NODE:-node}"`; Node on PATH is the default, `KANMER_NODE` overrides it | `claude plugin install kanmer@kanmer`, then `KANMER_NODE=<Kanmer.exe> claude -p` calling `mcp__plugin_kanmer_kanmer__get_status` → answered, `electron: 31.7.7` |
  | **grok** plugin | **Yes, on opt-in.** Same file, same form | `grok plugin install <dir> --trust`, then `grok -p` calling `get_status` → `…\.worktrees\kanmer ancestor-worktree true 151` |
  | **codex** plugin | **n/a — no server is advertised** (MCP-016). Skills only | `codex plugin add` into a fresh `CODEX_HOME`, then `codex exec` asked to call `get_status` → `NO_KANMER_MCP_TOOL`, with `codex mcp list` now empty |
  | **antigravity** (`agy`) plugin | **n/a — no server is advertised** (MCP-016). Skills only | `agy plugin install ./plugins/kanmer` → `✔ skills : 12 processed`, `- mcpServers : skipped (not found)`; a session bound to a Connect-free folder finds no `kanmer` server |

  Three things the matrix must state plainly, because each is a way the product looks fine and is not:

  1. **There is one bundled MCP config, not two, and the surviving one is host-specific.** `mcp/claude.mcp.json` (Claude Code, grok) uses `${CLAUDE_PLUGIN_ROOT}` and must **not** set `cwd` — a relative `cwd` collapses grok's handshake outright. `plugin:check` pins that shape, and separately asserts that `.codex-plugin/plugin.json` declares no `mcpServers` and that no `plugins/kanmer/.mcp.json` exists.

  2. **MCP-016: the plugin stops advertising an MCP server on codex and `agy`.** It was never a working feature to withdraw — the entry has not launched on any release — and it is redundant even in principle, because Connect already writes the working codex registration (`<repo>/.codex/config.toml`, absolute paths, `--root` pinned). So codex and Antigravity users get **skills from the plugin and MCP from Connect**, and nothing anyone relies on changes. Three findings support it, each measured:
     - **Neither host expands any `${…}` token** in a plugin's MCP config — `${PLUGIN_ROOT}`, `${CODEX_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_ROOT}` and `${VAR:-default}` each tried beside a variable-free control that *did* launch — and codex passes the child no `PLUGIN_ROOT`.
     - **It is not rescuable by editing the manifest.** `"cwd": "."` makes codex *start* the server, but discovery then runs from `~/.codex/plugins/cache/kanmer-plugins/kanmer/<version>` and correctly reports no board. **Locating the script needs cwd = the plugin root; finding the board needs cwd = the workspace; codex expresses only one.** `agy` is worse: it reads `.mcp.json` at the plugin root **regardless of what a manifest points at** (measured — it reported `source: "claude-code"` while copying the root `.mcp.json` verbatim) and joins the relative path to the **session** cwd, `Cannot find module '<session cwd>\mcp\kanmer-mcp.cjs'`.
     - Therefore **two removals, not one**: the manifest key stops codex, the deleted file stops `agy`, and either alone leaves the other host advertising it.

     What would bring it back is written down rather than remembered: a host that expands a plugin-root token in `args` *while* leaving the working directory at the workspace — i.e. one that lets a plugin locate its own script without moving board discovery into the plugin cache. Short of that, the entry can only ever be a listing.

  3. **A tool listing is not a launched server — on either host, and the two hosts fail differently.** `codex mcp list` printed the entry as `enabled` for a server that gave the agent zero tools; that is the proxy that hid this defect originally and misled MCP-009. On `agy` the trap is sharper still: the plugin's entry and Connect's `.agents/mcp_config.json` entry are **both named `kanmer`**, so probing inside a connected project returns a healthy board from *Connect's* server and reports the plugin's as working. Any check of this requirement must call a tool, and on `agy` must call it from a folder with no Connect registration.

- R7. **The plugin does not pin a board.** Since ADR-0012 the server discovers it, so an absolute `--root` — which cannot survive a different machine or user account — is not merely unnecessary but wrong. Verified by running it: a plugin-installed server in a linked worktree resolved `rootSource: "ancestor-worktree"` with 151 tickets and no `--root`. `plugin:check` fails if `--root` reappears in `mcp/claude.mcp.json`, the one MCP config the plugin still ships (R6.2). This says nothing about *Connect's* registrations, which are per-project, absolute and correctly `--root`-pinned (R1, R1c) — the constraint is on what a plugin copied into a host's global cache may assume, not on what a project-scoped file may state.

## Acceptance criteria

1. Connect codex twice: one `[mcp_servers.kanmer]` entry in the project file, zero new global entries, legacy `kanmer-<project>` gone from `~/.codex/config.toml`.
2. Connect opencode and Antigravity: opencode discovers the roster from `.opencode/skills/` and Antigravity from `.agents/skills/`; disconnecting either leaves the other's tree unchanged. For opencode, `opencode debug skill` lists the native-directory copy. For Antigravity the tree is read **only in a workspace-bound session**, so the criterion is checked as `agy` bound to the project folder, and it is checked by **invoking a skill and calling the MCP server's tool** — not by grepping a tool listing, in which a connected workspace server appears only as the generic `call_mcp_tool` / `list_resources` / `read_resource` triad. Kanmer does not bind a workspace today, so this criterion cannot pass for Antigravity until **MCP-015** lands; it is stated as the end state, with that dependency named rather than a passing test implied.
3. Every merge/unmerge is pure and unit-tested (unknown keys preserved, idempotent, byte-stable re-merge).
4. A failed command yields the exact copy-paste fallback (shipped behaviour retained).
5. Install a bundle, retire a skill from it, install again: the retired skill is gone from the destination, a user-authored skill beside it survives byte for byte, and Connect's output names what it replaced and what it removed. Disconnect after a retirement leaves nothing behind either.
6. Connect Claude, then connect **and disconnect** Grok: Claude's `.mcp.json` is byte-identical afterwards, and a Claude-only project never reports Grok as connected.
7. Run the legacy sweep against a global config holding two `kanmer-*` entries, one of whose projects has reconnected and one of whose has not: the first is offered pre-selected, the second is shown as a warning **with no way to remove it** and text naming the project and telling the user to Connect it first. Run it again: the removed one is gone, the held-back one is reported unchanged, and nothing else in the global file changed.

## Upgrade note — Grok users reconnect once

Grok's registration moved from the project `.mcp.json` to `<root>/.grok/config.toml` (ADR-0013), because `.mcp.json` is Claude's file and sharing it meant grok's disconnect deleted Claude's registration. **Kanmer does not migrate existing grok registrations automatically** — rewriting another host's file is the defect, not the fix. Anyone who connected Grok before this release should open the project and click **Connect** once. Nothing breaks in the meantime: grok still reads the old `.mcp.json` entry through its compatibility layer, so the worst case is a stale duplicate.
