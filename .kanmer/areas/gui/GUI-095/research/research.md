# Research — GUI-095: Cloudflare Tunnel remote access in the GUI

## Question

What current GUI, MCP remote-access, project identity, persistence, and verification surfaces must this ticket extend so a secure Cloudflare named-tunnel workflow is per-project, multi-project safe, and provider-neutral without duplicating transport or secret logic?

## Findings

- The GUI is currently a multi-project board shell, not a remote-access manager. apps/gui/src/main/index.ts keeps an in-memory contexts map keyed by canonical source-root projectId; each context has sourceRoot, boardRoot, a KanmerStore, watcher, and Git sync state. openProject() runs ensureBoardWorktree(), constructs the store on boardRoot with repoRoot: sourceRoot, records only the recent-project path, and starts a watcher. This is the source/board-root split that remote configuration must preserve.

- Persistence is only app-global settings.json in apps/gui/src/main/settings.ts. It stores theme, recent project paths, open tabs, UI preferences, and Git sync settings; there is no project registry record, schema migration, optimistic version, atomic write, or remote settings namespace. writeSettings() uses direct writeFileSync. A remote manager therefore needs an explicit schema/version layer and an app-owned data location while reusing the existing settings conventions rather than writing into project/board files.

- The existing Settings UI is a modal for the active project. apps/gui/src/renderer/src/components/Settings.tsx has Board, Profiles, Appearance, Git, and Connect tabs. ConnectSection only registers/disconnects AI hosts and skill copies through the active ProjectClient; it has no project overview, remote lifecycle, status subscription, doctor, token delivery, or per-project identity selection. GUI-095's “every registered project” requirement cannot be satisfied by adding a few fields to the current active-project Connect row; it needs a machine-level remote-access surface fed by the open/registered project set.

- The preload/IPC bridge is named and project-scoped, but has no remote channels. apps/gui/src/shared/ipc.ts defines CH and KanmerApi; apps/gui/src/preload/index.ts maps each method to ipcRenderer.invoke and event listeners. main/index.ts registers handlers without sender/frame/schema validation beyond individual store methods. The new surface must add named, narrow, project-fingerprint-bound operations and an unsubscribe-capable status event, without exposing generic IPC, ipcRenderer, filesystem, process, shell, or secret-store access.

- BrowserWindow security relies on Electron defaults rather than explicit options. createWindow() sets sandbox: false and a preload but does not explicitly set contextIsolation or nodeIntegration; Electron 31.3.0's installed declarations document defaults of context isolation enabled and node integration disabled. The implementation should make the intended security posture explicit or test the defaults, and must keep process/secret work in main.

- The pinned Electron 31.3.0 API exposes safeStorage.isEncryptionAvailable(), encryptString, decryptString, and getSelectedStorageBackend() (backend values include basic_text, gnome_libsecret, kwallet*, and unknown). It also exposes setUsePlainTextEncryption; this is an unsafe fallback and must not be enabled. The ticket's secure-storage policy can be implemented without a new native dependency, but availability/backend checks must happen after app readiness and fail closed for unavailable or basic_text storage.

- MCP-021 provides the canonical provider-neutral tunnel contract in packages/mcp-server/src/tunnels/types.ts: TunnelAdapter.doctor/start/getStatus/stop/getDiagnostics/subscribe, validated loopback TunnelTarget, normalized states, non-secret fingerprints/generations, and a TunnelProcess with optional provider-owned checkReadiness. GUI code must call this boundary rather than reimplementing cloudflared or accepting provider-specific YAML/args.

- The Cloudflared adapter in packages/mcp-server/src/tunnels/cloudflared.ts validates executable and protected credential references, validates the exact HTTPS hostname and loopback /mcp origin, generates a closed ingress config with a terminal 404, runs direct spawn with shell:false and an allowlisted environment, owns the PID/process tree, buffers redacted diagnostics, and performs bounded graceful/forced cleanup. cloudflared-config.ts, cloudflared-validate.ts, readiness.ts, and supervisor.ts are the reusable provider lifecycle/config/doctor seams; GUI must pass references and safe target data only.

- MCP-025/026/027 boundaries are separate from the GUI: http.ts owns Streamable HTTP/session lifecycle, http-auth.ts owns bearer generation/verifier/rotation, http-secret.ts owns protected token-file material, and http-diagnostics.ts redacts error text. remote-host.ts composes HTTP plus TunnelSupervisor, requires an authenticated local verifier callback, binds one project per host, reports local/provider/public-verification dimensions, and closes HTTP before the tunnel. remote-cli.ts demonstrates the protected local initialize/DELETE handshake and passes only verifier metadata to the tunnel. GUI should invoke/adapt this canonical host/doctor path and keep raw bearer bytes in main only.

- The project fingerprint contract is in packages/mcp-server/src/project-identity.ts: canonical board root, format, and repo root are hashed into kanmer-proj-v1:<sha256>. The GUI currently exposes only source-root projectId and board-root metadata in OpenProjectResult; it does not calculate or return the MCP fingerprint. A project-scoped remote record must bind full identity (board root, source/repo root, format/fingerprint) and reject moved/wrong projects instead of keying solely by path.

- Application lifecycle is explicit: app.on("window-all-closed") quits non-macOS, before-quit only runs the updater guard, and will-quit closes board watchers and kills dispatches. There is no tray/background remote owner. GUI-095 must hook true application quit to stop every GUI-owned remote host with a bounded deadline, while renderer reload/window close must not kill a host unless the existing platform lifecycle actually quits.

- Existing updater behavior matters to child ownership. FRD-021 and main/updater.ts state that install may terminate MCP sessions under the install directory; update restart is guarded in the renderer and main refuses unless the update is downloaded. Remote manager cleanup must be coordinated with true quit/update paths and must not assume renderer state or a persisted connected/PID flag.

- The planned verification files scripts/verify.mjs and .github/workflows/pr.yml are absent from this checkout; root package.json currently verifies through npm test, workspace typechecks, build/smoke scripts, and standalone scripts. GUI-095 should wire its focused tests/build into the existing scripts or add the shared rail only under an explicit follow-up, not silently assume those files already exist.

- Governing requirements are explicit in FRD-025/ADR-0017: loopback-only Streamable HTTP /mcp, mandatory bearer before parsing/session work, one project per host, distinct listener/auth/session/tunnel/remote-handshake health, guarded secret rotation, safe project fingerprints, provider-neutral adapters, Cloudflare named-tunnel first, no account/DNS provisioning, no Quick Tunnels, no executable downloads, no remote dispatch, no OAuth, and no additional provider UI here. GUI-104 is the separate OpenAI Secure MCP Tunnel workflow.

## Implications

- Add a main-process remote-access subsystem (schema/versioned settings, safeStorage-backed bearer records, manager/queues, canonical host/doctor adapter, redacted events) and a narrow shared/preload API. Keep all secrets/processes/doctor calls out of renderer and project/board files.
- Treat the GUI's source-root projectId, board root, repo root, and MCP projectIdentity fingerprint as different identity values; persist the full fingerprint and current path metadata, and support explicit reconciliation only after a fresh exact match.
- Build a machine-level overview over registered/recent/open projects, with one runtime record per fingerprint, bounded auto-start concurrency, isolated failures, and generation/version checks. Active-project Settings can host navigation/details but cannot be the sole data source.
- Reuse remote-host.ts, TunnelAdapter, http-auth.ts, and MCP-027 doctor contracts through a main-only integration boundary. Do not spawn cloudflared from the renderer, duplicate ingress validation, or pass raw bearer/provider credentials via argv/env/logs.
- Make security defaults observable: reject unavailable/basic_text safeStorage, set/test explicit context isolation and node integration posture, use sender/frame/unknown-field validation, and return only allowlisted DTOs. A one-time generated/rotated token response is the sole raw-token crossing.
- Wire focused main/preload/renderer tests and a fake-provider Electron smoke to existing workspace commands. Include multi-project concurrency/isolation, stale generation, missing/moved/wrong fingerprint, secure-storage failure, token-delivery/clipboard cleanup, renderer reload, quit/update cleanup, redaction, accessibility, and no-MCP-surface-change checks.
- Preserve the Cloudflare-only scope and link OpenAI profile lifecycle to [[GUI-104]]. Keep MCP-028 as the integrated remote disposable-client proof; GUI-095 should stop at review-ready implementation and evidence.

## Open questions

The plan must choose exact GUI manager/storage module paths and the concrete adapter/doctor invocation seam after checking current build boundaries; those are implementation decisions, not user decisions.
