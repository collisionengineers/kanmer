## What

Skill installation is an **overlay**. It copies the current bundle over whatever
is already there and removes nothing, so a skill Kanmer has deleted from its own
roster survives in every project that ever installed it — indefinitely, and
invisibly.

Found the hard way: `kanmer-import` was folded into `kanmer-setup` and deleted
from the source tree in `130f837`. The installed copy stayed until the operator
deleted it by hand.

## Why

Three places, and they fail together.

**1. Install is a pure overlay.** `installSkills`
(`apps/gui/src/main/connect.ts:163`):

```ts
await cp(join(pluginRoot(), "skills"), dest, { recursive: true });
```

No prune, no diff. A retired skill is simply not mentioned, so it stays.

**2. "Update skills" cannot fix it either.** `updateSkills`
(`connect.ts:213`) calls the same `installSkills`. The affordance that exists
precisely for "my skills are out of date" reproduces the bug.

**3. Even *disconnect* misses it.** `removeBundledSkillsOnly`
(`connect.ts:99-114`) enumerates the **currently bundled** skill folders and
removes those names from the destination. A skill that is no longer bundled is
not in that list, so it is never removed — not on update, and not on the one
operation whose entire job is to leave nothing behind.

The roster is therefore only ever additive across the product's whole lifetime.

## The constraint that makes this non-trivial

**`rm -rf` then re-copy is wrong.** The destination is a shared directory:
`.claude/skills/` in this repo holds `run-kanmer`, which is the operator's own
skill and nothing to do with Kanmer. Protecting exactly that is why
`removeBundledSkillsOnly` is roster-driven in the first place.

So the fix needs a record of **what Kanmer previously installed**, not of what
it currently ships. `SKILLS_VERSION_FILE` (`.kanmer-skills-version`,
`providers.ts:66`) is already written into the destination and already read back
by `skillsStatus` — it is the natural place to carry the installed roster
alongside the version.

## Not a duplicate of CORE-023

[[CORE-023]] already names this exact symptom — "its `.claude/skills/` is a
**v2-era** install — still shipping `impact-template.md` and `kanmer-import`" —
and then explicitly scopes itself out of the cure: *"Reconciliation (FRD-013) is
the repair path; this ticket is the detection."*

This is that repair path. CORE-023 tells you the install is stale; this makes
reconciling it actually remove things.

## Approach

- Record the installed roster (and the version) in `.kanmer-skills-version`, and
  have install/update remove any previously-installed skill absent from the new
  bundle.
- Make `removeBundledSkillsOnly` read that record rather than the live bundle,
  so disconnect also stops leaving retired skills behind. Fall back to the
  current behaviour when the record predates this change — existing installs
  have no roster stamped.
- Never touch a directory Kanmer did not install. `run-kanmer` is the test case.
- **Marketplace hosts are unverified.** `claude` and `codex` install via
  `plugin install`, where the host's plugin manager owns the tree. Whether it
  prunes a removed skill on update is *not known* — check the CLI rather than
  assuming either way ([[MCP-009]]'s rule), and record the command and its
  output. If the host does not prune, say so instead of quietly relying on it.

## Verification

- [x] Install a bundle containing skill X; install a later bundle without it; X
      is gone from the destination.
- [x] A user-authored skill in the same directory (`run-kanmer`) survives both
      operations.
- [x] Disconnect removes a retired skill that a previous version installed.
- [x] An install stamped by an older Kanmer (no roster recorded) upgrades
      without deleting anything it cannot account for.
- [x] Each marketplace host's prune behaviour is recorded with the command run
      against the real CLI, or named as unchecked. **Named as unchecked**, with
      the on-disk layout evidence and the caveat — see `proof`.

## Outcome

Shipped in **PR [#41](https://github.com/collisionengineers/kanmer/pull/41)**,
squash-merged 2026-08-16 as `9ac20af`.

The destination stamp `.kanmer-skills-version` now records a **roster** (version
on line 1, owned skill folders below) and install **reconciles** against it
rather than overlaying: owned folders are replaced wholesale, roster-recorded
folders the bundle no longer ships are pruned, and a **closed** two-entry
tombstone list repairs installs made before the roster existed. One mechanism
fixes all three sites — `installSkills` reconciles, `updateSkills` inherits it
by being a wrapper, and `removeBundledSkillsOnly` reads the recorded roster
instead of the live bundle, so disconnect stops leaving retired skills behind
too. The "never touch a foreign skill" contract is unchanged and is now asserted
against the new deletion paths, including a poisoned-roster path-escape case.

**Shipped differently than planned, both recorded in the checklist notes:**

1. The roster is introduced by a literal `skills:` marker line. Without it an
   empty roster is indistinguishable from a legacy one-line stamp, and that
   distinction is what decides whether Kanmer may delete.
2. The **disconnect peer guard was taken, not filed** — the delegated judgement
   call. `disconnectAgent` removed `.agents/skills` unconditionally even though
   that directory serves opencode *and* antigravity. It came to ~10 lines inside
   a function already being rewritten. The existing
   `hasRegisteredCopySkillsPeer` was not directly reusable — it answers "is any
   copy-skills peer registered", which would have retained `.agents/skills`
   merely because grok (a different directory) was connected — so it gained an
   optional `skillsDir` filter used only by the skills removal; the AGENTS-block
   call keeps its broad semantics and its existing test.

**FRD-012 amended** (operator-authorized): new R2a, rewritten R4, new acceptance
criterion 5.
