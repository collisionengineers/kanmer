## What\n\nTwo defects in `apps/gui/src/main/connect.ts` and `providers.ts`, the same shape\nin both: Connect reaches registrations that are not solely its own.\n\n## 1. The legacy codex drain reaches only the current project\n\n`providers.ts:307` runs `codex mcp remove kanmer-<this project>`. So reconnecting\nproject A drains `kanmer-A` and leaves every other project's legacy global entry\nin place, forever, loading in **every** codex session regardless of folder.\n\nFound live: `~/.codex/config.toml` carried `[mcp_servers.kanmer-pegasus]`,\nrooted at a different repo, in every session started anywhere on the machine.\n\n**ADR-0007's consequence — \"the global pile drains as projects reconnect\" — is\ntrue only for projects that are reconnected**, and nothing tells the user which\nones still owe one. That sentence is amended by this ticket.\n\nThe fix is a **one-time reconciliation sweep** (ADR-0010), not ongoing Connect\nlogic: scan `~/.codex/config.toml` for every `mcp_servers.kanmer-*`, list them,\nask once, remove. No-op on the second run.\n\n**The sweep must warn when a listed project has no project-scoped replacement.**\nOn this machine `pegasus/.codex/config.toml` held only `mcp_microsoftdocs`, so\nthe orphaned global entry was pegasus's *only working* registration — removing\nit blind would have silently cut board access. The correct order is reconnect,\nthen drain, and the sweep should say so rather than assume it.\n\n## 2. grok and Claude share `.mcp.json` and the `mcpServers.kanmer` key\n\ngrok's provider (`providers.ts:363`) writes `.mcp.json` with key\n`mcpServers.kanmer` — the same file and the same key `claude mcp add -s project`\nwrites. `mcpServersUnmerge` deletes that key unconditionally, so\n**disconnecting grok removes Claude's project registration.**\n\nDecide the ownership rule and make `disconnectAgent` respect it.\n\n## Approach\n\n- The sweep is a pure function over the parsed TOML plus a per-project\n  \"has a project-scoped replacement\" probe, so it is unit-testable without a\n  real `~/.codex`.\n- Amend ADR-0007's consequences: state the drain's real precondition and name\n  the sweep as the thing that actually drains the pile.\n\n## Verification\n\n- [x] Unit tests on the sweep as a pure function over TOML, with the **pegasus\n      case as a fixture**: an entry whose project has no project-scoped\n      replacement is reported, never silently removed.\n- [x] Second run of the sweep is a no-op.\n- [x] Test that disconnecting grok leaves Claude's `.mcp.json` entry intact.\n- [x] ADR-0007's consequences section matches what the code does.\n\n## Outcome\n\n**Grok users: reconnect once.** Grok's MCP registration moved out of the project\n`.mcp.json` and into **`<root>/.grok/config.toml`** — grok's own project config,\nand its highest-priority MCP source. `.mcp.json` belongs to Claude Code alone:\nsharing it meant disconnecting Grok deleted Claude's registration, and a\nClaude-only project reported Grok as connected. Kanmer deliberately does **not**\nmigrate existing Grok registrations for you, because rewriting a file another\nhost owns is the bug, not the fix. Open the project, click **Connect** once.\nNothing breaks meanwhile — Grok still reads the old entry through its\ncompatibility layer, so the worst case is a stale duplicate. (ADR-0013.)\n\n**Connect can now drain the old global codex registrations left by pre-0.3\nversions.** Those were written one per project into `~/.codex/config.toml`, and\nevery one of them loaded in every codex session no matter which folder you\nstarted it in — reconnecting a project only ever cleaned up its own. The Connect\npanel lists whatever is left, marks which projects have since re-registered\nproperly, and removes those on one confirmation. Entries belonging to a project\nthat has *not* reconnected are shown but cannot be removed: that entry is that\nproject's only working registration, and the fix is to open it and Connect it\nfirst. The panel is invisible when there is nothing to report.\n
