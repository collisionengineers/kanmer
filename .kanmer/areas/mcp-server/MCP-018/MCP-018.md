## What

`scripts/check-plugin-sync.mjs` refuses to run from any linked git worktree
(MCP-007). Make the guard test what it actually cares about — whether
`@kanmer/core` resolves to *this* checkout's core — rather than whether the cwd
is a worktree.

## Why

The guard's stated reason is:

> a worktree has no node_modules of its own, so @kanmer/core resolves up to the
> main checkout

That premise is **defeatable, and is routinely defeated**. MCP-010 hit the same
wall, could not use the main checkout because other agents held it, and ran
`npm install` inside the worktree instead — which removes the root cause rather
than working around it. [[SKILL-013]] did the same and verified with
`realpathSync` that `@kanmer/core` resolved to
`.worktrees/skill-013/packages/core`.

So the guard now blocks a correctly-prepared worktree, on a repo where the main
checkout is contended by design (parallel ticket lanes are how this board is
worked). Both tickets had to evidence bundle provenance by hand with the two
tells AGENTS.md §8 names, and defer `plugin:check` itself to merged main.

The guard is **right to exist** — the trap it prevents is real and SKILL-011
shipped a bundle that did not contain its own feature. This is about the test
being a proxy for the property instead of the property.

## Approach

- Resolve `@kanmer/core` and compare its `realpathSync` to this checkout's
  `packages/core`. Refuse when they differ, *wherever* the cwd is — which also
  catches a broken **main** checkout, something the path test cannot do.
- Keep the refusal message naming the fix (`npm install` here, or run from the
  root).
- The two tells (`../../node_modules` count, `../../../../node_modules` count)
  could become assertions rather than something two tickets ran by hand.
