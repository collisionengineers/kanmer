## What

Easy install across every supported provider, with the per-provider variance
that actually requires — Claude and Codex at minimum, then opencode,
Antigravity and grok CLI.

## Why

A marketplace already exists, and the answer to "do we have one" is *partly*:

- `.claude-plugin/marketplace.json` — Claude, one plugin, `./plugins/kanmer`
- `.agents/plugins/marketplace.json` — the agents format, with an install policy
- `plugins/kanmer/.claude-plugin/plugin.json` and
  `plugins/kanmer/.codex-plugin/plugin.json` — two plugin manifests

So this is parity and coverage work, not greenfield. What is unclear is whether
each provider's install path is **tested**, and whether the manifests agree with
each other and with `providers.ts`.

## The failure mode to guard against, named correctly

ADR-0009 records that it once carried a wrong premise — that two hosts received
no skills at all — and attributes it to provider research having "gone stale in
weeks". **That framing is wrong and should not guide this ticket.** Provider
capability gaps do not go stale: opencode and Antigravity had supported skills
for a long time, and no host is going to *remove* skill support. The mistake was
assuming a capability was absent without checking it.

So the instruction here is not "re-verify because things change". It is:

- **Never conclude a provider lacks a capability from the absence of evidence.**
  Check for the capability, and record what you found and where you looked.
- Treat every "provider X can't do Y" claim in this repo as unverified until
  someone has looked. [[GUI-073]] is one such claim already caught — Antigravity
  labelled register-only when it has project-level support — and it is unlikely
  to be the only one.

## How to check: the binary, not only the docs

Documentation lags and omits. **The installed CLI is the ground truth**, so every
capability claim is checked against the tool itself as well as its docs:

- `claude --help`, `codex --help`, `opencode --help`, and the grok and
  Antigravity equivalents — then the relevant subcommand's own help
  (`claude mcp --help`, `claude plugin --help`, and so on). Subcommands that
  exist and are undocumented are common; the reverse happens too.
- Where a config file is the interface rather than a flag, read a real one the
  tool has written rather than a documented example.
- Record the command run and its output in the research document. A capability
  claim with no command behind it is the same assumption this ticket exists to
  stop, wearing a citation.

Note that the agent doing this work may not have every CLI installed. That is a
finding to report, not a reason to fall back on assumption.

## Also in scope: fix the source of the bad instruction

**ADR-0009's staleness clause is amended by this ticket.** It currently tells
future readers to re-verify provider specs "at implementation time" because
"skill-ecosystem facts go stale in weeks" — the wrong lesson, in the document
with the most authority, which is how it propagated into the first draft of this
ticket. Replace it with the absence-of-evidence rule and the check-the-binary
method above. Amending a merged ADR's reasoning is a real decision, so it is
called out here rather than done quietly.

## Approach

- Establish what parity means: same skills, same MCP registration, same install
  entry point — and where a provider genuinely cannot match, say so with the
  evidence, not the assumption.
- Audit the existing "cannot" claims across `providers.ts`, the manifests and
  FRD-012's install matrix, and check each one by the method above.
- Note the convergence already recorded in ADR-0009: one project-scoped write to
  `.agents/skills/` serves both opencode and Antigravity.
- Keep FRD-012's install matrix as the single description, corrected to match.

## Verification

- [ ] Each of the five providers installs from a documented path, tested rather
      than asserted.
- [ ] Every capability claim cites **both** the doc and the command run against
      the real CLI, with its output.
- [ ] The manifests agree with each other and with `providers.ts`.
- [ ] FRD-012's install matrix matches reality.
- [ ] ADR-0009's staleness clause is replaced with the absence-of-evidence rule
      and the check-the-binary method.
- [ ] Any CLI that could not be checked is named as unchecked, not assumed.
