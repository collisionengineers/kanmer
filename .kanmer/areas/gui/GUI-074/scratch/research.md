## Research findings (chore profile — no research/files doc owed pre-plan; recording here for the planner)

### The nav item and its wiring
- `apps/gui/src/renderer/src/components/Settings.tsx:206-213` — the button itself: `<button className="tab help-link" title="Open the manual for this tab" aria-label="Open the manual for this tab" onClick={() => onOpenManual?.(SETTINGS_HELP[tab])}>?</button>`, inside `<nav className="settings-rail">` right after the `SETTINGS_TABS.map(...)` block (Settings.tsx:191-214).
- Comment above it, Settings.tsx:201-205, is the one the ticket asks to verify.
- `SETTINGS_HELP` map: Settings.tsx:52-58 — `{ board: "stages", profiles: "profiles", appearance: "getting-started", git: "board-sync", connect: "dispatch" }`.
- `onOpenManual` prop: declared Settings.tsx:49, destructured :74. **Only one caller**: `apps/gui/src/renderer/src/App.tsx:1653-1656`, passed to `<Settings ...>` as `onOpenManual={(chapter) => { setSettingsOpen(false); setManual({ chapter }); }}`. No other component reads `onOpenManual` or `SETTINGS_HELP` — confirmed via repo-wide grep. Removing the button leaves both fully dead; both should go (App.tsx prop line + Settings.tsx prop/const), matching the ticket's own instruction.
- Unused-CSS cleanup found beyond the ticket's listed scope: `.help-link` rule at `apps/gui/src/renderer/src/styles.css:1881-1884` (`margin-left: auto; opacity: 0.7;`) is used ONLY by this button (`className="tab help-link"`) — grep confirms no other `.help-link` usage. Should be deleted too, or it's orphaned CSS.

### The "asserted by manual.test.ts" claim — verified FALSE, and worse than the ticket assumed
- Grepping `SETTINGS_HELP` in `apps/gui/src/renderer/src/manual/manual.test.ts` — zero matches, confirming the ticket's claim.
- But there IS a related block at `manual.test.ts:66-74`, `describe("deep-link targets")`, that checks a **separately hand-maintained, hardcoded array**: `["profiles", "stages", "documents", "proof", "shortcuts", "troubleshooting"]`, asserting each exists in `MANUAL_CHAPTERS`.
- This list does NOT match `SETTINGS_HELP`'s values (`stages`, `profiles`, `getting-started`, `board-sync`, `dispatch`). Overlap is only `profiles` and `stages` — the test never actually checked that `getting-started`, `board-sync`, or `dispatch` (3 of the 5 SETTINGS_HELP targets) exist. So the comment's claim was doubly wrong: not only does the test not reference `SETTINGS_HELP`, the thing it does check doesn't even cover most of the map's real targets.
- Repo-wide grep for `initialChapter`, `MANUAL_CHAPTER_IDS`, and each of the test's checked ids as string literals (`"documents"`, `"proof"`, `"shortcuts"`, `"troubleshooting"`) found **no other deep-link caller anywhere in the renderer** — `Settings.tsx`'s `?` button was the only thing in the app that deep-links into a manual chapter by id (F1 and the Help menu both open the manual with no chapter, defaulting to the first chapter). So once this button is gone, the app has *zero* deep links, and the `manual.test.ts:66-74` "deep-link targets" block becomes a test guarding a feature that no longer exists — it should very likely be removed as part of this ticket (not just the map in Settings.tsx). This is a planning decision, not made here.

### Manual stays reachable another way — confirmed
- F1 handler: `App.tsx:916-920` — `if (e.key === "F1") { setManual((m) => (m ? null : {})); }` opens the manual with no specific chapter (defaults to `MANUAL_CHAPTERS[0]`, "Getting started").
- Help menu: `apps/gui/src/main/index.ts:316-325` — `&Help` submenu, item `label: "Manual"`, `accelerator: "F1"`, sends `{ type: "manual" }` over the menu channel.
- Renderer picks that up at `App.tsx:558-562` (`onMenu` handler): `else if (cmd.type === "manual") setManual({ chapter: cmd.chapter });`.
- Both paths are independent of `Settings.tsx`/`onOpenManual` — removing the Settings "?" does not touch either. Manual stays fully reachable.
