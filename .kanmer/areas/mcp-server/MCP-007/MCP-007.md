## What

Make `scripts/check-plugin-sync.mjs` detect that it is running from a path under
`.worktrees/` and refuse — or loudly warn — instead of returning a meaningless
pass.

## Why

[[SKILL-011]] merged (PR #31) with a plugin bundle that **did not contain the
feature it shipped**, and every guard in the rail said it was fine.

A git worktree has no `node_modules` of its own, so `@kanmer/core` resolves *up*
to the main checkout's workspace symlink. `tsup` therefore bundles **main's**
core, silently ignoring the core just changed in the worktree:

```
$ ls -d .worktrees/skill-011/node_modules
No such file or directory
$ grep -c filter.group .worktrees/skill-011/packages/core/dist/index.js   -> 1
$ grep -c filter.group .worktrees/skill-011/plugins/kanmer/mcp/kanmer-mcp.cjs -> 0
```

Nothing caught it:

- **Tests** run from `src` via vitest and never touch the bundle.
- **`plugin:check`** compares the committed bundle against a fresh build — and
  inside a worktree *both* are built the same wrong way, so it is self-consistent
  and passes. It is only meaningful when the artifact was built where the check
  runs.
- The single visible tell is the embedded path comments switching from
  `../../node_modules` to `../../../../node_modules`, which nobody reads.

It failed the moment it was run at the repo root, after merge. Fixed for that
instance by PR #32, and AGENTS.md §8 gotcha 8 now names the trap — but prose is
the weakest fix available, and every future ticket that touches `@kanmer/core`
from a worktree hits this.

## Approach

- In `check-plugin-sync.mjs`, detect a `.worktrees/` segment in the repo root it
  resolves, or the absence of a local `node_modules` beside the workspace root.
- Prefer **refuse over warn**: a passing check that cannot be true is worse than
  no check, which is exactly how this shipped.
- Say what to do — build at the repo root — rather than only that something is
  wrong.
- Consider the same guard in `plugin:build`, which is where the bad artifact is
  actually produced. Detecting it at build time would stop the artifact ever
  existing; detecting it at check time only stops it being trusted.

## Verification

- [ ] `npm run plugin:check` inside a `.worktrees/<id>` worktree fails with a
      message naming the cause and the fix.
- [ ] The same command at the repo root is unchanged.
- [ ] Reproduce the original failure: change something in `packages/core` inside
      a worktree, run `plugin:build`, and confirm the guard fires rather than
      producing a bundle built from main's core.
- [ ] `scripts/release.mjs` still passes at the root — the guard must not break
      the release rail it is part of.
