# ADR-0009 — Skills are not the contract; skills derive rules, never restate them

## Context

All five supported hosts now load agent skills (re-verified against the installed binaries 2026-08-16): Claude Code and codex via the plugin; grok via its skills dir, its Claude compat *and* `.agents/skills/`; opencode natively (project `.opencode/skills/`, plus Claude-compatible `.claude/skills/` and agent-compatible `.agents/skills/`); Antigravity at project `<root>/.agents/skills/` — **but only in a session bound to a workspace folder**, which Kanmer does not yet establish (see the convergence note below). An earlier premise of this ADR — that two hosts received no skills at all — was **wrong**: it repeated Phase-6-era provider research that nobody had checked. It was not stale; see the method clause below, which replaces the staleness reading with the rule that actually prevents a recurrence.

What remains true on every host: skills are **on-demand** (loaded only when the agent judges them relevant), often **permission-gated** (opencode: allow/deny/ask per skill), **install-time copies** that go stale between updates, and **prose** an agent can fail to follow. Meanwhile shipped skills hardcoded gate rules in prose (kanmer-auto restates four gates), which profiles (ADR-0003) make per-ticket-wrong.

## Decision

The contract hierarchy is: (1) **server-enforced gates** — the only layer that cannot be skipped; (2) **MCP tool descriptions** — every client reads them on every session; `get_doc_gates` teaches profiles in two sentences; (3) **the AGENTS.md managed block** — universal orientation, always in context (profiles exist; call get_doc_gates before moving; read the whole ticket folder and group context); (4) **skills** — workflow choreography, best-effort by nature. Skills never restate enforceable rules: they call `get_doc_gates` and do what it says.

Supporting files *inside* a skill directory are fine — every host's skill spec ships them. **Cross-skill** references (e.g. skills pointing at `kanmer-tickets/references/tool-reference.md`) are permitted only because Connect installs the roster atomically as sibling directories; that is a stated constraint on installs, not an assumption. No new cross-skill shared files are added (the questioning behaviour is per-skill prose by explicit user decision).

### Method: how a provider capability claim is established

Provider capability claims are established **against the installed binary, not the documentation**, and are **never inferred from the absence of evidence**. A statement that a host cannot do something is admissible only with the command that was run and its output; "the docs do not mention it" is not a finding. Prefer each host's own resolved-configuration dump over its documentation and over its narrower subcommands — `grok inspect`, `opencode debug skill`, `codex plugin list`, `claude plugin details` — several of which are undocumented, and one of which (`grok mcp list`) reports "none configured" for servers `grok inspect` shows as active. Where a config file is the interface, read one the tool itself has written rather than a documented example. Where a capability appears absent, prove the probe works by finding a case where it reports the capability present. If a CLI is not installed, record it as **unchecked** — an unchecked host is a finding, never a default.

A positive control is necessary but **not sufficient**: **verify the mechanism you are actually testing, not a proxy for it.** The worked example is this clause's own near-miss. A probe asked Antigravity's CLI to list its skills and to reach a probe MCP server, got nothing, and concluded that `agy` reads no project skills directory — with a positive control that passed. The conclusion was false, for two independent reasons. First, the session was not bound to a workspace folder: bare `agy` binds to `default-cli-project`, whose record carries `"projectResources": {}`, so there is no folder to read `.agents/` from and the working directory is irrelevant. `--new-project`, `--project <id>` with a `folderUri`, and `--add-dir <path>` each bind, and **only the flag on the command line binds** — workspace trust is not the gate, a git root does not auto-bind, and a project merely existing does not bind. Second, and the trap that generalises: **a workspace MCP server never surfaces as a named top-level tool.** It appears as the generic `call_mcp_tool` / `list_resources` / `read_resource` triad, so grepping a tool list for the server's own tool name is a **false negative even when the server is connected**. The tool list was a proxy; calling the tool is the mechanism. Ten runs with controls throughout, corroborated by the probe server's own process log, settled it.

This ADR's own correction is the precedent, and its lesson is **not** that such facts go stale. They did not: opencode and Antigravity had supported skills for a long time, and no host removes skill support. The premise was wrong because nobody checked. Re-verification is therefore not a calendar exercise — it is the standard of evidence above, applied once, properly.

Connect deliberately writes OpenCode's roster to its native `.opencode/skills/` directory and Antigravity's roster to `.agents/skills/`. OpenCode can discover the latter, but using the provider-specific directory prevents Antigravity's project copy from also becoming OpenCode's—and, through Codex's `.agents` discovery, a duplicate Codex roster. Grok also reads `.agents/skills/`, which still makes grok's separate `.grok/skills` write redundant. One caveat decides whether the `.agents` write does anything for Antigravity: `agy` reads `.agents/skills/` and `.agents/mcp_config.json` only in a **workspace-bound** session, and **Kanmer establishes no binding today** — no `--project`, `--new-project`, `--add-dir` or any `agy` invocation appears anywhere in `apps/` or `packages/`. The write is correct and currently **inert**; MCP-015 owns making it live.

## Alternatives considered

(a) Skills as the primary rulebook — skips the on-demand/permission/staleness reality; one unloaded skill silently voids the rules. (b) A shared asking/rules reference file across skills — adds a cross-skill coupling for content the user explicitly wants as tailored per-skill prose.

## Consequences

Skills get shorter and drift-proof; behaviour degrades gracefully when a skill isn't loaded; the AGENTS block and tool descriptions join the release rail as reviewed surfaces; Connect upgrades opencode/antigravity from AGENTS-block-only installs to real project-scoped skill installs — for Antigravity that upgrade is written but **inert until Kanmer binds a workspace folder** (MCP-015), so the roster is in place and unread rather than absent. The method clause also raises the cost of a capability claim: a "provider X cannot do Y" line now needs a command and its output behind it, which is deliberate — the claims that survive that bar are the ones worth building a registry on.
