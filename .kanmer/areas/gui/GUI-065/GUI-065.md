## What

With no project open, the app gives no way to see or act on an available update.
Render the update banner, toasts and the restart prompt on the welcome screen
too.

## Why

`apps/gui/src/renderer/src/App.tsx:1015` returns early:

```tsx
if (!root || !board) {
  return <Welcome … />;
}
```

Everything that surfaces an update sits *below* that return — the banner at
`:1112`, the toast stack, and the "Restart and update" prompt at `:1371`. The
updater itself is app-global and runs fine (its own comment at `:452` says so),
and **Help → Check for Updates…** is not gated (`main/index.ts:328-331`). So the
check runs, the download happens, and the result renders into a subtree the
welcome screen never mounts. The user sees nothing and concludes updating only
works inside a project.

This is the first screen after launch and the most likely moment someone updates
— it is the worst place to hide it.

## Approach

- Lift the update surface (`lib/update.ts` → `updateSurface`) above the `!root`
  early return so both branches render it, rather than duplicating the markup.
- The restart prompt carries the MCP-session warning (`restartWarning`); keep
  that intact on the welcome path — with no project open there is usually
  nothing to lose, but the probe is app-wide, not project-scoped.
- Check `Welcome.tsx` has somewhere sane to put a banner without shifting the
  recents list under the cursor.

## Verification

- [x] Launch with no project open against a feed offering a newer version — the
      banner appears on the welcome screen. (Real local feed, real `downloaded`
      event. "Restart and update" was deliberately not clicked — see proof.)
- [x] Help → Check for Updates… on the welcome screen produces a visible result
      in both the up-to-date and update-available cases. (The menu item was
      already ungated; the missing piece was a `.toast-stack` to render into.
      A live update toast is shown in one on the welcome screen.)
- [x] In-project behaviour is unchanged. (Banner at `y=86`, below the tab strip
      and topbar, `overflows: false`, board renders 160 items.)

## Outcome

Shipped in **PR [#61](https://github.com/collisionengineers/kanmer/pull/61)**,
squash-merged as `6dbb284` on 2026-08-17.

**Zero IPC, zero preload, zero main-process code.** The updater was already
app-global and every piece of state already ran on the welcome screen — only
three JSX blocks were in the wrong subtree. They are now bound as JSX *values*
above the early return and rendered from both branches, which keeps exactly one
banner instance and therefore keeps `installUpdate()`'s single call site
(duplicating the markup was the obvious wrong fix). All three moved: lifting
only the banner would have left the menu check silent and "Restart now" opening
a modal that never renders. The welcome branch gained a `.app` shell and
`.welcome` became `flex: 1; min-height: 0`.

Shipped beyond the title, deliberately:

- **`FRD-021` R1 gains "on every screen, including with no project open"** plus
  an `## Amended — GUI-065` section. The FRD was silent on the case — an
  omission, not a decision — so this was a bug against R1's plain reading *and*
  the FRD owed a clause so the next reader cannot mistake the silence for intent.
- **The repo's first React test.** `components/UpdateBanner.test.tsx`, with
  `jsdom` + `@testing-library/react` as new `apps/gui` devDeps (operator-
  authorized). jsdom is enabled **per file** by docblock, so the other 23
  `apps/gui` suites keep their node environment. The convention change is
  recorded in `AGENTS.md` §7, as the operator required, not slipped in.
- **`AGENTS.md` §7's "exactly two `installUpdate` renderer call sites"
  corrected to one** — stale since GUI-064.
- **The whole `.toast-stack` moved, not just update toasts**, so GUI-064's
  install-refusal toast is now visible on the welcome screen too. Intended.

Known and accepted: the centred welcome content shifts **down** by ~18px when
the banner appears (~30 s after launch) — half a banner height, because the
content re-centres in the shorter box. The plan predicted "up"; the measurement
corrected it.

The honest limit, stated in `proof.md` and in the test file: the component test
proves the banner renders, **not** that `App.tsx` mounts it above the early
return — and the mounting is the bug. That gap is closed by a one-off visual
pair (pre-fix vs merged main under the same `downloaded` state), not by
anything that re-runs.

**No follow-up tickets.** The deferred `KANMER_FAKE_UPDATE` dev hook is weaker
than research anticipated now that the repeatable guard is a real test.
