## What

`plugins/kanmer/.mcp.json` is read by **codex** and by **Antigravity (`agy`)**.
On neither host can it produce a working board, and [[MCP-011]] established that
this is an upstream limit rather than a manifest defect. Decide what Kanmer does
about it.

## Why — the measurement ([[MCP-011]] research, finding 3 and 5)

Against `codex` 0.147.0 and `agy` 1.1.13, each probed by **calling a tool**
through a real plugin install, always beside a variable-free positive control
that did launch:

- **Neither host expands any `${…}` token** in a plugin's MCP config —
  `${PLUGIN_ROOT}`, `${CODEX_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_ROOT}` and
  `${VAR:-default}` were each tried. codex also hands the child no `PLUGIN_ROOT`
  env var (`pluginEnv: {}`). So the shipped `${PLUGIN_ROOT}` form **silently
  never launched**, for either host, on any release to date.
- **codex does resolve a relative `cwd` against the installed plugin root**, so
  `{"command":"node","args":["mcp/kanmer-mcp.cjs"],"cwd":"."}` starts the server
  — MCP-011 shipped exactly that. But discovery then runs from
  `~/.codex/plugins/cache/kanmer-plugins/kanmer/<version>` and correctly reports
  no board:

  ```
  kanmer-mcp fatal: no Kanmer board found. Tried:
    C:\Users\PC\.codex\plugins\cache\kanmer-plugins\kanmer\0.3.2\.kanmer
    …
  ```

  **Locating the script and discovering the board need different working
  directories, and codex offers no way to express both.** An ambient
  `KANMER_ROOT` did not rescue it either (tried with and without a manifest
  `env` block; the server accepts `KANMER_ROOT` fine when run by hand, so codex
  is not passing the ambient environment through).
- **`agy` is worse**: it reads `.mcp.json` at the plugin root regardless of what
  a manifest points at, copies it **verbatim** into
  `~/.gemini/config/plugins/<name>/mcp_config.json`, and joins a relative path
  to the *session* cwd — `Cannot find module '…\proj\${PLUGIN_ROOT}\mcp\…'`.
  No committed manifest content can make it launch.

## Options

1. **Leave it** — the manifest is as correct as those hosts permit, the failure
   is now loud rather than silent, and it starts working the day either host
   gains expansion. FRD-012 R6 states the limitation; the README tells codex
   users to register via Connect or `codex mcp add`. *This is the status quo
   after MCP-011.*
2. **Remove `mcpServers` from `.codex-plugin/plugin.json`** so the plugin
   honestly advertises skills-only for codex, and stop shipping a registration
   that cannot work.
3. **Make Connect do it** — after `codex plugin add`, also write the project
   `.codex/config.toml` entry (Connect already does this; the question is
   whether the plugin path should stop pretending to duplicate it).
4. **Upstream** — ask codex for `${PLUGIN_ROOT}` expansion, or a `cwd` that
   defaults to the workspace while `args` resolve against the plugin.

Option 1 was taken by default in MCP-011 because it is the reversible one and
because changing what a shipped plugin advertises is a product decision, not a
manifest fix. **This ticket is where that decision gets made deliberately.**
