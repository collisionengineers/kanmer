## What

**8 of the manual's 12 chapters are stubs** — an FRD's H1 and a pointer line,
~100 characters each. Replace them with written user-facing chapters, and stop
the generator deriving user documentation from internal specs.

## Why

Run the generated chapters and the state is unambiguous:

| Chapter | Body |
|---|---|
| getting-started | 1799 |
| troubleshooting | 1772 |
| board-sync | 1761 |
| shortcuts | 717 |
| profiles, stages, documents, groups, proof, references, backlog, dispatch | **82–116 chars each** |

Every stub is literally this:

```
# FRD-002 — Requirement profiles

*Full specification: `docs/functional/frd/FRD-002-requirement-profiles.md`.*
```

Three things are wrong, in order of severity:

1. **The chapters are empty.** A user opening Help → Manual → Requirement
   profiles learns nothing at all.
2. **It exposes our internal document scheme.** PRD/FRD/ADR ids are a
   contributor concern. The manual may *explain* that Kanmer's process uses
   governing docs — that is a product concept — but it must never print
   `FRD-002` as a chapter title or send a user to a path that is not in the
   installed app.
3. **The pointer line is a dead end.** `docs/functional/frd/…` does not ship in
   the package (`scripts/build-manual.mjs:5-8` says so), so the one line each
   stub does contain points at a file the reader cannot open.

How it got here: `build-manual.mjs:41-47` takes each FRD's "lead prose" —
everything above the first `## ` — but these FRDs go straight from H1 to their
first section, so the lead is just the heading. The `if (!body) throw` guard at
`:66` was meant to catch exactly this and did not fire, because the H1 strip at
`:46` left a non-empty string. The guard is testing the wrong thing.

[[GUI-017]] built the manual mechanism; this ticket is the content it needs.

## Approach

- Write the 8 chapters by hand into `docs/manual/`, in the user's vocabulary:
  what the thing is, when to use it, what it looks like in the app. No
  requirement ids, no repo paths, no "full specification" footer.
- Drop the `FROM_FRD` derivation from `build-manual.mjs`. An FRD is written for
  an implementer; a manual assembled from FRDs is the wrong shape however much
  prose they have. The script's own comment at `:22-27` already argues this — it
  just stopped one step short.
- Replace the emptiness guard with one that cannot be satisfied by a heading:
  minimum prose length after stripping headings, and no `FRD-`/`ADR-`/`PRD-`
  token in any chapter body or title.
- Keep the two generated chapters that are genuinely generated — shortcuts (from
  the binding table) — and keep `--check`.
- Amend FRD-024 to say the manual is hand-written; it currently permits the
  derivation.

## Verification

- [ ] Every chapter body is substantive prose; the shortest is well past the
      current 82 characters.
- [ ] No chapter title or body contains `FRD-`, `ADR-`, `PRD-`, or a
      `docs/…` repo path — asserted in `manual.test.ts`, so it cannot regress.
- [ ] `npm run check:manual` passes and the committed artifact is current.
- [ ] Read the manual in the packaged app: each chapter answers its own title
      for someone who has never seen the repo.
