## What

Add a Settings surface for **background dispatch**, per provider: which model a
dispatch runs on, and what prompt it sends. Today neither is adjustable without
editing the repo and rebuilding.

## Why

Your assumption is correct — confirmed in the code. `providers.ts:314-371`
defines every dispatch invocation, and **not one passes a model**:

```ts
codex:     dispatchArgs: (prompt) => ["exec", prompt]
claude:    dispatchArgs: (prompt) => ["-p", prompt]
opencode:  dispatchArgs: (prompt) => ["run", prompt]
grok:      dispatchArgs: (prompt, root) => ["-p", prompt, "--cwd", root]
```

The signature is `(prompt, root) => string[]` — there is nowhere for a model to
enter. So every dispatch runs on whatever that CLI is configured to default to,
decided outside Kanmer entirely, and Kanmer cannot see or show it.

The prompt is equally fixed: `dispatch.ts:106` —

```ts
const prompt = task ? task.prompt(ticketId) : takeTicketPromptText(ticketId);
```

Both come from `@kanmer/core` and are compiled in. `AppSettings`
(`main/settings.ts:24-36`) has no dispatch section at all.

Why it matters: **model choice is the cost/quality dial for the whole feature.**
FRD-010's point is that a dispatch does *one* deliverable — map the files, write
the plan, run the verification. Those are not the same difficulty, and a person
dispatching a dozen tickets wants a cheap fast model for the mechanical ones and
a strong one for planning. Right now every task gets the same model, chosen
elsewhere.

And the prompt is the actual interface to the agent. A team with house rules
("always run the linter", "never touch generated files") has no way to say so.

## Approach

The design questions are real; research should settle them before code.

- **What axis do overrides hang on?** Provider is the obvious one and what was
  asked for. But per *task type* may matter more — cheap for "map the files",
  strong for "write the plan" — and per project may matter too. Provider × task
  is a grid; pick deliberately rather than shipping the first one.
- **Scope: global or per project?** `AppSettings` is per machine. A model choice
  probably is too; a house-style prompt probably is not.
- **Do not fork the prompt SSOT.** [[CORE-009]] made prompt/dispatch a single
  source of truth on purpose. A user prompt that *replaces* the built-in one
  silently reintroduces the drift that ticket removed — favour appending house
  rules to the built-in prompt, or at minimum showing the default alongside any
  replacement so divergence is visible.
- **Verify each CLI's model flag individually.** They will not agree, and a
  wrong flag either errors or is silently ignored — both invisible in a
  background process. `dispatchArgs`'s signature has to widen to carry the
  config.
- **Failure has to be visible.** An invalid model name fails inside a detached
  child; today that surfaces as a dispatch that simply dies. Validate what can
  be validated up front and surface the rest.
- Antigravity has no dispatch at all ([[GUI-073]]) — the UI must not offer
  dispatch settings for a host that cannot dispatch.
- **FRD-010 needs extending**, not just implementing: it describes dispatch as
  fixed, and this makes it configurable.

## Verification

- [ ] Setting a model for a provider changes the flag actually passed — asserted
      against the spawned argv, not just the settings object.
- [ ] With nothing configured, behaviour is byte-identical to today: no model
      flag, built-in prompt. Nobody gets a changed default by upgrading.
- [ ] A custom prompt reaches the agent, and the built-in take-ticket contract
      (work the ticket via MCP) still holds — a prompt that breaks the workflow
      should be hard to write by accident.
- [ ] An invalid model produces a visible failure, not a silently dead dispatch.
- [ ] Providers without dispatch show no dispatch settings.
