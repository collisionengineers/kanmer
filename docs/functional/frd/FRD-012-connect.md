# FRD-012 — Connect: agent registration & skill install

## Overview

Connect registers the project's board with an agent host's MCP client and installs the skill roster — per provider, idempotently, with a copy-paste fallback when a command fails. Five providers: Claude Code, codex, opencode, Grok CLI, Antigravity.

## Requirements

- R1. **Registration matrix (end-state):** Claude Code — `claude mcp add kanmer -s project` (project `.mcp.json`, **Claude's alone**; stale user-scope cleanup retained). **codex — project config file** `<root>/.codex/config.toml` (`[mcp_servers.kanmer]`, TOML merge preserving unknown keys, idempotent unmerge), with the *project must be trusted* caveat surfaced in the UI, plus legacy cleanup `codex mcp remove kanmer-<project>` on reconnect. opencode — `opencode.json` merge (as shipped). **Grok — `<root>/.grok/config.toml`** (`[mcp_servers.kanmer]`, the same TOML merge as codex; grok's native project scope and its highest-priority MCP source — it no longer writes `.mcp.json`, see ADR-0013). Antigravity — `.agents/mcp_config.json` (as shipped).
- R1a. **One host, one file.** Kanmer registers a host only in a file that host alone owns, and unregisters only from files it owns (ADR-0013). No two providers may write the same path. Whether a config still registers Kanmer is answered by the provider that owns the file, tri-state, so "cannot read this file" stays distinct from "not registered".
- R1b. **Machine-wide legacy sweep.** The Connect panel lists every `mcp_servers.kanmer-*` left in the global `~/.codex/config.toml` by pre-ADR-0007 versions, classified against the project each one names, and drains the ones whose project has a registration codex will actually load — one confirmation, a no-op on the second run (ADR-0010). Entries whose project has **no** project-scoped replacement, or whose folder codex does not trust, are reported and **never removable**: that entry is the project's only working registration, and the user is told to open that project and Connect it first. Kanmer never writes another project's config files, and never rewrites the global TOML — removal is delegated to `codex mcp remove`. This, not per-project reconnection, is what drains the pile (ADR-0007, amended).
- R1c. **Registration files stay gitignored, not committed (GUI-083).** `.codex/config.toml` is per-project config a team could legitimately share — ADR-0007 is precisely about project scope being the right place for it — but that is a question of *where* the registration lives, not of whether *today's* file content is fit to commit. Every registration file this matrix writes (`.mcp.json`, `.codex/config.toml`, `.grok/config.toml`, `opencode.json`, `.agents/mcp_config.json`) is built from the same `Invocation` — `command` and `args` are this machine's absolute paths to the local Kanmer install, never a portable form. Committing one would be exactly as inert to a teammate as a checked-in `.mcp.json` hardcoding a different machine's `C:\Users\<other>\...` path: it silently fails to register anything and reads as if it should work. So all five are gitignored, symmetrically, for this one reason — not project-vs-personal-scope, which ADR-0007 already settled in project scope's favor. If a future change makes `Invocation` portable (e.g. a relative or env-resolved command), this call is worth revisiting; it is not settled for all time, only for what these files contain today.
- R2. **Skill install matrix (end-state).** Corrected 2026-08-16 against the installed binaries per ADR-0009's method clause; each divergence between this matrix and shipped code names the ticket that owns closing it.
  - **Claude Code** — plugin marketplace. The marketplace manifest is at the **repo root**, not inside `plugins/kanmer`, and the shipped command passes the plugin directory, so the install fails and the failure is swallowed. Second command is `claude plugin install kanmer@kanmer`. Owner: **MCP-013**.
  - **codex** — plugin marketplace, same wrong root. Its verb is `codex plugin add` (there is no `codex plugin install`) and its marketplace name is **`kanmer-plugins`**, taken from `.agents/plugins/marketplace.json` — *not* Claude's `kanmer`. The two names legitimately differ; any shared "install the plugin" copy that assumes one is wrong for the other. Owner: **MCP-013**.
  - **opencode** — project-scoped copy to `.agents/skills/`. opencode has no plugin installer at all, so the copy is a genuine necessity rather than a fallback. It also reads `.claude/skills/` and `.opencode/skills/`; `.agents/skills/` is the one to write.
  - **Antigravity** — project-scoped copy to `.agents/skills/`, plus `.agents/mcp_config.json`. Both **are** read by `agy`, but **only in a session bound to a workspace folder**, and Kanmer establishes no binding today, so the write is correct and currently inert. Antigravity can also take the plugin directly (`agy plugin install`), but that delivers to `~/.gemini/config/plugins/` — global, which cuts against ADR-0007. Owner of both the binding and that choice: **MCP-015**.
  - **Grok** — `.agents/skills/` serves grok too, so its separate `.grok/skills` write is redundant, and grok can take the plugin outright (`grok plugin install <dir> --trust`). Note `grok inspect` is grok's oracle; `grok mcp list` reports "none configured" for servers that are active. Owner: **MCP-014**.
  - One project-scoped write to **`.agents/skills/` therefore serves three hosts** — opencode, grok and Antigravity — subject to Antigravity's binding caveat. All copies stamped (`.kanmer-skills-version`) with the existing update-offer flow; note that a marketplace host reports no installed version, so the update offer does not apply to Claude Code or codex.
- R2a. **A skill install is a reconciliation, not an overlay.** The stamp records the bundled version on line 1 and, below it, the **roster** — the skill folders Kanmer wrote to that destination. Install replaces each owned folder **wholesale** (so a file the bundle has dropped or renamed cannot outlive it) and removes any roster-recorded folder the bundle no longer ships. Wholesale replacement discards local edits inside a Kanmer-owned skill folder; that is accepted under ADR-0009's "install-time copies", and Connect therefore **names the folders it replaced** in its output rather than deleting silently. Skills Kanmer did not write are never touched: the roster is the only deletion authority, never a name prefix. A stamp that predates the roster means "ownership unknown" and must make Kanmer delete less, not more. One **closed** tombstone list of two paths retired by `130f837` (`kanmer-import`, `kanmer-research/assets/impact-template.md`) repairs installs made before the roster existed; **nothing is ever added to it** — every later retirement is the roster's job, and a growing list would be a second source of truth about what Kanmer owns.
- R3. The **AGENTS.md managed block** is written for every provider — the universal orientation layer (ADR-0009), no longer anyone's sole delivery. Idempotent, marker-delimited, verified by `verify-agents-block`.
- R4. Disconnect reverses exactly what connect **wrote** (config entries, skill copies, never the AGENTS block without asking) — which means the recorded roster, not the currently-bundled names: a skill retired since that install was written by connect and must be removed by disconnect. Where one directory serves more than one host (`.agents/skills` — opencode and Antigravity today, and grok as well if **MCP-014** retires its redundant separate `.grok/skills` write, per R2), the copies are retained while **any** host writing that directory is still registered; ADR-0009 makes the roster's atomicity a stated constraint, so a half-removed roster breaks a connected host. **And nothing else:** "what connect wrote" is scoped by ownership (R1a), so disconnect can never remove another host's registration, and it does not reach into a file this host no longer owns to undo what an older Kanmer wrote there.
- R5. **Provider capability claims follow ADR-0009's method clause** — established against the installed binary, never inferred from the absence of evidence, with the command and its output recorded; a probe needs a positive control, and a positive control is not sufficient, because the mechanism must be verified rather than a proxy for it. The rule is stated once, in ADR-0009, and is **not** paraphrased here: an earlier version of this requirement carried the wrong lesson ("re-verified against current host docs at implementation time" — a staleness reading of a failure that was never about staleness), and it carried it because the rule had been copied instead of referenced.

## Acceptance criteria

1. Connect codex twice: one `[mcp_servers.kanmer]` entry in the project file, zero new global entries, legacy `kanmer-<project>` gone from `~/.codex/config.toml`.
2. Connect opencode and Antigravity: both discover the roster from one `.agents/skills/` tree. For opencode, `opencode debug skill` lists them. For Antigravity the tree is read **only in a workspace-bound session**, so the criterion is checked as `agy` bound to the project folder, and it is checked by **invoking a skill and calling the MCP server's tool** — not by grepping a tool listing, in which a connected workspace server appears only as the generic `call_mcp_tool` / `list_resources` / `read_resource` triad. Kanmer does not bind a workspace today, so this criterion cannot pass for Antigravity until **MCP-015** lands; it is stated as the end state, with that dependency named rather than a passing test implied.
3. Every merge/unmerge is pure and unit-tested (unknown keys preserved, idempotent, byte-stable re-merge).
4. A failed command yields the exact copy-paste fallback (shipped behaviour retained).
5. Install a bundle, retire a skill from it, install again: the retired skill is gone from the destination, a user-authored skill beside it survives byte for byte, and Connect's output names what it replaced and what it removed. Disconnect after a retirement leaves nothing behind either.
6. Connect Claude, then connect **and disconnect** Grok: Claude's `.mcp.json` is byte-identical afterwards, and a Claude-only project never reports Grok as connected.
7. Run the legacy sweep against a global config holding two `kanmer-*` entries, one of whose projects has reconnected and one of whose has not: the first is offered pre-selected, the second is shown as a warning **with no way to remove it** and text naming the project and telling the user to Connect it first. Run it again: the removed one is gone, the held-back one is reported unchanged, and nothing else in the global file changed.

## Upgrade note — Grok users reconnect once

Grok's registration moved from the project `.mcp.json` to `<root>/.grok/config.toml` (ADR-0013), because `.mcp.json` is Claude's file and sharing it meant grok's disconnect deleted Claude's registration. **Kanmer does not migrate existing grok registrations automatically** — rewriting another host's file is the defect, not the fix. Anyone who connected Grok before this release should open the project and click **Connect** once. Nothing breaks in the meantime: grok still reads the old `.mcp.json` entry through its compatibility layer, so the worst case is a stale duplicate.
