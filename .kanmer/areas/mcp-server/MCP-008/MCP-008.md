## What

An agent should be able to work the board with the desktop app **closed**, and
Kanmer should ship a `.mcpb` bundle installable directly into Claude Desktop.

## Why

Nothing plans this today. FRD-010 uses the word *headless* for **dispatch** —
spawning provider CLIs — not for board access, and no FRD covers running without
the GUI. What actually happens is undocumented and partly accidental:

- The MCP server is registered as `command = <Kanmer.exe>` with
  `ELECTRON_RUN_AS_NODE=1` (`connect.ts`), so it runs without a window — but it
  lives inside the install directory, which is what [[MCP-005]] exists to undo.
- The board worktree `.worktrees/kanmer` and its git auto-sync are created and
  driven by the **app**. With the app closed, who commits?

So "does it work headless" has no clear answer, which is itself the problem.

`.mcpb` is separate and simpler: a bundle format for installing an MCP server
into Claude Desktop without a CLI. Kanmer has no such artefact.

## Approach

- Establish what already works with the app closed, by testing rather than
  reasoning: reads, writes, gate evaluation, and whether the board worktree
  stays consistent without the sync timer.
- Decide who owns git sync in a headless session — the server on write, a
  separate process, or nobody (and the app reconciles later).
- Sequence against [[MCP-005]]: shipping the server outside `$INSTDIR` is close
  to a precondition for a standalone story, and the two should not fight.
- Add a `.mcpb` build target with the `--root` argument surfaced, since a desktop
  install has no project context to infer from.

## Verification

- [ ] With the app never launched, an agent can list, create, move and gate-check
      tickets, and the board is consistent afterwards.
- [ ] The git sync question is answered explicitly rather than left to the app.
- [ ] A `.mcpb` installs into Claude Desktop and connects to a chosen project
      root.
- [ ] Any change here is reflected in FRD-022 and the Connect install matrix.
