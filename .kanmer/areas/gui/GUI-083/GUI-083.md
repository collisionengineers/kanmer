## What

`.gitignore` ignores `.claude/skills/` but says nothing about the other
destinations Connect writes. `.gitignore` has **no entry at all** for `.agents/`,
`.grok/`, or `.codex/`.

Measured in this repo right now, after a Connect run during the HZN-003 auto run:

```
$ git ls-files .agents/
.agents/plugins/marketplace.json          <- tracked, belongs to the repo

$ git status --porcelain --untracked-files=all .agents/
?? .agents/mcp_config.json
?? .agents/skills/.kanmer-skills-version
?? .agents/skills/kanmer-auto/SKILL.md
?? .agents/skills/kanmer-closeout/SKILL.md
... (12 skill folders)
```

So a full copy of the skills tree is sitting untracked in the working directory of
the repo those skills are the source of.

## Why

`.claude/skills/` is gitignored precisely because it is an **install artifact**,
not source — the source of truth is `plugins/kanmer/skills/`. `.agents/skills/`
and `.grok/skills/` are the same artifact for different hosts, written by the same
`copySkills` code path. Ignoring one and not the others is an asymmetry that reads
as an oversight rather than a decision.

Two concrete harms:

1. **A `git add -A` commits a duplicate skills tree into the repo.** That is not
   hypothetical here — the tree exists on disk now, and the repo routinely has
   several agents working in parallel worktrees.
2. **It pollutes `git status` for every contributor who has ever clicked Connect**,
   which trains people to ignore untracked noise — and the next thing hidden in
   that noise will matter. During this run a stale-v2 `AGENTS.md` corruption was
   sitting in the same `git status` output.

The awkward part, and the reason this is a fix rather than a one-liner: **`.agents/`
is partly tracked.** `.agents/plugins/marketplace.json` is a real repo file. So the
ignore rules must be specific to what Connect writes — `.agents/skills/`,
`.agents/mcp_config.json` — and must not swallow the marketplace manifest.

## Approach

- Ignore exactly what Connect writes, derived from the `copySkills` and
  `configFile` destinations in `apps/gui/src/main/providers.ts` rather than from a
  guessed list. Do not blanket-ignore `.agents/`.
- Check `.codex/` the same way: `<repo>/.codex/config.toml` is a Connect artifact
  and is currently untracked and unignored too. Decide deliberately whether a
  project-scoped codex registration is meant to be committed (it may legitimately
  be, since it is per-project config a team could share) — and if so, say why in
  the FRD rather than leaving the asymmetry unexplained.
- Add a check that every `copySkills` destination in `providers.ts` has a
  corresponding ignore rule, so a new provider cannot reintroduce this.

## Verification

- [x] After a Connect for each provider, `git status --porcelain` in a clean repo
      is empty.
- [x] `.agents/plugins/marketplace.json` is still tracked and still shows in
      `git ls-files`.
- [x] A test fails if a `copySkills` destination is added to `providers.ts`
      without an ignore rule.
- [x] The `.codex/` decision is recorded with its reason, either way.

## Outcome

Shipped in [[PR #50]] (merge commit `6c3ae7745bc0b224b716a2646c8be8871ed175ce`).
`.gitignore` now covers every Connect-written destination derived from
`providers.ts` (`.agents/skills/`, `.agents/mcp_config.json`, `.grok/skills/`,
`.codex/config.toml`, `.grok/config.toml`, `opencode.json`), leaving
`.agents/plugins/marketplace.json` tracked. A regression test in
`apps/gui/src/main/providers.test.ts` fails if a future `copySkills`
destination ships without a matching rule — demonstrated failing on a
deliberately-added fake destination before being trusted. `.codex/config.toml`
(and `opencode.json`) were deliberately decided to stay gitignored rather than
committed, recorded as FRD-012 R1c: the *location* question (ADR-0007) is
separate from *today's content* being machine-specific and therefore unfit to
commit. Mid-execute, discovered GUI-079 had already landed on `origin/main`
(grok's `configPath` moved to `.grok/config.toml`, ADR-0012/0013) — the
worktree's actual `providers.ts` was re-read and the ignore rules verified
against it, not against the stale pre-fetch assumption. Verified on merged
main in the main checkout: `git status --porcelain` clean of Connect
artifacts, full rail green (see proof.md).
