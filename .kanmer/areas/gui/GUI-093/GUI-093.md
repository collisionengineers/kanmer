## What

On the real v0.3.3 release, `electron-builder --win --publish always` **created**
the GitHub release, uploaded the installer, then tried to create the release
**again** for the next artifact and got:

```
⨯ 422 Unprocessable Entity
POST https://api.github.com/repos/collisionengineers/kanmer/releases
{ "message": "Validation Failed",
  "errors": [ { "resource": "Release", "code": "already_exists",
                "field": "tag_name" } ] }
```

`electron-builder` then aborted the whole command. The result was a **published,
`Latest`-tagged release carrying only the installer** — no `.exe.blockmap`, and no
`latest.yml`. With no manifest, every existing client's update check hits a
release it cannot read.

## Why the safety net did not fire

[[GUI-066]] added exactly the right repair for this: verify every published asset,
re-publish once on a gap, re-verify, then refuse loudly. **It never ran.** It is
step 9 of the script; the failure was inside step 9's publish call, which threw
and took the process with it.

So the release rail has a repair step that is unreachable in precisely the failure
it was written for. That is the defect here — not GUI-066's logic, which worked
perfectly when invoked by hand afterwards and produced a correct release.

## Approach

- **Make verification reachable after a failed publish.** Wrap the publish so a
  non-zero exit still falls through to asset verification and the bounded repair,
  rather than aborting. A publish that half-succeeded is the single most important
  case to verify, and currently the only one that skips verification.
- Investigate the 422 itself. It looks like a race inside `electron-builder`'s
  publisher: several artifacts each resolve "get or create release" concurrently
  and more than one attempts the create. `EP_GH_IGNORE_TIME` is already set and is
  not the cause here — the release was seconds old. Worth checking whether
  publishing artifacts serially avoids it.
- Note the tag is pushed **before** publishing (deliberately, `14f2715`), so by the
  time this fails the tag is already public. Refusing is right; the repair should
  still be attempted first.

## Manual repair used on v0.3.3, for reference

Uploaded the two missing assets with `gh release upload --clobber`, using GitHub's
dashed naming (`Kanmer-Setup-0.3.3.exe.blockmap`) rather than the on-disk spaced
names, then re-ran `verify-release-assets.mjs 0.3.3` until it passed. Also had to
correct `latest.yml` — see the sibling ticket on the double pack.

## Verification

- [x] A publish that fails partway still runs asset verification and the bounded
      repair, and only then refuses.
- [x] Simulated: a release with the installer uploaded but no manifest is detected
      and repaired by the script itself, without hand intervention.
- [x] The 422 either no longer occurs, or is handled as "release already exists,
      reuse it" rather than as a fatal error.
