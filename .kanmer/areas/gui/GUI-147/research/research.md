# Research — GUI-147: Claude Connect stages the marketplace in a deleted temp dir and never upgrades an installed plugin

## Question

Why does Claude Code keep serving the previous Kanmer skills/MCP version after Connect reports success, and what is the smallest change that (a) stages the marketplace somewhere stable, (b) forces an already-installed plugin to the bundled version, and (c) surfaces that version next to the skills stamp?

## Findings

- `stageClaudeMarketplaceRoot()` (`apps/gui/src/main/connect.ts:195-230`) copies `.claude-plugin`, `.agents`, `plugins/kanmer` into `mkdtemp(tmpdir(), "kanmer-claude-marketplace-")`, binds `KANMER_BOARD_BRANCH` into the staged `claude.mcp.json`, and returns the temp path.
- The install loop (`connect.ts:581-604`, function `installSkills`) runs `provider.install.marketplaceCommands(stagedRoot ?? marketplaceRoot())` — for claude that is `claude plugin marketplace add <staged>` then `claude plugin install kanmer@kanmer` (`apps/gui/src/main/providers.ts:874-877`) — then a `finally` block unconditionally `rm(stagedRoot, { recursive: true, force: true })`s it (`connect.ts:~601-604`). Claude Code's `known_marketplaces.json` records `installLocation` as that now-deleted directory, so `/reload-plugins` reports `cache-miss` — confirmed live: `~/.claude/plugins/known_marketplaces.json` currently shows `"kanmer": { source: {source:"directory", path: "C:\\Users\\Alex\\AppData\\Local\\Kanmer\\claude-marketplace"} }` only because of the hand-repair; before that it pointed at a deleted temp dir.
- `claude plugin install <name>` is a no-op when already installed (measured: `claude plugin install --help` gives no upgrade semantics; `claude plugin update <plugin>` is the only verb that reinstalls an existing plugin, but its help text says "restart required to apply"). `~/.claude/plugins/cache/kanmer/kanmer/` currently holds `0.3.12`, `0.3.3`, `0.4.0` side by side — stale cache generations are harmless; only `installed_plugins.json`'s recorded version and `claude plugin list`'s report matter.
- `claude plugin list` (live, read-only) currently reports `kanmer@kanmer  Version: 0.4.0  Scope: user  Status: enabled` — this is the hand-repaired state, not what Connect itself produces today.
- `claude plugin marketplace --help` verbs: `add <source>`, `update [name]`, `remove|rm <name>`, `list`. `claude plugin --help` verbs: `install|i <plugin>`, `uninstall|remove <plugin>`, `update <plugin>`, `list`. No verb upgrades a marketplace-tracked plugin as a side effect of `install`.
- `known_marketplaces.json` (`~/.claude/plugins/known_marketplaces.json`, cross-platform under `homedir()`, not `%LOCALAPPDATA%`) keys by marketplace name and records `{source:{source:"directory",path}, installLocation, lastUpdated}` — reading it is a reliable, read-only way to decide add-vs-update without depending on CLI stderr text (which Connect must not parse for control flow; only the failure *message* is surfaced verbatim per MCP-013's existing contract).
- `installed_plugins.json` (`~/.claude/plugins/installed_plugins.json`, same home root) keys by `<plugin>@<marketplace>` → array of `{scope, installPath, version, installedAt, lastUpdated}`. Reading it tells Connect whether `kanmer@kanmer` scope `user` is already installed, so it can choose uninstall+install over a bare install.
- `pluginRoot()`/`marketplaceRoot()` (`connect.ts:156-188`) already encode the MCP-013 invariant `marketplaceRoot() + "/plugins/kanmer" === pluginRoot()`; nothing here needs to change about how the *bundled* source tree is located, only where it is staged and what happens after `add`/`install`.
- `bundledSkillsVersion()` (`connect.ts:~230-240`) already reads `plugin.json`'s `version` field (currently `0.4.0`) — this is the exact value Connect must require `claude plugin list` to report back.
- There is **no** existing Node-side resolver for `%LOCALAPPDATA%` as an absolute path. Every existing reference (`providers.ts:81`, AGENTS.md §4/§10/§13, `installer.nsh`) is a literal `%LOCALAPPDATA%`/`!LOCALAPPDATA!`/`$LOCALAPPDATA` token expanded by `cmd.exe`/`powershell.exe`/NSIS at runtime, never by Node. Electron's `app.getPath(...)` has no `localAppData` key; the only Node-side equivalent is `process.env.LOCALAPPDATA` (Windows-only), which is exactly what `installer.nsh` and the NSIS `customInstall` macro treat as the runtime-root parent for `%LOCALAPPDATA%\Kanmer\mcp` and `%LOCALAPPDATA%\Kanmer\bin` (AGENTS.md gotchas #4/#10/#13; `scripts/check-updater-package.mjs:209,270`). `%LOCALAPPDATA%\Kanmer\claude-marketplace` is therefore the natural sibling of those two installer-owned roots, not a new naming scheme.
- `skillsStatus()` (`connect.ts:626-669`, IPC `getSkillsStatus`) returns `scope:"marketplace", installedVersion:null, updateAvailable:false` unconditionally for every marketplace-kind provider (both codex and claude) — this is the exact function the brief means by "the GUI's staleness read", and it already flows end-to-end through `apps/gui/src/shared/ipc.ts` (`SkillsStatus`), `preload/index.ts`, `renderer/src/lib/client.ts`, and is rendered in `apps/gui/src/renderer/src/components/Settings.tsx:553-575` (the `updateAvailable` badge + "Update skills" button next to each provider row). No new IPC channel or type field is needed — only populating the existing fields for `id==="claude"`.
- `disconnectAgent()` (`connect.ts:1315-1367`) for a marketplace-kind provider currently only runs `provider.register.removeCommands()` (for claude: `claude mcp remove kanmer -s project|-s user`, i.e. the MCP registration only) and never touches the marketplace or the installed plugin. FRD-012 R4 (`docs/functional/frd/FRD-012-connect.md:33`) requires disconnect to reverse exactly what connect wrote; today connect writes nothing marketplace-durable to reverse, because the temp dir already vanished at connect time. Once staging is durable, disconnect must add `claude plugin marketplace remove kanmer` before the stable directory can safely be removed (R1a: only remove what this provider owns).
- Test precedent: `connect.test.ts` already injects a `probeRunner: CodexProbeRunner` through `ConnectOptions` (`connect.ts:710-712`) to make the codex probe path testable without a real `codex` binary, and drives the marketplace-command loop through synthetic `testProviders` (`connect.test.ts` `useProvider` helper, ~845-895) with real subprocess scripts (`failingCommand`/`succeedingCommand`) rather than stubbing `exec`. The same seam (an injectable runner in `ConnectOptions`, defaulting to the real `execAsync`/`fs` reads) is the only way to unit-test claude-specific add-vs-update / install-vs-uninstall / verify branching without a real `claude` CLI or mutating the operator's real `~/.claude` state.

## Implications

- The fix is bounded to `apps/gui/src/main/connect.ts` (staging location, install sequencing, verification, skills-status read) plus a small `providers.ts` touch only if the claude `install` spec needs a new optional hook; `apps/gui/src/renderer/src/components/Settings.tsx` needs at most a copy fix (marketplace-scope wording), not new state.
- Add-vs-update and install-vs-uninstall decisions must be made from the two on-disk JSON files (`known_marketplaces.json`, `installed_plugins.json`), not from parsing CLI stderr — deterministic, and does not require running a mutating `claude plugin` command during research/planning.
- Verification after install must shell out to `claude plugin list` (read-only) and parse the `kanmer@kanmer` block's `Version:` line, comparing against `bundledSkillsVersion()`; mismatch is a Connect failure carrying a pasteable fallback command, per MCP-013's existing failure-reporting contract (`SkillsInstallOutcome.failure`).
- The `%LOCALAPPDATA%` resolution needs a small Node helper (`process.env.LOCALAPPDATA` with a `homedir()`-based fallback for non-Windows test runs) — there is no existing one to reuse, but the naming convention (`%LOCALAPPDATA%\Kanmer\<subdir>`) is already established for `mcp` and `bin` and documented in AGENTS.md.
- The existing `stagedRoot` `finally { rm(...) }` in `installSkills` must be deleted outright (not conditioned differently) — it was solely there for the temp-dir lifecycle; codex's `stagedRoot` is always `undefined` so removing it changes no other provider's behaviour.
- Codex's marketplace flow is unaffected: it uses `marketplaceRoot()` directly (no staging), stays on the declarative `marketplaceCommands()` list, and this ticket's scope is Claude only (per the ticket body and outcome section).

## Open questions

None remain unresolved for planning — the operator-approved outcome section fixes the location, upgrade mechanism, and verification requirement. One implementation-time confirmation is deferred to `kanmer-execute` rather than blocking planning: the exact `claude plugin marketplace add` behaviour when a marketplace of the same name is already registered at the same path is not exercised here (running it would mutate the operator's real Claude install, which this research/plan phase is forbidden to do) — the plan avoids needing that behaviour at all by deciding add-vs-update from `known_marketplaces.json` before ever invoking the CLI, so no CLI trial-and-error is required.
