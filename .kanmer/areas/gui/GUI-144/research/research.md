# Research — GUI-144

## Question

How does the GUI present the FRD-029 named endpoint registry (health, identity, location, sync, policy, controllers/workspaces) and the selected project's active-controller state, and write registry entries, without becoming a second global board and without letting the renderer choose arbitrary paths?

## Findings

1. **Registry contract lives in `packages/mcp-server/src/project-registry.ts` (MCP-054, origin/main e903289e).** File shape `{ schema: 1, endpoints: { <name>: { boardRoot, repoRoot?, boardBranch?, policy? } } }`; name regex `^[a-z0-9][a-z0-9._-]{0,63}$`; absolute paths; location `KANMER_ENDPOINT_REGISTRY` (absolute) else `~/.kanmer/endpoints.json`. `observeEndpoint` builds a throw-away read-only `KanmerStore`, never `init()`s, health `ok|unassigned|missing-board|invalid|error`, controllers/workspaces from `claimState` over taken tickets. `writeRegistry` is atomic (tmp + rename) but `upsertEndpoint` is an unlocked read-modify-write (reviewer F-001 on MCP-054).
2. **The GUI cannot import that module in a typed way today.** `apps/gui` depends only on `@kanmer/core`; `packages/mcp-server` emits no `.d.ts` (tsup without `dts`, no `exports` map) and `apps/gui/tsconfig.node.json` is `composite: true`, so a relative source import of `../../packages/mcp-server/src/...` fails TS6307 unless `include` is widened. Fixing this needs a server-package change (tsup `dts`, package `exports`), which this lane must not make. Source: `apps/gui/package.json`, `apps/gui/tsconfig.node.json`, `packages/mcp-server/tsup.config.ts`, `packages/mcp-server/package.json`.
3. **Every observation input already exists in the GUI main process.** `@kanmer/core` `KanmerStore` (`exists`, `detectFormat`, `getBoardWithSource`, `getProject` → `ProjectRecord{project_id, board_id, origin}`, `listItemsWithWarnings`, `paths.repoRoot`), `claimState` + `DEFAULT_CLAIM_EXPIRY_MINUTES` (types.ts), `apps/gui/src/main/kanmerGit.ts` `inspectBoardSync(boardRoot, branch)` (returns `{remote, ahead, behind, localSha, remoteSha}`) and `inspectBoardWorktree` (actual branch), `remoteAccess/identity.ts` `canonicalProjectPath` + `remoteProjectIdentity` (byte-compatible `kanmer-proj-v1` fingerprint). Implication: a GUI-side `projectRegistry.ts` mirroring the file contract is fully implementable without the server package; the risk is shape drift, mitigated by a contract test that loads the server module by runtime path (untyped `await import`) and checks `parseRegistry`/`validateEntry` accept the GUI's output.
4. **Existing cross-project GUI pattern is `RemoteSection` in `Settings.tsx` (line 1137) + `RemoteAccessManager.overview()`.** Overview cards for every registered project, selected project marked "Selected project actions are below", others only get "Open project". IPC handlers in `index.ts` 1038-1086 use `assertTrustedRemoteSender` + `assertRemoteProjectId` and derive identity from the open `ProjectContext` (`remoteIdentity(ctx)`), never from renderer-supplied paths. Same pattern for this ticket: registry writes take a `projectId` that must be an open tab (`requireCtx`), boardRoot/repoRoot come from `ctx.boardRoot`/`ctx.sourceRoot`.
5. **Folder picker flow.** `CH.pickProject` (`index.ts` 1027) shows `dialog.showOpenDialog` and returns the chosen root; the renderer then calls `openProject(root)`. "Add a project to the registry" therefore = open it via the standard picker (existing) then register the open tab; no new path-carrying IPC.
6. **Serialisation primitives.** `settings.ts` `withSettingsFileLock` is an in-process promise queue; `RemoteAccessManager` uses `enqueue` + `withSettingsLock`. The GUI is the sole registry writer (MCP never writes; MCP-054 gotcha 16), so an in-process queue around read-modify-write + atomic rename resolves F-001 for this writer; a stale-read guard (re-read and compare mtime/text before rename) protects against a concurrent operator edit.
7. **Active-controller state on main.** `Item` has `assignee`, `taken_at`, `claim_expires_at`, `claim_controller`; `claimState(item, now, minutes)` returns `unclaimed|live|expired`. CORE-115 (`.worktrees/core-115`, unmerged) adds optional `lease_id`, `lease_revision`, `lease_controller_run`, `lease_worker_run`, `lease_workspace`, `lease_provider`, `lease_phase`, `lease_heartbeat_at`. Read defensively as `(item as Record<string, unknown>).lease_*` strings so the view follows CORE-115 without a type dependency.
8. **Docs.** `docs/manual/connect.md` "Named endpoint registry" subsection says "The app's project-health view of this registry is tracked separately (GUI-144)"; `docs/manual/settings.md` tours Settings tabs (five listed; remote/openai/dispatch already exist unlisted). `npm run build:manual` regenerates `apps/gui/src/renderer/src/manual/chapters.generated.ts`; `check:manual` is in `npm test`.
9. **Tests.** GUI uses vitest (`vitest run --no-file-parallelism`); main tests mock `electron` (`settings.test.ts`, `index.sync.test.ts`); renderer tests use `// @vitest-environment jsdom` + testing-library with `window.kanmer` stubbed (`Settings.remote.test.tsx`).
10. **FRD-029 boundary.** "The GUI presents the same selected-project boundary rather than a second global board"; cross-project ops observational. Implication: the registry view shows health only; the only per-endpoint action for a non-selected project is "Open project" (switch selection); registry entry edits are metadata (name/policy/remove), never board mutations.

## Implications for this ticket

- Build `apps/gui/src/main/projectRegistry.ts` (contract mirror + observer + serialised writer), IPC `registry*` channels, a `ProjectRegistrySection` renderer component under a new Settings tab "Projects", and a contract test against the server module by runtime import.
- Registry file location honours `KANMER_ENDPOINT_REGISTRY` exactly like the server so both read the same file.
- Bound/selected marking uses `project_id` first, `kanmer-proj-v1` fingerprint fallback (`endpointMatches` semantics).
