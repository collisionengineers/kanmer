# Research — MCP-025 session lifecycle and test model

## Session registry

Use an in-memory registry owned by the HTTP host. A registry entry should contain only operational protocol state:

- cryptographically random session id generated by the SDK/host;
- authenticated principal/token fingerprint supplied by the authorizer (opaque; never the token);
- MCP server/transport instance or SDK-required session object;
- created/last-active timestamps;
- active request count/cancellation handles;
- closing state.

Do not store ticket content, prompts, bearer credentials, or project paths per session. The host itself is already bound to one immutable project.

## Lifecycle states

`new → active → closing → closed`, with expiry as a closing reason. Unknown, closed, expired, cross-principal, or malformed session ids are rejected according to the pinned MCP transport semantics. A request without a session header is permitted only where the initialization flow/spec allows creating a session.

Registry requirements:

- maximum total sessions and maximum per principal;
- idle TTL using a monotonic clock where practical;
- bounded sweep interval with unref'd timer;
- touch activity only after an authenticated valid request;
- idempotent close;
- removal on DELETE, transport close callback, idle expiry, auth rotation signal, and process shutdown;
- no sessions survive restart.

MCP-026 owns the real principal and rotation signal; define injectable interfaces now.

## Request ordering and concurrency

Honor the SDK's session transport rules. Do not allow concurrent initialization on one session. Apply a bounded global/per-session in-flight request limit before expensive tool execution. Reads may run concurrently if the server/store supports it; mutations retain existing store/version/gate protections and should not gain a new transport-specific transaction model.

Cancellation/disconnect must release in-flight counters and allow the SDK to cancel work where supported. A dropped HTTP connection must not leave the registry permanently busy.

## Limits and errors

Define configuration defaults in one module with validation:

- loopback host only;
- port `0` allowed for tests/parent allocation, explicit range otherwise;
- maximum body/header sizes;
- request/header/keepalive timeouts;
- maximum sessions and in-flight requests;
- idle TTL and graceful shutdown timeout.

Configuration failure is a startup error with no listener. Limit rejection occurs before tool dispatch and returns ordinary HTTP/protocol errors, not Kanmer success envelopes. Do not leak whether a token/session exists in unauthenticated diagnostics.

## Shutdown

On SIGINT/SIGTERM or parent stop:

1. mark host stopping and reject new sessions;
2. stop accepting new connections;
3. close/abort active sessions through SDK hooks;
4. wait up to configured grace period for in-flight requests;
5. destroy remaining sockets/transports;
6. clear expiry timers and registry;
7. close listener;
8. emit one structured stopped event and exit.

Make cleanup idempotent so signal, parent IPC, startup failure, and test teardown can converge safely.

## Test harness

Build tests around a real loopback listener on port 0 and disposable board root. Use the official MCP client Streamable HTTP transport where possible and raw HTTP calls for method/header/error edges.

Required scenarios:

- production host refuses startup with no authorizer;
- non-loopback bind rejected;
- valid injected test authorizer initializes and lists remote-safe tools;
- stdio discovery stays unchanged;
- remote discovery omits only explicit dispatch tools;
- POST initialization and session header semantics;
- valid subsequent POST/GET/DELETE;
- unknown, malformed, expired, and cross-principal session;
- duplicate/concurrent initialization;
- protocol-version/content-type/malformed JSON handling delegated correctly;
- `404`, `405`, body limit, timeout, session cap, in-flight cap;
- path containing spaces/project fingerprint readiness record;
- client disconnect/cancellation releases counters;
- DELETE and idle expiry dispose transport/server exactly once;
- shutdown with idle and active sessions, forced timeout, repeated close;
- no token/session/document content in logs;
- one project for process lifetime and request cannot select another root.

Use fake clock only for registry unit tests; run at least one real short-TTL integration case without sleeps longer than necessary. Do not use public network/tunnel.

## Compatibility tests

Snapshot or structurally compare local stdio tool names/input schemas before and after refactor. Run existing stdio protocol/discovery smokes. If generated plugin bytes change, isolated `plugin:check` from MCP-018 must pass and provider registration command remain unchanged.

## Evidence

Record the exact SDK version/API selected, loopback address/allocated endpoint, session lifecycle traces with redacted ids, remote/local tool-set diff, shutdown proof, test counts, and a clean real-board working tree. No public URL or bearer secret is part of this ticket's proof.
