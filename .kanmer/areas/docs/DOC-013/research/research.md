# Research — DOC-013: provider-neutral remote-access manual

## Question

What is the canonical manual surface, and what does the shipped remote-access implementation actually support today? The answer must separate the accepted provider-neutral contract from the Cloudflare-only appendix, identify the exact headless/auth lifecycle that can be documented, and expose any evidence that must wait for MCP-027, GUI-095, or MCP-028.

## Findings

- **The accepted boundary is provider-neutral and one-project scoped.** FRD-025 requires opt-in Streamable HTTP at `/mcp`, mandatory bearer authentication before MCP parsing/session work, loopback binding, one immutable project fingerprint per host process, one central remote exposure policy, and existing board/document/expected-project gates. Background dispatch is excluded remotely. ADR-0017 makes Streamable HTTP the sole remote transport, keeps stdio unchanged, and makes the tunnel an adapter rather than a protocol implementation. Sources: `docs/functional/frd/FRD-025-remote-access.md`, `docs/architecture/adr/ADR-0017-streamable-http-remote-access.md`.

- **The current manual is a generated in-app chapter set, not a separate index folder.** `docs/manual/` currently contains 19 authored chapters. `scripts/build-manual.mjs` is the chapter index and compiles them into the committed `apps/gui/src/renderer/src/manual/chapters.generated.ts`; `npm run check:manual` passes on the current tree. There is no `docs/manual/README.md`, and no existing `scripts/verify-docs.mjs`, `scripts/verify.mjs`, `verify:docs`, or root `verify` script. Existing chapter guards reject top-level body H1s, specification vocabulary, `docs/` paths, requirement-list shapes, and short prose. Sources: `scripts/build-manual.mjs`, `apps/gui/src/renderer/src/manual/manual.test.ts`, package root `package.json`, read-only command `node scripts/build-manual.mjs --check`.

- **The existing Connect chapter is specifically the OpenAI Secure MCP Tunnel stdio path.** `docs/manual/connect.md` documents `tunnel-client`, an OpenAI control-plane tunnel, and the installed stdio server. It explicitly says this does not produce a provider-neutral stable MCP URL. It must remain the separate DOC-010/GUI-104 route; the new manual must link to it rather than merge its commands or credentials into the Cloudflare path. Source: `docs/manual/connect.md`, plus DOC-013 links to [[DOC-010]] and [[GUI-104]].

- **MCP-025 exposes an opt-in loopback HTTP host using the official SDK.** `packages/mcp-server/package.json` ships `kanmer-mcp-http` (no positional configuration). `http-cli.ts` requires the protected `KANMER_HTTP_TOKEN_FILE` environment reference, rejects raw token arguments/environments, starts the host, prints only safe ready metadata, and closes on SIGINT/SIGTERM. `http.ts` defaults to `127.0.0.1`, generates an endpoint ending `/mcp`, reports `projectFingerprint`, `authRequired: true`, and supported protocol versions, and owns bounded in-memory sessions with idle expiry and shutdown/rotation cleanup. POST/GET/DELETE handling and protocol framing are delegated to the official MCP SDK. Sources: `packages/mcp-server/src/http-cli.ts`, `packages/mcp-server/src/http.ts`, MCP-025 proof.

- **MCP-026’s supported bearer workflow is protected-file based and secret-safe.** `kanmer-mcp-token <new-token-file>` creates an exclusive protected file and prints only a fingerprint; `loadTokenFile`/the internal material loader validates regular non-symlink files, bounded size, no-follow identity, and POSIX mode where meaningful. The authorizer accepts only a standard `Authorization: Bearer` header, rejects missing/wrong/query/cookie credentials before body/session handling, and token rotation/revocation invalidates sessions. The 32-byte generated token is URL-safe and represented in the header only at runtime. GUI OS-backed delivery is not present in the current GUI tree; that remains GUI-095 scope. Sources: `packages/mcp-server/src/http-auth.ts`, `packages/mcp-server/src/http-secret.ts`, `packages/mcp-server/src/remote-token-cli.ts`, MCP-026 proof.

- **MCP-021’s first adapter is narrowly Cloudflare named-credentials mode.** `TunnelAdapter` now exposes provider-neutral `doctor`, `start`, `getStatus`, `stop`, diagnostics, and optional status subscription. The shipped Cloudflared adapter accepts one operator-provisioned credential-file reference, validates an absolute executable and version, generates one exact configured hostname → loopback `/mcp` ingress plus a terminal 404 rule, uses direct `shell: false` spawning, `--no-autoupdate`, loopback metrics/readiness, bounded redacted logs, and owned shutdown/restart cleanup. It does not create accounts/DNS/tunnels, download/update the executable, use Access, use Quick Tunnels, use remote-managed token mode, host a Worker, or promise public acceptance. The remote host performs a required authenticated local MCP initialize/DELETE callback before spawning the provider and passes only opaque project/auth metadata—not bearer material—to the adapter. Its public verification dimension remains unknown until a public client/doctor run. Sources: `packages/mcp-server/src/tunnels/types.ts`, `tunnels/cloudflared.ts`, `tunnels/cloudflared-config.ts`, `tunnels/cloudflared-validate.ts`, `remote-host.ts`, MCP-021 proof/report.

- **The current headless remote command is environment-driven, not a documented flag-based doctor/config CLI.** `kanmer-mcp-remote` accepts no command-line arguments and requires `KANMER_TUNNEL_PROVIDER=cloudflared`, `KANMER_HTTP_TOKEN_FILE`, `KANMER_TUNNEL_HOSTNAME`, `KANMER_CLOUDFLARED_EXECUTABLE`, `KANMER_CLOUDFLARED_TUNNEL_ID`, and `KANMER_CLOUDFLARED_CREDENTIALS_FILE`. It authenticates against the local `/mcp` endpoint and closes the diagnostic session before starting the tunnel, then emits redacted JSON status/ready lines and owns signal-driven shutdown. This is the only exact remote CLI behavior available to quote now. Source: `packages/mcp-server/src/remote-cli.ts`, `remote-cli.test.mjs`, `smoke-remote.mjs`.

- **MCP-027 is not implemented yet, so its doctor contract is planned rather than shipped.** The ticket is Preparing with no implementation files under `packages/mcp-server/src/doctor/`. Its files/plan define the intended modes `config|local|public`, exits 0/1/2, and 26 stable ids: `PROJECT_CONFIG_VALID`, `REMOTE_CONFIG_VALID`, `SECRET_REFERENCE_VALID`, `TUNNEL_EXECUTABLE_VALID`, `TUNNEL_CONFIG_VALID`, `LOCAL_STATUS_READY`, `LOCAL_BIND_LOOPBACK`, `AUTH_MISSING_REJECTED`, `AUTH_WRONG_REJECTED`, `AUTH_VALID_ACCEPTED`, `MCP_INITIALIZE_LOCAL`, `PROJECT_FINGERPRINT_LOCAL`, `REMOTE_TOOL_POLICY_LOCAL`, `SESSION_CLOSE_LOCAL`, `TUNNEL_PROCESS_READY`, `PUBLIC_DNS_RESOLVES`, `PUBLIC_TLS_VALID`, `PUBLIC_ROUTE_NO_REDIRECT`, `AUTH_MISSING_PUBLIC_REJECTED`, `MCP_INITIALIZE_PUBLIC`, `PROJECT_FINGERPRINT_PUBLIC`, `REMOTE_TOOL_POLICY_PUBLIC`, `SESSION_CLOSE_PUBLIC`, `LOCAL_PUBLIC_CONSISTENT`, `DIAGNOSTIC_REDACTION`, and `NO_BOARD_MUTATION`. These ids and repairs must be re-read from the merged implementation before the troubleshooting matrix is written; they must not be presented as an already-shipped command or output. Source: MCP-027 item/files/plan and the current source tree.

- **GUI-095 is not implemented yet, so exact UI labels and storage/lifecycle behavior are unavailable.** The GUI currently has Settings tabs for Board, Profiles, Appearance, Git, and agent Connect only; `apps/gui/src/main/` and `apps/gui/src/renderer/src/components/` have no Remote Access implementation. GUI-095 still owns project-scoped Cloudflare configuration, secure bearer delivery, status/action/error contracts, multi-project isolation, auto-start/quit behavior, and doctor rendering. The manual must be updated from that ticket’s merged implementation/tests, not from the current Settings labels or DOC-013’s proposed steps. Sources: `apps/gui/src/renderer/src/components/Settings.tsx`, `apps/gui/src/shared/ipc.ts`, GUI-095 item.

- **MCP-028 is the only planned public acceptance evidence, and it does not exist yet.** Its boundary is a disposable Cloudflare Worker as an external MCP client only: bearer in a Worker secret binding, public HTTPS `/mcp`, normal MCP initialize/project/tool checks, a disposable ticket lifecycle, redacted evidence, and teardown. It is not a hosted Kanmer server, proxy, or relay. No public Cloudflare route was created by MCP-021, so DOC-013 must not claim public DNS/TLS/remote-client success until MCP-028 proof is available. Source: MCP-028 item/plan, MCP-021 proof.

## Implications

- The canonical implementation surface for the in-app manual is `docs/manual/*.md` plus the `CHAPTERS` list and generated TypeScript artifact in `scripts/build-manual.mjs`; a new `docs/manual/README.md` should only be created if the implementer deliberately chooses it as the actual index. The existing Connect chapter should link to the new provider-neutral chapter and keep OpenAI Secure MCP Tunnel separate.
- The provider-neutral chapter can safely describe the accepted security/transport boundary and the current protected-file/headless command only. It must defer exact GUI labels, doctor output, and public verification claims to the merged MCP-027, GUI-095, and MCP-028 evidence.
- The Cloudflared appendix must document only locally managed named credentials, exact hostname-to-loopback routing, operator provisioning, and external executable/version checks. It must not suggest account/DNS automation, Access, Quick Tunnels, remote-managed token mode, Worker-hosted Kanmer, or executable auto-download.
- The troubleshooting matrix must be generated from the final MCP-027 registry and repair mappings, with each stable id exactly once. The ids listed in the current MCP-027 files are a planning contract, not evidence that the doctor exists.
- The plan/files documents assume a canonical docs verifier and `verify:docs`/root `verify` route, but no such verifier/script exists in the current checkout. DOC-013 must either create and wire that one canonical rail (without duplicating `check:manual`) or revise its planned surface before implementation; it must not silently claim an existing command.
- Examples should use obvious placeholders and synthetic test domains only. Bearer tokens, provider credential contents, user paths, account ids, session ids, raw logs, and real public hostnames must never enter the manual or generated in-app artifact.
- Manual verification must happen after predecessor implementation is merged: first re-read exact package bins/env/flags and GUI labels, then run disposable headless/GUI walkthroughs, then incorporate only redacted MCP-028 public evidence. The current tree’s `node scripts/build-manual.mjs --check` PASS proves only that the pre-remote 19-chapter artifact is current.

- Which exact GUI-095 navigation labels, secure-storage fallback, owner conflict, status, auto-start, rotate/revoke, and quit semantics ship?
- Does DOC-013 introduce `scripts/verify-docs.mjs` and `verify:docs`/root `verify`, or does another canonical docs rail get selected before implementation?

These are implementation-evidence dependencies, not requests for a new product decision; the plan must not silently assume them.
