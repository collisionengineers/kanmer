`FRD-002-requirement-profiles.md:29` still reads:

> **Open design question.** The only signal that distinguishes code-then-plan
> from plan-then-code is a document's first-write time against the **first
> commit on the ticket's branch** … deliberately left unresolved rather than
> half-built.

[[CORE-021]] researched it and it is now known-wrong twice over. Leaving the
paragraph standing means the next reader implements something that cannot work.

Replace it with the resolved answer:

1. **The timestamp comparison is unimplementable.** `setDoc` records no time —
   its `version` is a content hash. `syncBoard` commits the whole board in one
   `git add -- .kanmer` per sync, so every document written between two syncs
   shares a commit time, which with autosync off can post-date the code. Git
   does not carry mtimes.
2. **The branch check works but is aimed wrong.** The correct formulation is
   commits *unique* to the branch — `rev-list --count <branch> --not <every
   other ref>` — base-free and measured across seven scenarios. (The obvious
   `rev-list --count <branch>` returns the whole inherited history: **147** on a
   fresh branch in this repo.) It still misses the real case: code written in
   the main checkout before the branch exists, which is exactly how this repo's
   own tickets went wrong.
3. **No gate proves causation, only sequence.** A plan written first and then
   ignored passes anything mechanical. Review catches that or nothing does — and
   the FRD should say so, because a gate that claims more than it delivers is
   one people route around.

Also note the cost that decided it: the check would put the first subprocess
into `@kanmer/core`, which is bundled into the shipped MCP server, and cost two
git spawns per GUI drag.
