## What

`apps/gui/src/main/kanmerGit.test.ts` fails on `origin/main`, non-deterministically —
a **different test each run**. Observed both of:

- `renameBoardBranch > keeps the history, the path and the remote consistent`
- `ensureBoardWorktree reconciliation > moves a worktree left on the old branch onto the configured one`

## Why it happens

Every test in the file shells out to real `git` and takes **4.6–8.7 s** on this
machine, against vitest's **5 s** default `testTimeout`. Whichever test loses the
race times out; the `afterEach` at `kanmerGit.test.ts:49` then fails a second time
because `rmSync` hits `EPERM` / `ENOTEMPTY` on the Windows temp dir that the
still-running git process is holding.

Timings from one run:

```
✓ renameBoardBranch > keeps the history, the path and the remote consistent   6610ms
✓ renameBoardBranch > is a no-op when the name already matches                5687ms
✓ renameBoardBranch > refuses a name that is already taken                    6726ms
✓ renameBoardBranch > renames locally even with no remote to push to          6583ms
× ensureBoardWorktree reconciliation > moves a worktree left on the old branch 8719ms
  -> Test timed out in 5000ms.
  -> EPERM, Permission denied: \\?\C:\...\Temp\kanmer-git-qhpgCr
```

Four of seven tests already run **longer than the timeout they are given** and pass
only because vitest's timer and the git process race. This is not really a flake —
the suite is mis-specified and happens to pass most of the time.

## Why this matters more than a flaky test usually does

`npm test` is **step 1 of the release GATE** (`scripts/release.mjs`) and item 1 of
`AGENTS.md §10`. A suite that fails ~50% of the time on Windows means the release
rail and the pre-merge checklist both fail for no real reason, which trains people
to re-run until green — and that habit is what lets a *real* failure through.

## Approach

- Give the file a `testTimeout` that reflects what it actually does (it drives real
  git through several commands per test) — per-file config or a third arg on each
  `it`. 30 s is not unreasonable for a suite doing real `git init`/`worktree add`.
- Make the `afterEach` cleanup non-fatal, or retry harder: on Windows a git process
  can still hold the temp dir when the test body returns. A cleanup failure should
  not be reported as a test failure — it is teardown noise, and here it doubles
  every real failure into two.
