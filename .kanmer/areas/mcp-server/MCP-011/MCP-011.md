## What

`plugins/kanmer/mcp/claude.mcp.json` and `plugins/kanmer/.mcp.json` both
register:

```json
{ "command": "node", "args": ["${PLUGIN_ROOT}/mcp/kanmer-mcp.cjs"] }
```

Three defects in two small files.

## Why

1. **No `--root`.** Falls back to cwd, which cannot find a worktree board — see
   [[MCP-010]]. This is what makes a marketplace install report an empty board.
2. **`"command": "node"` reintroduces the Node-on-PATH dependency** that
   `connect.ts:51` deliberately avoids by launching `process.execPath` with
   `ELECTRON_RUN_AS_NODE=1`. Two install paths, two different runtime
   assumptions, one of them undocumented.
3. **`plugin.json` says `0.1.0`; the repo is `0.3.2`.** `bundledSkillsVersion()`
   (`connect.ts:61`) reads that manifest, so `skillsStatus().updateAvailable`
   compares against a number nobody bumps and can never fire. The "Update
   skills" affordance is dead.

So the answer to "do we have a plugin marketplace" is yes — `.claude-plugin/`
and `.agents/plugins/` both exist — and installing from it does not give a
working board.

## Approach

- Ship with [[MCP-010]]: until discovery lands, dropping `--root` is not
  something these manifests can rely on.
- Decide the runtime question **with evidence, not assumption** ([[MCP-009]]'s
  rule): can the plugin path reach the Electron binary, or must it assume Node?
  Whichever it is, state it rather than leaving it implicit.
- Bump both `plugin.json` versions to the repo version, and add a rail check so
  they cannot drift again.

## Verification

- [x] `claude plugin install kanmer@kanmer` from the local marketplace, then
      `get_status` finds this repo's board — `rootSource: cwd-worktree`,
      `exists: true`, 155 tickets, no `--root`. **For Claude Code and grok.**
      For codex it cannot pass; see the Outcome.
- [x] `plugin:check` asserts both manifests' invocations resolve, and both
      `plugin.json` versions match the repo version — each new assertion also
      demonstrated failing on a deliberately broken manifest.
- [x] The runtime dependency is stated in FRD-012's install matrix (new **R6**),
      with the command that established each row.

## Outcome

Shipped in **PR #52**, squash-merged as `29bee81` on 2026-08-16.
<https://github.com/collisionengineers/kanmer/pull/52>

**The runtime question, answered by measurement and split by host.** Claude Code
2.1.233 and grok 0.2.111 both expand `${CLAUDE_PLUGIN_ROOT}` *and* the
shell-style `${VAR:-default}` form, so the plugin path **can** reach the Electron
binary: `mcp/claude.mcp.json` now uses `"command": "${KANMER_NODE:-node}"` with
`ELECTRON_RUN_AS_NODE=1`. Node stays the default; a Node-less machine points
`KANMER_NODE` at `Kanmer.exe`. Proven by *calling the tool*, which answered from
Electron 31.7.7. So `"command": "node"` had been an unnecessary assumption, not a
necessity.

**Three things shipped differently from the ticket, each recorded rather than
absorbed:**

1. **`.mcp.json` had never worked on codex, for a reason the ticket did not
   suspect.** codex 0.147.0 expands **no** `${…}` token anywhere in a plugin's
   MCP config — `${PLUGIN_ROOT}`, `${CODEX_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_ROOT}`
   and `${VAR:-default}` each tried beside a variable-free control that *did*
   launch — and passes the child no `PLUGIN_ROOT`. The server silently never
   started. [[MCP-009]] Finding 2 had seen `codex mcp list` print the token
   unexpanded and read it as cosmetic; that listing is exactly the proxy its own
   adjudication warns against, and calling the tool is what exposed it.
2. **The fix for codex is a relative `cwd`, and it is only a partial fix.**
   `"cwd": "."` resolves against the installed plugin root, so the server now
   starts — but discovery then runs from the plugin cache and correctly reports
   no board. Locating the script and finding the board need different working
   directories and codex expresses only one. A loud, actionable failure replacing
   a silent one is a real improvement and is the honest limit of these two files.
   **A codex plugin install still does not give you a working board**, and
   [[MCP-016]] (filed) owns the decision about whether to keep advertising the
   registration at all. `agy` cannot launch it under any manifest content, and
   it reads `.mcp.json` rather than `mcp/claude.mcp.json` — correcting MCP-009
   Finding 4a.
3. **The two manifests cannot be unified, and that is now enforced.** `cwd: "."`
   collapses grok's handshake outright; `${CLAUDE_PLUGIN_ROOT}` is inert on
   codex. `plugin:check` pins each shape to the host that requires it.

**The version freeze was unreachability, not staleness.** `installSkills()`
stamps copies with the same constant `bundledSkillsVersion()` reads, so installed
and bundled came from one number and `updateAvailable` could never be true.
[[GUI-080]]'s merged reconciliation (`9ac20af`, PR #41) had no way to be invoked
— its proof said so, and this is the ticket that makes it reachable. Verified by
a new test running the real `skillsStatus()` against the real manifest, which
fails on the baseline with `expected '0.1.0' to be '0.3.2'`.

**Rails, both kinds:** `plugin:check` *detects* drift (versions, both invocation
shapes, resolvable script paths, no `--root`) and `release.mjs` *prevents* it by
bumping both manifests with the two `package.json` files — detection alone would
have caught this drift and let the next release recreate it.

**Governing docs:** **FRD-012** gains **R6** (the plugin-runtime matrix, each row
with its establishing command) and **R7** (no manifest pins a board); R2's codex
bullet corrected. ADR-0009's method clause was followed, not amended. No new ADR.

**Follow-ups:** [[MCP-016]] (codex/`agy` plugin MCP — the decision), [[GUI-089]]
(a pre-existing `kanmerGit.test.ts` Windows flake, proven pre-existing by failing
on the parent commit). [[MCP-013]] was re-encountered throughout and deliberately
untouched; it did not block verification.
