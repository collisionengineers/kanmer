## What

`plugins/kanmer/.mcp.json` is read by **codex** and by **Antigravity (`agy`)**.
On neither host can it produce a working board, and [[MCP-011]] established that
this is an upstream limit rather than a manifest defect. Decide what Kanmer does
about it.

## Why — the measurement ([[MCP-011]] research, finding 3 and 5)

Against `codex` 0.147.0 and `agy` 1.1.13, each probed by **calling a tool**
through a real plugin install, always beside a variable-free positive control
that did launch:

- **Neither host expands any `${…}` token** in a plugin's MCP config —
  `${PLUGIN_ROOT}`, `${CODEX_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_ROOT}` and
  `${VAR:-default}` were each tried. codex also hands the child no `PLUGIN_ROOT`
  env var (`pluginEnv: {}`). So the shipped `${PLUGIN_ROOT}` form **silently
  never launched**, for either host, on any release to date.
- **codex does resolve a relative `cwd` against the installed plugin root**, so
  `{"command":"node","args":["mcp/kanmer-mcp.cjs"],"cwd":"."}` starts the server
  — MCP-011 shipped exactly that. But discovery then runs from
  `~/.codex/plugins/cache/kanmer-plugins/kanmer/<version>` and correctly reports
  no board. **Locating the script and discovering the board need different
  working directories, and codex offers no way to express both.**
- **`agy` is worse**: it reads `.mcp.json` at the plugin root regardless of what
  a manifest points at, copies it **verbatim** into
  `~/.gemini/config/plugins/<name>/mcp_config.json`, and joins a relative path
  to the *session* cwd. No committed manifest content can make it launch.

## Options

1. **Leave it** — the status quo after MCP-011.
2. **Stop advertising it** so the plugin honestly says skills-only for those
   hosts.
3. **Make Connect do it** — Connect already does.
4. **Upstream** — ask codex for `${PLUGIN_ROOT}` expansion.

## Verification

- [x] A decision recorded, with the option chosen and why
- [x] Whatever ships is checked by **calling a tool** on the host in question,

- [x] FRD-012 R6 updated to match whatever is decided

## Outcome

**Option 2 shipped** — the operator's decision, implemented and evidenced.
PR **#62**, squash-merged as **`8f4bdc1`** on 2026-08-17.
<https://github.com/collisionengineers/kanmer/pull/62>

The plugin no longer offers an MCP server on the hosts where it cannot deliver
one. Skills still ship to both; **Claude Code and grok are untouched**.

**Two removals, not one, and that is the finding that shaped the change.** codex
follows `.codex-plugin/plugin.json`'s `mcpServers` key, so removing the key stops
codex. `agy` never consults a manifest for MCP — measured directly: it reported
`source: "claude-code"` (i.e. `.claude-plugin/plugin.json`, which points at
`mcp/claude.mcp.json`) while copying the **root `.mcp.json`** verbatim into
`~/.gemini/config/plugins/kanmer/mcp_config.json`. So the file itself had to go.
Either removal alone would have left one host still advertising it.

**Profile changed `spike` → `fix` before implementation.** `spike` reaches Done
on `research` alone, which was right while this was purely a decision; it now
ships real change, and `spike` would have closed it with **no `proof`** — exactly
the artefact the ticket's own rule demands. `fix` is stricter on both boundaries,
so this added a gate rather than dodged one.

**Verified by calling a tool, never by reading a listing** (`proof`, on merged
main): a plugin-installed codex reports `NO_KANMER_MCP_TOOL` **and** all 12
skills, with `codex mcp list` now empty — the listing agreeing with the mechanism
is itself the change, since before it printed `enabled` for a server that gave
the agent nothing. `agy plugin install` reports `- mcpServers : skipped (not
found)` / `✔ skills : 12 processed`, and a bound session finds no `kanmer`
server beside a variable-free control server that *is* connected. The positive
control for the whole exercise: Connect's `<repo>/.codex/config.toml`
registration still answers `get_status` with a real board (162 tickets).
`~/.gemini/config` and `~/.gemini/skills` were snapshotted and `diff -r` is empty
after uninstall; `~/.codex` was never touched.

**A new trap, found here and now written into FRD-012 R6.3.** On `agy` the
plugin's entry and Connect's `.agents/mcp_config.json` entry are **both named
`kanmer`**. The first probe, run inside this repo, returned a perfectly healthy
board — from *Connect's* server — making the broken plugin registration look
fine. It is the `agy` analogue of `codex mcp list`, and MCP-011 had not seen it.
Every `agy` probe here was re-run from a Connect-free folder.

**Rails.** `plugin:check` inverts: it now asserts the *absence* of the codex
`mcpServers` key and of `plugins/kanmer/.mcp.json`, each with the reason and this
ticket id in the failure message — and, because inverting the codex rules left
nothing asserting what the plugin still *does* deliver, it also now requires both
manifests to keep `"skills": "./skills/"` and requires `mcp/claude.mcp.json` to
exist. All four demonstrated failing on a deliberately reverted tree before being
trusted.

**Governing docs:** **FRD-012** R2 (codex and Antigravity bullets), **R6** (matrix
rows plus the decision, its three-part reasoning, and the listing-vs-launch trap),
**R7** (narrowed to the one surviving config, with an explicit note that it does
not constrain Connect's project-scoped registrations), and the closing "Open
work" line. ADR-0009's method clause followed, not amended. **No new ADR** — a
requirement changed, not an architectural axis.
