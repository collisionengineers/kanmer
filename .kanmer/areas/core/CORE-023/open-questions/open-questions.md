# Open questions — CORE-023

## OPERATOR ONLY — these need the user, now, not at planning time

- [ ] **Q1 (scheduling). Do CORE-023 and [[MCP-012]] run in sequence or in parallel?**
      Both edit the same ~40 lines — `packages/mcp-server/src/index.ts:216-257`,
      the `get_status` handler — both add a top-level block to the same returned
      object, both rewrite the same tool `description`, both touch
      `tool-reference.md`, and both force a rebuild of the committed
      `plugins/kanmer/mcp/kanmer-mcp.cjs` (a 1.4 MB binary blob that cannot be
      merged and must be regenerated by hand on whichever lands second).
      They also share one unanswered build-rail decision (Q2). Research
      recommends **sequencing, MCP-012 first** — it is already through research
      and settled the rail constraints this ticket inherits. Confirm, or accept
      the conflict cost.

- [ ] **Q2 (release rail). Is baking a bundled fingerprint into the standalone
      MCP bundle acceptable, given `scripts/check-plugin-sync.mjs:57-76` demands
      the committed bundle be byte-identical to a fresh build?**
      A manifest derived purely from the source tree (skills path→sha256 + the
      canonical AGENTS block hash) is deterministic and passes the rail
      unchanged — unlike a timestamp or git sha, which MCP-012 found would break
      it permanently. The alternative is walking the filesystem at runtime, which
      has three different relative answers (packaged / plugin / dev) and is
      fragile. Research prefers the baked manifest; this is a change to a rail
      whose comments argue for caution, so it is the user's call — and it is the
      **same** call MCP-012 is asking. Answer it once, for both.

- [ ] **Q3 (scope). Does the GUI surface ship in this ticket, or a follow-up?**
      The GUI has no MCP client — it calls core directly — so a `get_status`
      field does not reach it. Its only staleness UI today is the format banner
      (`App.tsx:1103-1125`) and an "Update skills" button that, per research
      finding 3, can never light up. Adding the IPC handler + renderer surface
      roughly doubles the ticket. Splitting it means the GUI stays blind to
      everything except board format until the follow-up lands.

- [ ] **Q4 (a live bug found in passing). `apps/gui/src/main/agentsBlock.ts`
      carries a stale v2 block body — seven stages, `impact.md`, the deleted
      `-import` skill — and `connect.ts:18` imports it, so the GUI's Connect
      flow writes that stale block into every repo it touches, today.**
      Its own header comment says "Phase 8 reconciles the two on one canonical
      body"; that never happened. This is not CORE-023's work, but the detector
      will immediately flag every GUI-connected repo as stale — reporting a fault
      of Kanmer's own making as its first act. Fix it before/with this ticket
      (small: point `connect.ts` at the canonical body), or file it as its own
      ticket and accept the noise? A ticket should probably exist either way.

## To settle at planning (no user needed)

- [ ] **Q5.** The exact `state` vocabulary. Research proposes `behind` /
      `compensated` / `unstamped` / `unknown`. `compensated` is load-bearing:
      every board in existence has a `board.yml` without `questions-resolved`
      (injected at read time by `resolveProfiles`), and reporting that as
      `behind` would put a permanent warning on every `get_status` call.
- [ ] **Q6.** What exactly gets hashed for the skills tree — every file, or only
      `SKILL.md` per skill? Every file is more correct and catches template and
      reference drift; `SKILL.md`-only is cheaper on a call that runs every
      session. Also: does an *extra* skill in the installed tree (a user's own)
      count as drift? It must not.
- [ ] **Q7.** Caching. `get_status` runs on every session's first call, but
      `detectFormat` deliberately re-stats because the GUI can migrate underneath
      a live server (`store.ts:167-171`). Does the staleness result inherit that
      hazard, and if so is a mtime+size stamp enough?
- [ ] **Q8.** Should `version.json` gain `reconciledWith` (the product version
      the repo was last reconciled against) in this ticket, given nothing writes
      it until `kanmer-setup` does? `kanmer-setup` SKILL.md §2 already instructs
      the agent to compare against exactly this non-existent value. Adding the
      field with no writer means it is permanently absent, which must report
      `unknown`, never `behind`.
