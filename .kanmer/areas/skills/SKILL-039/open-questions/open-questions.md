- [x] **Does `obsolete-after-change` require a non-empty `reason`?** Yes
  *(operator decision 2026-09-02)*. The reason names the superseding commit —
  `superseded by <sha>`. It therefore joins the `rejected-with-reason` /
  `accepted-risk` condition at `review-attestation.ts:74`, and the existing
  error message already interpolates the disposition name.

  (`openBlockingReviewFindings`) blocks only

  `eligible` array is the proof; the file itself is on the do-not-modify list.
- [x] **Does `check-pr.mjs` hold a second disposition enum to keep in step?**
  No. It imports `parseReviewAttestation` from `@kanmer/core` (`:13`) and only
  reshapes the result (`:83–96`). The CI gate follows the core change with no
  edit, once the bundle is rebuilt.
- [x] **Is a new attestation field needed for outdated threads?** No — the
  ticket's "Not in scope" forbids any field beyond the one enum value, and
  `threads_snapshot` (documented at `kanmer-review/SKILL.md:213–221`) has no
